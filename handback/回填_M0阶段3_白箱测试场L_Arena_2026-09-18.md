## C. 卡点（全部本机实测，**本轮的主要产出**）

### C-1 ★★★ `unreal.Rotator` 的位置参数顺序是 (roll, pitch, yaw)，不是 (pitch, yaw, roll)

**症状**：`L_Arena` 与 `L_TuningRange` 两张图在编辑器视口和 `-game` 里**全部渲染成纯黑**；HUD 正常、Actor 数量正常（229 个 StaticMeshActor 全部有有效 StaticMesh 和材质）、相机位置正确、帧率还很高（200+ fps）。

**根因**（A，`ue5ops/_scratch/editor_probe4.py` 回读）：

```python
unreal.Rotator(-42, 30, 0)   # 期望 pitch=-42 yaw=30 roll=0
# 实际得到: pitch=30.0  yaw=0.0  roll=-42.0
```

于是 `spawn_actor_from_class(unreal.DirectionalLight, loc, unreal.Rotator(-45, 0, 0))` 造出来的太阳 **pitch = 0 / roll = -45 —— 横着照甚至朝上照**：

- 朝上照的太阳 = 地面与所有方块的 `dot(N, -L) < 0` = **零直射光**
- 天空大气把太阳算到地平线以下 = **夜空全黑**
- 于是"几何全在、光全没了" → 全黑，且因为没有东西可画，帧率飙到 200+ fps

**验证方法**（A，可复现）：`-game -ExecCmds="r.ForceDebugViewModes 1, viewmode unlit"` —— Unlit 下蓝机体、灰参照柱、掩体块、调试线**全部正常画出**，Lit 下全黑。`viewmode lightingonly` 全黑 = **场景里一点光都没有**。这一对视图模式是本轮最有用的诊断手段。

**修法**：一律用关键字构造 —— `unreal.Rotator(pitch=..., yaw=..., roll=...)`，并在 builder 里**回读自校验**（`build_arena.py` 现在会打印 `SunLight 旋转 期望=... 实际=... OK`）。

### C-2 ★★★ `LevelEditorSubsystem.save_current_level()` 打印成功但**不写盘**

**症状**：builder 打印 `save_current_level OK`、不抛异常、Actor 数也对，但 `.umap` 的**修改时间一直不变**。于是后面所有"我改了光照/加了后处理体积"的修复都只停在内存里，编辑器/游戏读到的仍是旧关卡 —— 这个坑让我白排查了近一小时。

**证据**（A）：`ls -la --time-style=full-iso Content/AC6/Maps/` 显示 `L_Arena.umap` 的 mtime 停在 21:37:39，而期间至少跑了 3 次 builder。

**修法**：
```python
unreal.EditorLoadingAndSavingUtils.save_map(unreal.EditorLevelLibrary.get_editor_world(), MAP_PATH)
```
返回 `True` 且文件时间确实更新（已验证：22:31:46 / 383906 B）。

### C-3 ★★ `LevelEditorSubsystem.new_level(path)` 在目标已存在时**静默失败**

**症状**（A，日志原文）：
```
LevelEditorSubsystem: Error: NewLevel. Failed to validate the destination.
An asset already exists at this location.
```
**它只打这一行，不抛异常、也不建关卡。** 脚本如果 `try/except` 就会以为建好了，然后所有 Actor 都 spawn 进了"当前那个旧关卡"。

**修法**：整条链路改成 **`new_blank_map(False)` + `save_map(world, path)`** 两件套 —— 幂等、可重复、且真的落盘。两个 builder（`build_arena.py` / `build_tuning_range.py`）都已改。

### C-4 ★★ commandlet 建的关卡里，SkyLight 必须是 RealTimeCapture

默认 `ASkyLight` 是 `SourceType = SLS_CapturedScene` + `bRealTimeCapture = False`，环境光来自**在编辑器里烘焙一次的立方体贴图**。而我们的关卡是 `-run=pythonscript` commandlet 建的 —— **commandlet 不渲染，`recapture_sky()` 永远不会完成，立方体贴图是空的 = 环境光为 0**。

模板关卡 `Lvl_ThirdPerson` 能正常渲染，正是因为它的 SkyLight cubemap 是当年在编辑器里烘好的。

**修法**：`lc.set_editor_property('real_time_capture', True)` 并**回读确认**（builder 现在会打印 `SkyLight real_time_capture=True 已确认`）。

### C-5 ★★ 抓 UE 窗口截图前必须声明 DPI 感知

`GetWindowRect` 在非 DPI 感知的 PowerShell 进程里返回**被虚拟化的坐标**：请求 1280×720 的窗口，实际只抓到了左上角约 66% 的画面（1944×1139 才是对的）。这直接导致我早期所有截图的构图判断都是错的（准星不在画面中心）。

**修法**：`Add-Type ... SetProcessDPIAware()`（已写进 `_scratch/shot_any.ps1`）。

**更根本的教训**：**不要用 GDI 抓窗口来判断"渲染对不对"**。本轮真正解决问题的是引擎自己的调试视图模式（`viewmode unlit` / `lightingonly`）。

### C-6 `-game` 下 `UE_LOG` 有时进不了日志

在 Pawn 的 `Tick` 里加的 `UE_LOG(LogTemp, Warning, ...)` 诊断，跑 60 秒一次都没出现；同一份代码在 `BeginPlay` 里的 `UE_LOG` 却正常。**修法**：把诊断直接画在 HUD 上（`AAC6DebugHud` 的 `bShowDiag` 块，F2 开关）—— 画 HUD 是每帧必跑的，一定看得到。

### C-7 沿用上轮（已记在回填 #2，此处只补一句）

`-run=pythonscript` 下做关卡编辑，脚本执行成功、地图已存盘，引擎退出阶段仍在 `python311.dll` 里 `EXCEPTION_ACCESS_VIOLATION`（退出码 3）。**产物为准，不看退出码。**

## D. 给文档 session 的回填（需要你更新 `outputs/` 的地方）

### D-1 ★ `P1_镜头与相机系统_报告.md` §2.2 有一处读数错误

报告里那张 12 行参数表的第 5 列写着「FOV-Y **变化量**（度），实测 25~60，均值 43.06」。

**实际是 `LockCamParam.CamFovY` = 绝对垂直画角[deg]。** 我用 98 行全量复算：min 25 / **均值 43.06** / max 60 —— 均值逐位吻合，列身份可以确定。

**结论要改**：AC6 的 FOV 是**基线 45°（垂直）**（`Bipedal_legs` 行），不是"基线 + 25~60 的增量"。换算到 16:9：**45° 垂直 = 72.73° 水平**；UE 默认水平 90° = 垂直 58.72°，**明显比 AC6 宽**。这一条直接决定了复刻的镜头手感，必须改。

### D-2 ★ P1 关于「AB 时相机拉远」的 C 级猜测与数据相反

报告 §2.2 写「AB：距离 20~30（拉远）」。数据是**反过来**的（A，`DT_LockCam[FNR_Assault_Boost_2_legs]`）：

| 字段 | 基础态 `Bipedal_legs` | AB 态 `FNR_Assault_Boost_2_legs` |
|---|---:|---:|
| `CamDistTarget` | 26 m | **9 m**（拉近！） |
| `CamFovY` | 45° | **60°**（+15°） |
| `ChrOrgOffsetY` | 12 m | 6.5 m |
| `ShoulderOverDeg` | 3° | 51° |
| `ChrTransChaseRateForBoostX/F/B` | — | **0.95 / 0.85 / 0.85**（几乎刚性跟随） |

**即：AB 的速度感不是靠"相机滞后"，而是靠"拉近 + 广角 + 刚性跟随"。** 滞后的机制属于 QB（同一行内 `ChrTransChaseRateForQBX` 从 0.45 掉到 0.22）。这修正了 P1 把 AB/QB 归为同一种机制的说法。

- **`EquipParamBooster.QBAccelTimeF30` 的单位是"帧 @30fps"**，不是秒。8~16.5 帧 = **0.267~0.55 s**，正好对上 M0 §3.10 里 T3 靶写的"灯亮 0.27~0.55 s"。
