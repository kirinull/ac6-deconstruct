# §1 概览与愿景（Overview and Vision）

> **业界标准要求这一章写**：游戏标题与标语 · 高层概要（电梯稿）· **设计支柱（Design Pillars）** · 目标受众 · 类型与平台
> **其中"设计支柱"是整份策划案最重要的部分**——它是"每一个决策都要对照的核心体验"。
> 原文的例子：*Hades 的设计支柱是"快节奏流畅的战斗"与"通过重复挑战获得的叙事深度"，**每个功能都要对照这两条检查***。

## 1.1 标题与标语

| 项 | 内容 |
|---|---|
| 标题 | 《装甲核心6：境界天火》/ ARMORED CORE VI FIRES OF RUBICON |

> **策划案写法提示**：标语不是广告词，是**给团队的定位锚**。它必须能回答"这个游戏最独特的那个点是什么"。

## 1.2 电梯稿

> **一款高速三维机甲动作游戏。它不给你难度选项——难度藏在装配界面里。你不靠操作变强，你靠理解"伤害类型 × 资源预算 × 时机窗口"这三条轴变强。**

## 1.3 ★ 设计支柱（本文最重要的部分）

> **这五条是从实测数据反推出来的**，不是先有口号再找证据。
> 每条都给出：**数据证据** + **它如何约束其他决策**（这是"支柱"之所以是支柱的判据）+ **代价**。

### 支柱 ① 装配即难度（Assembly is the difficulty dial）

| | |
|---|---|
| **一句话** | 卡关的解法是"回去改装"，不是"调低难度"或"练更熟" |
| **数据证据** | 选项菜单 **62 条属性里没有任何难度项**；无字号设置、无色盲模式 [B]<br>装配三层约束：**硬门**（总重超腿载重 → 默认禁止出击）+ 软门（臂载重）+ 资源门（EN 负荷）[B]<br>OS 强化 **197 点可得 vs 287 点全满 = 68.6%**，结构性取舍 [B]<br>存在 `AutoAssembleEvaluate`（自动配装评分）→ 官方知道这是难点并给了兜底 [B] |
| **如何约束其他决策** | ① 12 个槽位不是"丰富度"，是**难度旋钮的分辨率**<br>② 总重必须是**硬门**——"能不能出击"若是连续值，玩家读不出边界<br>③ 结算必须在**任务完成时**才扣弹药/修理费，否则玩家不敢试新配置（§2.4） |
| **代价** | 新手不知道"该换什么"。**这是"设计很好但传达失败"的典型** |

### 支柱 ② 技巧在时机，不在准度（Timing over aim）

| | |
|---|---|
| **一句话** | 让"什么时候打"和"打哪里"变得和"打得中"一样重要 |
| **数据证据** | 引入会自我衰减的**第二血条（ACS 姿态）**，打满进易伤窗口 [B]<br>**QB（快速推进）无无敌帧**（三处独立来源一致）→ 闪避靠空间位移，不靠时间无敌 [B]<br>直击补正（`staggerCriticalRate_*`）让硬直窗口内的伤害成为独立乘区 [B]<br>存在多层瞄准辅助：水平补正角众数 **15°**、垂直 **25°**；软锁 450 m、导弹锁 280 m [B] |
| **如何约束其他决策** | ① 瞄准辅助可以做得慷慨——**因为技巧不在这里**<br>② QB 不能给无敌帧——**给时间无敌会摧毁时机判断**<br>③ 敌人必须有 **0.3~1.2 s 的预警段**——闪避容错与预警时长是一对必须联调的参数 [C] |
| **代价** | 需要**第二条资源条**（姿态），UI 复杂度上升；且必须教会玩家它是什么 |

### 支柱 ③ 重不等于慢，重等于预算（Weight is budget, not slowness）

| | |
|---|---|
| **一句话** | "重"指的是**你要多花多少 EN、多等多久、少带什么**，而不是"动作变慢" |
| **数据证据** | 总重曲线：**3 倍重量只掉 35% 速度**（断点 40000/62500/75000/80000/120000 kg，倍率 1→0.65）[B]<br>重量感由 **8 条并行通道**表达（二次运动、伺服延迟、悬挂行程…），**不是调慢动画** [B]<br>角速度基本被设为"无限"（258 行转向数据里 **159 行**），**主动放弃转动惯量** [B]<br>10 m 落地：机甲 **0.408 s** vs 等比放大的成人 **1.429 s**（差 3.5 倍）；重力 **120 m/s² = 动态相似律预测的 2.20 倍** [B] |
| **如何约束其他决策** | ① 惩罚曲线要**缓**，门槛要**硬**——否则重装直接不可玩<br>② 必须**故意违反物理律**（超重力、无限角加速度）——等比放大做不出机甲感<br>③ "重"要有好处（踢击伤害 ×2、重量加成 ×1.25），否则只是惩罚 |
| **代价** | 物理"假"，懂行的玩家会发现不符合动力学 |

### 支柱 ④ 信息分级，不隐藏（Layer, don't hide）

| | |
|---|---|
| **一句话** | 屏幕上的信息不删减，但分层 + 定时 + 只在需要时出现 |
| **数据证据** | HUD 槽位表 `MenuPropertyLayoutParam` **2512 行**在描述这些槽位 [B]<br>但实现了**状态驱动显隐**：脱战后按写死的秒数淡出（血条 1.5 s、归零 0.3 s）[B]<br>**锁定框大小写实地反映"离锁上还差多远"** → 玩家不用教程就学会 280 m 是导弹锁分界线 [B]<br>战斗内瞬时反馈集中在 **0.3~2.0 s（中位 ≈1.0 s）** [B] |
| **如何约束其他决策** | ① 面板数量可以多（因为会淡出），但**中心区域必须留白**<br>② 显示"判定依据的量"而不是判定结果<br>③ 可读性优先级：**亮度分层 → 轮廓 → 时间闸门 → 颜色**——颜色是最后一道防线 [B] |
| **代价** | **从未提供整体简化档位**（无字号设置、无色盲模式）——对新玩家不友好 |

### 支柱 ⑤ 叙事永不打断循环（Narrative never blocks the loop）

| | |
|---|---|
| **一句话** | 最大的一块叙事，放在玩家**本来就在做别的事**的时间轴上 |
| **数据证据** | 战斗中通讯 **5965 条 / 248,181 UTF-16 码元**，占全部菜单文本池 **58.3%**，是第二大通道的 **6.6 倍** [B]<br>但**唯一 100% 送达的通道是任务简报**（约 260 条串 ≈12,800 码元，只占文本池 **5.2%**）[B]<br>分支做成"数据可用性"（互斥任务 ID）而非演出分支 → 存档只存"已完成任务集合" [B] |
| **如何约束其他决策** | ① 核心循环（接单→出击→交战→结算→改装）**不允许插入过场**<br>② 因此**必须有冗余通道**（可选长文档案），因为战斗中通讯的吸收率不可控<br>③ 把"选边"接到核心循环上——**每条分支给专属机体部件**，让叙事决定变成构筑决定 [B] |
| **代价** | 战斗中通讯的吸收率不可控；不看的玩家会完全迷失 |

### 1.3.1 设计支柱自检表（策划案可直接复用）

> **这是本文最该抄走的一页。** 当你写自己的策划案时，把每条支柱填进这个表——
> **填不出来的支柱就是口号，不是支柱。**

| 检查项 | 好的支柱 | 坏的口号 |
|---|---|---|
| 能不能用**一句玩家能感知的话**说清？ | "卡关就回去改装" | "深度策略体验" |
| 有没有**至少 3 条数据/事实**支撑？ | 3 条以上 | 0 条 |
| 能不能**否决一个具体方案**？ | "QB 不能给无敌帧，因为…" | 无法否决任何东西 |
| 有没有**明确的代价**？ | "新手不知道该换什么" | 只有好处 |
| 团队 A 与团队 B 的理解会一致吗？ | 会 | 不会 |

## 2.1 核心循环（四个嵌套的时间尺度）

> **策划案写法提示**：核心循环**不是一个环，是嵌套的多个环**。每个环都必须有自己的"结算时刻"。

```
┌─ 0.2 ~ 3 秒：交火环 ──────────────────────────────┐
│  读招 → 闪避(QB) → 反击 → 打姿态 → 硬直 → 爆发伤害  │
│  结算时刻：破防的那一下                              │
└──────────────────┬───────────────────────────────┘
┌─ 3 ~ 30 秒：遭遇环 ──────────────────────────────┐
│  资源管理（EN/弹药/AP）→ 判断该不该继续 → 打或撤     │
│  结算时刻：敌人倒下                                 │
└──────────────────┬───────────────────────────────┘
┌─ 5 ~ 20 分钟：任务环 ────────────────────────────┐
│  出击 → 清目标 → Boss → 结算（评价 + 报酬）→ 改装    │
│  结算时刻：评价页 + 报酬到账                        │
└──────────────────┬───────────────────────────────┘
┌─ 20+ 小时：周目环 ───────────────────────────────┐
│  买装备 → 打竞技场拿 OS 点 → 解锁分支 → 新周目新视角  │
│  结算时刻：新结局 / 新专属部件                       │
└──────────────────────────────────────────────────┘
```

### 一条可迁移的设计约束

> **TTK ≥ 机制链长度 × 单环耗时。**
> AC6 的机制链是 3~4 环、单环 2~4 秒 → **TTK 下限 8~15 秒**。
> **如果 TTK 缩短 10 倍，姿态系统直接失效**（第二血条永远打不满）[C]。
>
> 这是用数学**否决一个节奏方案**的样板。当有人说"把 TTK 做短更爽"，你可以回答这个。

## 2.2 主要机制

| 机制 | 设计要点 | 关键数据 |
|---|---|---|
| **移动** | 走 / 冲刺 / 悬浮 / QB / AB 五种；EN 池同时供机动与能量火力 | 冲刺终速 **430 km/h**、飞行 408、滑行 600、重力 **120 m/s²** [B] |
| **锁定** | 三层：软锁 / 硬锁 / 解耦；锁定框大小 = 判定依据可视化 | 通常锁 **450 m**、导弹锁 **280 m**、进瞄准模式 ×2；脱锁粘滞 1.5 s [B] |

## 2.4 成长与经济系统

| 机制 | 设计要点 | 关键数据 |
|---|---|---|
| **三条互不重叠的解锁管道** | 钱（商店，248 件）/ 条件解锁（21 件非卖品）/ 令牌（95 个）。**规模比 24 : 248 : 95 就是设计意图的自白** | [B] |
| **"性能税"而非"失败惩罚"** | `成本 = 原始消耗 × 系数`，再取上限。**系数决定惩罚哪类行为，上限决定最坏情况** | 弹药率全 1.0、修理系数 **2.0**、上限均 **200,000** [B] |
| **只在任务完成时结算** | 否则玩家为省钱不敢试新装配 → **直接摧毁支柱①** | 双上限合计 400,000，而 **46/59 行基础报酬低于它** [B] |
| **官方对照实验** | 唯一全 0 的例外是**脱狱关**（那一关你没用自己的机体） | [B] |
| **经济缺口驱动重复消费** | 一周目买不满目录 → **重打是必然而非可选** | 单周目可得 **15,048,000 ÷ 全目录 62,052,000 = 24.25%**；含竞技场 29.35% [A] |

### 2.4.1 ★ 一个可以直接抄走的机制：装配即难度的三层约束

| 层 | 约束 | 性质 | 为什么这么分 |
|---|---|---|---|
| **硬门** | 总重 vs 腿载重 | **能 / 不能**（超了默认禁止出击） | "能不能出击"必须是**单点**，玩家才读得出边界 |
| **软门** | 臂载重 | 连续惩罚（QB 恢复时长最高 ×3.5） | 让玩家有调优空间，不是撞墙 |
| **资源门** | EN 负荷 | 挤压其他预算 | 制造取舍，而不是禁止 |

> **可迁移结论**：**惩罚曲线要缓、门槛要硬。**
> 把"能/不能"的单点门槛单独抽出来，其余全部做成连续预算——这是 AC6 数值设计里最值得抄的一条分工。

# §3 叙事与角色（Narrative and Characters）

> **业界标准要求这一章写**：世界观 · 剧情大纲 · 角色设定与动机 · **叙事机制（story 与 gameplay 如何交互）**
> 原文特别提到：*"Narrative Mechanics: How story and gameplay interact (e.g., Bioshock's audio logs)"*——**这一项最容易被漏，而它是 AC6 做得最好的部分之一**。

---

## 3.1 世界观（一句话骨架）

> **一颗被"珊瑚"（Coral）覆盖的星球上，几家企业为了这种既是能源又是准生命体的物质相互争夺；玩家是一名"强化人"佣兵，被雇来打这场代理人战争。**

## 3.2 叙事载体：六条通道的预算分配

> **这是 AC6 叙事设计最值得学的一张表**——它把"叙事"当成**一套投放预算**来管理。

| 通道 | 规模 | 占比 | 吸收率 |
|---|---:|---:|---|
| **战斗中通讯** | 5965 条 / 248,181 码元 | **58.3%** | 不可控（但注意力免费） |
| 菜单文本 | 约 1721 条 | — | 主动查看 |
| 档案（Archive） | 51 条、均长 371.9 | — | 主动查看 |
| 提示（Tips） | 114 条 | — | 主动查看 |
| 邮件（Mail） | 46 条 | — | 主动查看 |
| **任务简报** | 约 260 条串 ≈12,800 码元 | **5.2%** | **唯一 100% 送达** |

**结论**：把**最贵的池**放在玩家已经在操作的时刻；但**必须保留一条 100% 送达的通道**（任务简报）作为冗余。[B]

## 3.3 信息分期揭露（按"消化能力"排序）

| 顺序 | 玩家此刻的问题 | 投递方式 |
|---:|---|---|
| 1 | 我下一步打哪？ | 任务简报（100% 送达） |
| 2 | 我正在打谁？ | 战斗中通讯（短、情绪化） |
| 3 | 为什么会这样？ | 档案 / 邮件（可读长文，可选） |
| 4 | 谁在操纵一切？ | 跨周目解锁 |

## 3.4 角色设计：三角色代词化

| 角色 | 叙事功能 | 为什么这么设计 |
|---|---|---|
| **雇主**（Handler Walter） | 告诉你去哪、为什么 | 替代"任务说明"这种冷冰冰的 UI |
| **异质他者**（Ayre） | 让你质疑自己的立场 | 提供与主线对立的价值坐标 |
| **镜像对手**（Rusty / Iguazu） | 展示"如果当初选了另一条路" | 用同为佣兵的 NPC 反照玩家 |

**主角是沉默无脸的**，人格表达**外移到外观系统**：[B]
- `EmblemPieceSpec` **997 行**、`DecalParam` 248 行、配色 **882 行**、预设徽章 147 行
- **表达系统的规模（近 2300 行）是解释系统（Archive 57 行）的 40 倍**

> 这本身就是一句策划案该写的话：**"玩家想被看见，胜过想知道。"**

## 3.5 分支结构：做成"数据可用性"，而不是"演出分支"

| 手段 | 做法 | 好处 |
|---|---|---|
| 互斥任务 | 完成 A → B 从菜单消失 | **零演出成本** |
| 存档 | 只存"已完成任务集合" | 天然可存档、可回放 |
| 分支奖励 | 每条分支给**专属机体部件** | **把叙事决定变成构筑决定** |

**数据**：8 组互斥分支（其中一组 3 选 1）+ 6 个 ALT 变体；三终局报酬 550k / 340k / 660k [A]

# §4 美术与美学（Art and Aesthetics）

> **业界标准要求这一章写**：视觉风格指南 · 情绪板 / 参考图 · **可及性考量（色盲模式、对比度）**
> ⚠️ **注意**：可及性是标准章节，而 **AC6 在这里是缺项**——这正是一个策划案该显式讨论的地方。

---

## 4.1 视觉风格与可读性优先级

> **核心原则：可读性不靠色相，靠亮度差。**

| 优先级 | 手段 | 说明 |
|---:|---|---|
| 1 | **亮度分层** | 自发光承担"状态/功率感"的信息通道 |
| 2 | **轮廓** | 盾命中是波纹、装甲命中是烟尘——**形状先于颜色** |
| 3 | **时间闸门** | 50 m 内近失 SFX 最多 1 个、多段命中间隔 200 ms [B] |
| 4 | **屏幕中心留白** | 中心只放"我现在能不能打" |
| — | **颜色编码** | **最后一道防线，不是第一道** |

## 4.2 关键美术技术决策（设计层）

| 决策 | 数据 |
|---|---|
| **发光与反光分工**：自发光是信息通道，反光是材质通道，**二者不可互替** | — |
| **玩家自定义外观靠"5 层材质栈 + 参数覆写 + 5 通道分区配色"**，美术只画一张部位遮罩 | 46 行材质预设 + 24 行旧化预设 [B] |
| **打击反馈做成"攻击属性 × 目标材质"二维矩阵 + 频率闸门** | `HitEffectSfxParam` **71 行 × 25 槽**；**金属命中用满 10 个 ID，能量盾命中只复用 2 个** [B] |
| **先做闸门，再做美术** | 否则优化阶段被迫砍掉一半美术量 |

## 4.3 性能与画质的设计化

| 项 | 值 |
|---|---|
| 动态画质阶梯 | 30 fps 档阈值 30.60/31.60、60 fps 档 60.60/61.60 [B] |
| **不对称迟滞** | **降 5 帧 / 升 20 帧**；降后冷却 30、升后冷却 10 [B] |
| 可降项 | **19 个**可独立升降的画质项 [B] |
| LOD | 尺寸分桶（100/200/350/∞ m）+ 平台缩放曲线（PS4 最狠 0.962→0.475）[B] |

> **可迁移**：跨平台游戏的"降级"应该**做进设计**，而不是留到优化阶段。

## 4.4 ❌ 可及性缺项（策划案里必须显式承认的部分）

| 项 | AC6 的现状 | 证据 |
|---|---|---|
| 字号设置 | **无** | 选项菜单 62 条里没有 [B] |
| 色盲模式 | **无** | 同上 [B] |
| 字幕 | 仅 ON / OFF | [B] |
| 难度选项 | **无**（这是设计选择，不是疏漏） | [B] |
| HUD 可调 | 位置 / 缩放 / 不透明度，4 个槽位 | [B] |

> **策划案写法**：可及性缺项**不该被隐藏**。写成"我们已知的取舍 + 理由 + 补偿手段"，比不写更专业。
> AC6 的补偿手段是：**训练场（7 关）+ 档案（57 条）+ 自动配装**。

# §5 音频设计（Audio Design）

> **业界标准要求这一章写**：音乐风格 · 关键音效清单（脚步 / UI / 战斗）· 配音计划
> **AC6 的特殊之处**：音频不只是"氛围"，它**承担了信息通道的职责**——所以这一章要按"带宽"来写，不是按"风格"来写。

---

## 5.1 核心设计决策

| # | 决策 | 为什么 |
|---:|---|---|
| 1 | **先设计调度器类别，再设计音效资产** | "一直响"的循环层与"点一下"的一次性层分成两套调度器：前者用连续参数控，后者靠**并发槽位 + 重播冷却**硬控。<br>**独立游戏最常犯的错是：先做 200 个 wav，再想它们怎么共存。** |
| 2 | **音频参数维度必须正交，不能做成 10 层 if 树** | 武器音色拆成 **4 个独立维度**同时生效：武器类型 14 × 射击分类 38 × 材质 17 × 攻击力档 3 [B] |
| 3 | **"体量"写成参数，不靠听感调** | 低频 + 震动双通道、距离不衰减、同一事件三层距离变体 |
| 4 | **动态音乐先定义"状态枚举"，再定义"谁负责把状态推回去"** | 105 行的过场表就是一张**状态回推表**——这是最容易漏的一环 |
| 5 | **高速场景用"距离分档 + 碰撞点统计"代替手摆混响触发器** | 避免机甲一帧飞 100 m 时穿过 5 个触发器 |
| 6 | **语音按独立资源池 + 独立空间处理 + 独立混音目标对待** | 而不是"加了个人声" |

## 5.2 关键数据

| 项 | 值 | 等级 |
|---|---|---|
| BGM 状态 | **8 个**：normal / in_combat / heat_up_1~5 / death → **战斗强度是一把 6 档连续量** | B |
| 重播冷却 | 弹着音最短间隔 **0.56 s**；反制推进音 0.4 s；"致命一击音"专门留 **0.6 s** 延迟预算 | B |
| 单条攻击限流 | 挂 4 个限流秒数；弹药 / 落地 / 飞行上限分别为 0.45 / 1.0 / 1.0 s | B |
| **带宽取舍** | 联机对战中**超过 600 m 的地图着弹音直接省略**——用音频预算换 CPU 与带宽 | B |
| 动态混响 | 按距离分档 4 档：50–290 / 290–620 / 620–900 / 900–1024 m，室外默认干声 | B |
| 平滑时间 | 连续参数变化统一 **100 ms** | B |
| 音频参数的可调范围 | 上下各只能挪约 **2~3 倍**（而战斗数值可以 ×10）→ **所以调参只能靠实测听感** [C] | B/C |

## 5.3 "声音是 AI 的输入"——一个需要小心表述的结论

| 报告 | 说法 | 证据 |
|---|---|---|
| P11 | 声音是 AI 的输入 | `AiSoundParam` 听觉半径 30 / 100 / 150 m [B] |
| P12（纠错） | AI 听觉实际关闭 | 听觉半径字段 **1047/1178 行填 0.1 m** [B] |

**调和后的正确表述**（本文采用）：

> **"声事件广播"与"AI 感知参数"是两套通道。**
> 命中 / 开火会**广播声事件**，但 AI 是否响应由**脚本**决定，不由这个半径字段决定。

> **策划案写法提示**：当两个结论冲突时，**不要二选一，也不要和稀泥**——
> 写"这是两套通道"，并说明各自负责什么。**这比选一个更准确。**

## 8.2 里程碑推断（按依赖关系，不是按时间）[C]

> **能写进策划案的是"依赖顺序"，不是"日期"**——日期是团队的，依赖是设计的。

| 阶段 | 必须先完成什么 | 为什么不能跳 |
|---:|---|---|

| 3 | **相机与锁定** | 依赖移动；相机不做对，后面所有战斗测试都不可信 |
| 4 | **战斗数值核心（ACS）** | 依赖 1、2；**这是整个战斗系统的支点** |
| 5 | **反馈系统** | 依赖 4；反馈是"能不能读出信息"的问题，不是"好不好看" |
| 6 | **武器与弹道** | 依赖 4、5 |
| 7 | **装配系统** | 依赖 1、4；**卡关解法依赖它，所以必须在 Boss 之前完成** |
| 8 | **敌人 AI** | 依赖 4、6 |
| 9 | **动作与动画** | 依赖 2、5 |
| 10 | **关卡与任务** | 依赖 8、9 |
| 11 | **UI / HUD** | 依赖 3、4 |
| 12 | **音频** | 依赖 5、6 |
| 13 | **表现力打磨** | 最后 |

## 8.3 风险清单

| 风险 | 说明 | 缓解手段（AC6 实际用的） |
|---|---|---|
| **范围爆炸** | 12 槽位 × 全武器 × 多关卡 | 经济缺口（一周目只买得起 29%）→ **内容量被刻意限制** [B] |
| **新手墙** | 机制好但传达失败 | 训练场 7 关 + 自动配装 + 任务简报 100% 送达 [B] |
| **平衡补丁推翻既有经验** | 1.02 削弱 Balteus 引发老玩家不满 | 制度化热更（把数值做成可独立更新的快照）[C] |
| **PvE / PvP 平衡冲突** | 同一套数值服务两边 | `MultiPlayCorrectionParam` **仅 2 行** → **官方也隔离不干净**，只能靠热更 [B] |
| **任务结构重复** | 21 区域支撑 49 任务 | 用**限时 + 评分**制造差异，而不是靠新几何 [B] |
| **数据只增不减** | 废弃字段堆积 | paramdex 显式标记（**53 个字段**）[B] |

# §9 已知代价与争议（策划案的"取舍说明"）

> **为什么评价好的策划案都有这一章**：策划案的本质是**做取舍**，不是列功能。
> 只写优点的文档，读的人会怀疑你没想过代价。**主动写代价，是专业度的信号。**

---

| # | 代价 / 争议 | 具体是什么 | 证据 | 怎么评价 |
|---:|---|---|---|---|
| 1 | **无难度选项 → 门槛转移** | 不提供难度设置，只能靠换装调节 | 选项菜单 **62 条无任何难度项**；**无字号、无色盲模式** [B] | 它把"调节难度"的门槛从"菜单点一下"**提高到"理解装配系统"**——对新手是真实的墙 |
| 2 | **新手墙在"装配"而非"操作"** | 官方希望你换装，但新手不知道该换什么 | 存在 `AutoAssembleEvaluate`（官方兜底）[B] | **"设计很好但传达失败"的典型**。做复刻时如果要改进，**这里最值得改** |
| 3 | **信息密度过高** | HUD 同时呈现 7 类信息 | `MenuPropertyLayoutParam` **2512 行** [B] | 核心玩家觉得"专业"，新玩家觉得"糊"。有状态驱动显隐，但**无整体简化档** |

| 5 | **任务结构重复** | 多为"到地点 → 清敌人 → Boss" | 21 区域 / 49 任务 [B] | 这是**内容产能**问题，不是设计能力问题。**但提醒你：机制漂亮 ≠ 内容耐玩** |
| 6 | **PvP / PvE 隔离不彻底** | 同一套数值服务两边 | 联机修正层**仅 2 行** [B] | 所有"PvE 数值直接搬进 PvP"游戏的**通病** |

## 9.1 三条"取舍说明"的写法（可直接套用）

| 模板 | AC6 的例子 |
|---|---|
| **"我们选择了 X，代价是 Y，我们用 Z 补偿"** | 选择"装配即难度"，代价是新手不知道该换什么，用"自动配装 + 训练场"补偿 |
| **"这个数字看起来是 bug，其实是有意的"** | 12 行剧情任务的 S 阈值 <0（**怎么打都是 S**）——用数值给演出关免除评价压力 |
| **"我们知道它不完美，但改它要付更大代价"** | 联机修正层只有 2 行——把产能留给单人内容（因为 PvP 只是配菜） |

## C.2 三份真实历史策划案的结构实证

> 上面两份是**写作规范**（教你该怎么写）。下面这些是**真实成品**——
> 我把它们下载下来提取了文本，用来**验证本文采用的结构是否站得住**。

### 实证 ① 《Planescape: Torment》Product Review Packet（1997, v1.5, 47 页）

这是业界被引用最多的策划案之一（当年代号 **Last Rites**）。它的**真实目录**（原文抄录）：

| 章节 | 原文副标题 |
|---|---|
| QUICK INTRO | *"To start the engine..."* |
| **VISION STATEMENT** | *"Contained herein are all the hopes and dreams for this project."* |
| **TEAM VISION STATEMENT** | *"Team vision statement."* |
| THE MANGY CAST | 角色圣经（character bible） |
| MANAGEMENT AND MARKETING REALITIES | 商业与营销现实 |
| DEVELOPMENT | *"Our system for how we plan to build..."* |
| DA FUCKING PLOT | 详细剧情 |
| GAMEPLAY ELEMENTS | 玩法机制评注 |

**它的 HIGH CONCEPT 原文**（一句话讲完）：

> *"The player is a scarred, amnesiac immortal in search of his identity. On the way, the player character will kill a lot of people...including himself."*

### 实证 ② Narbacular Drop Technical Design Document（2004, DigiPen —— 即 Portal 的前身）

| 一级 | 二级 |
|---|---|
| Project Overview | **Game Concept** / Technical Goals / System Requirements / **Technical Risks** / Third Party Tools |
| Game Play | Game structures / Physics / … |

### 实证 ③ 与现代指南的对照

| 现代指南（8 章骨架） | Torment 1997 / Narbacular 2004 | 本文对应 |
|---|---|---|
| 1 Overview and Vision | VISION STATEMENT + TEAM VISION STATEMENT | §1 |
| 2 Gameplay Core | GAMEPLAY ELEMENTS + DA FUCKING PLOT | §2 |
| 3 Narrative and Characters | THE MANGY CAST + DA FUCKING PLOT | §3 |
| 4 Art / 5 Audio / 6 UI | （散落在各章） | §4 / §5 / §6 |
| 7 Technical | Narbacular Drop 的 Project Overview | §7 |
| 8 Project Planning | DEVELOPMENT + **MANAGEMENT AND MARKETING REALITIES** | §8 |

> **结论：本文采用的 8 章结构，与 1997 年的顶级策划案、2004 年的技术设计文档都能对上。**
> 这说明**策划案的骨架三十年来是稳定的**——变的是载体（Word → wiki），不是结构。

## C.3 从真实范本里提炼的 6 条写法

| # | 写法 | 证据 |
|---:|---|---|
| 1 | **愿景优先，且要单独成章** | Torment 把 VISION STATEMENT 放在第一大章（约 12 页） |
| 2 | **高概念必须是一句话** | Torment 的 HIGH CONCEPT 一句话讲完主角与核心冲突 |
| 3 | **团队共识要单独写一节** | Torment 有独立的 TEAM VISION STATEMENT——**"我以为我们想的一样"是项目最大的隐性风险** |
| 4 | **商业与技术约束要写进策划案本身** | Torment 有 MANAGEMENT AND MARKETING REALITIES；Narbacular Drop 有 System Requirements 与 Third Party Tools |
| 5 | **风险显式成节** | Narbacular Drop 把 Technical Risks 单列；本文对应 §8.3 与 §9 |
| 6 | **语气可以有性格** | Torment 敢写 "DA FUCKING PLOT"、"COOL ENGINE SHIT"，还带自嘲旁注。**好策划案是给人读的，不是给流程看的** |

> **第 3 条最容易被忽略，也最贵**：一份没写"团队共识"的策划案，会让美术、程序、策划各自理解出一个不同的游戏。
> **本文的"设计支柱"（§1.3）就是团队共识的载体。**
