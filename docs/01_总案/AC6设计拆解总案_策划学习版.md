## §1 一句话读懂 AC6 的设计主张

> **"把'难度'从菜单里拿走，塞进装配界面；把'技巧'从准度里拿出来，放进时机里。"**

展开成四句话：

| # | 主张 | 具体表现 |
|---:|---|---|
| 1 | **难度不是选项，是配置** | 游戏**没有难度菜单**（实测：选项菜单 62 条里没有任何难度项 [B]）。卡关的解法是"回去改装"，而不是"调低难度" |
| 2 | **技巧不在准度，在时机** | 加了一条会自我衰减的"第二血条"（ACS 姿态），让"什么时候打"和"打哪里"变得和"打不打得中"一样重要 [B] |
| 3 | **信息分级，而不是信息隐藏** | HUD 同时呈现 AP／姿态／四武器／锁定／雷达／EN，靠**状态驱动显隐**而不是删减来保持可读 [B] |
| 4 | **重不等于慢，重等于多花预算** | 重量曲线是"3 倍重量只掉 35% 速度"的**缓坡**，而不是等比惩罚 [B] |

**这四条合起来，就是 AC6 区别于一般动作游戏的地方**：它把玩家的成长路径从"手更熟"改成了"更懂配置 + 更懂时机"。

## §2 核心循环：四个时间尺度

一款游戏的"核心循环"不是一个环，是**嵌套的四个环**。AC6 的四个环咬得很紧：

```
┌─ 0.2 ~ 3 秒：交火环 ──────────────────────────────┐
│  读招 → 闪避(QB) → 反击 → 打姿态 → 硬直 → 爆发伤害  │
│  关键：这一环里玩家要做 3~4 个决策，不是"扣扳机"      │
└──────────────────┬───────────────────────────────┘
                   │ 累积成
┌─ 3 ~ 30 秒：遭遇环 ──────────────────────────────┐
│  资源管理（EN/弹药/AP）→ 判断该不该继续 → 打或撤     │
│  关键：EN 池同时供机动与能量武器，制造真实取舍        │
└──────────────────┬───────────────────────────────┘
                   │ 累积成
┌─ 5 ~ 20 分钟：任务环 ────────────────────────────┐
│  出击 → 清目标 → Boss → 结算（评价 + 报酬）→ 改装    │
│  关键：结算后回到装配界面，"改装"是下一环的起点       │
└──────────────────┬───────────────────────────────┘
                   │ 累积成
┌─ 20+ 小时：周目环 ───────────────────────────────┐
│  买装备 → 打竞技场拿 OS 点 → 解锁分支 → 新周目新视角  │
│  关键：经济缺口让你一周目买不满，重打是必然而非可选    │
└──────────────────────────────────────────────────┘
```

### 三条从这张图里读出来的设计规律

| # | 规律 | 证据 |
|---:|---|---|
| 1 | **上层环为下层环提供"理由"** | 任务环的报酬（`baseReward`）→ 周目环的购买力；竞技场首通 3,165,000 是 OS 点的**唯一来源** [B] |
| 2 | **每一环都必须有自己的"结算时刻"** | 交火环 = 破防的那一下；遭遇环 = 敌人倒下；任务环 = 评价页；周目环 = 新结局 [B] |
| 3 | **TTK 必须 ≥ 机制链长度 × 单环耗时** | AC6 机制链 3~4 环、单环 2~4 秒 → TTK 下限 8~15 秒。**如果 TTK 缩短 10 倍，姿态系统直接失效** [C] |

> **第 3 条是这一节最值钱的**：它给出了"用数学否决一个节奏方案"的样板。当有人提"我们把 TTK 做短一点更爽"，你可以回答："机制链需要 4 个环 × 2 秒 = 8 秒才能走完，TTK 低于这个数，我给玩家设计的第二个血条就永远打不满。"

## §3 系统总览：谁在给谁供数

AC6 的所有系统围绕一条主链：**装配 → 战斗数值 → 反馈 → 关卡**。

```
                  ┌──────────────────────────┐
                  │  数据层（257 张表 / 5.6 万行）│
                  └────────────┬─────────────┘
                               │ 读
      ┌────────────────────────┼────────────────────────┐
      ▼                        ▼                        ▼
┌───────────┐          ┌──────────────┐         ┌────────────┐
│ 装配系统   │──机体───▶│  战斗数值核心  │◀──意图──│  敌人 AI    │
│ 12 槽位    │  数值     │  · 伤害公式   │         │  · 行为状态机│
│ 重量/EN/热 │          │  · ACS 姿态   │         │  · 读招预警  │
└───────────┘          │  · 硬直/补正  │         └────────────┘
                       └───────┬──────┘
                               │ 事件
                               ▼
                  ┌──────────────────────────┐
                  │      反馈系统（多通道）     │
                  │ 顿帧 / 抖动 / VFX / 音效 / UI│
                  └────────────┬─────────────┘
                               │
      ┌────────────────────────┼────────────────────────┐
      ▼                        ▼                        ▼
┌───────────┐          ┌──────────────┐         ┌────────────┐
│  相机系统  │          │  动作/动画系统 │         │  关卡与任务 │
│ 锁定/跟随/QB│          │ 上下半身/IK/惯性│        │ 目标/结算/评价│
└───────────┘          └──────────────┘         └────────────┘
```

### 三条架构级洞见（都可迁移到任何项目）

| # | 洞见 | 证据 | 怎么用 |
|---:|---|---|---|
| 1 | **数据和逻辑彻底分离** | AC6 连"教学是否判定玩家做过某动作"（`TutorialActJudgeParam` 31 行）和"自动配装的评分"（`AutoAssembleEvaluate`）都是**表** [B] | 任何要长期平衡的项目：把手感、反馈、教学判定、解锁条件全部外置成数据 |
| 2 | **成组建模，不按字段堆** | 相机锁定表 `LockCamParam` 的列是 **(距离, 角度)** 严格成对交替（偶数列值域 −4~9999、奇数列 −360~1000）[B] | 你的表也应该按"档位"建模，而不是"一个字段一个用途" |
| 3 | **平台分档是数据** | 绘制距离按平台配置（`LoadBalancer*DrawDistScaleParam_ps5/_xsx/_win64`）[B] | 跨平台项目的性能预算应该做成数据，不是硬编码 |

### 4.1 战斗框架与数值底层（P2）

**① 解决的设计问题**

如果武器差异只体现在 **DPS 一个标量**上，装配空间就会退化成一维排序（谁 DPS 高用谁），技巧也只剩"准不准"。
**需要一个让「命中时机」也成为技巧的机制轴。**

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **加一条会自我衰减的"第二血条"（ACS 姿态）** | 积累 → 打满进易伤 → 窗口内用直击补正兑现。比"加血量"便宜，比"加无敌帧"更能制造技巧表达。**任何想给战斗加深度的游戏都可以照抄这条** |
| 2 | **阈值 / 衰减速度 / 窗口长度必须拆成三个量** | 只有拆开，重甲与轻甲才是**两条不同风险曲线**，而不是同一条曲线上的两个点 |
| 3 | **把老系列的"热"折叠进 EN** | 一个池两种消费（机动 / 能量火力）→ 少一条 UI 条、少一套教程，却制造了真实取舍 |
| 4 | **防御用"空间闪避 + 冷却"，不用"时间无敌"** | 代价是预警段必须够长够清晰——**预警时长与闪避容错是一对必须联调的参数** |
| 5 | **属性从二分升到三分** | 目的不是"相克乐趣"，而是给装配买**第三条正交取舍轴**。减伤用"以 1000 为中性点的线性系数乘法"，让"每 100 点防御 = 10% 减伤"可以心算 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 最终伤害 | `攻击力 × (2 − 防御/1000) × 属性耐性 × 补正` | B |
| 防御中性点 | 1000 = ×1.0；1227 = ×0.773；1500 = ×0.5 | B |
| 训练机三抗 | 1227 / 1105 / 1194 → 减伤 −22.7% / −10.5% / −19.4%（同机体跨属性承伤差约 12 个百分点） | A/B |
| 敌人三段式 | 预警 0.3~1.2 s / 出招 0.2~1.5 s / **收招 0.5~2.0 s（= 惩罚窗口）** | C |
| QB（快速推进） | **无无敌帧**（三处独立来源一致） | B |
| 姿态被动回复 | 体干 20 point/s、停手等待 5.0 s；阈值 10~4250 | B |
| 时间尺度 | 帧级 0.2~0.5 s / 决策级 1~3 s / 战斗级 5~20 s | C |

**④ 对策划的启示**

> 能用**「两条正交血条 + 一个爆发窗口」**讲清战斗节奏骨架，并给出**可计算的否决理由**（TTK 与机制链长度的数学约束）。
> 面试里能"用数字否决一个节奏方案"的人极少——大多数人只会说"我觉得这样更爽"。

### 4.2 装配与机体数值系统（P5）

**① 解决的设计问题**

玩家卡关时，不能只让他"回去练技术"。
**需要一把随时可用、零成本、连续可调的难度旋钮——而这把旋钮同时还要承担玩家的自我表达。**

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **用装配代替难度选项** | 卡关的解法从"操作"转向"伤害类型匹配 + 资源预算"；调节时机是每次死亡后的装配界面（随时、零成本、反馈快） |
| 2 | **三层约束分工** | 硬门（总重 vs 腿载重，超了**默认不能出击**）+ 软门（臂载重）+ 资源门（EN 负荷）。把"能/不能"的单点门槛单独抽出来 |
| 3 | **预算用线性求和，后果用折线曲线** | 线性好懂、好算、好做 UI；折线有手感、有断崖。**"惩罚曲线要缓、门槛要硬"是最值得抄的一条分工** |
| 4 | **让"重"有好处，而非单纯惩罚** | 踢击伤害 ×2、重量加成 ×1.25 → 重与轻是**两种正反馈**，不是"好"与"差" |
| 5 | **行为模板 + 参数包** | 25 条腿只需 8 个移动元型 + 6 个转向元型 → 部件数量远小于行为数量，维护便宜而体验差异大 |
| 6 | **核心不是防御件，是"总线倍率器"** | QB 传递 76~126%、发电机传递 83~126%、冷却 70~112%——**这才是组合爆炸的根源** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 槽位 | 12 个；头 24 / 核 19 / 臂 20 / 腿 58（玩家可用 25）/ 推进器 23 / FCS 19 / 发电机 24 | B |
| 总重曲线断点 | 40000 / 62500 / 75000 / 80000 / 120000 kg，倍率 1 → 0.65（**3 倍重量只掉 35% 速度**） | B |
| 超重曲线断点 | 100 / 105 / 110 / 130 / 150%；**150% 时 QB 时长倍率 = 0、上升推力只剩 0.25** | B |
| 臂载重曲线 | 0 / 5000 / 10000 / 30000 / 50000 kg，QB 恢复时长最高 ×3.5 | B |
| 硬门证据 | OS 强化 4010「Weight Control」仅 1 级 3 点，解锁"脚部积载重量过多出击限制解除" | B |
| OS 强化 | 20 项（5 攻 + 4 防 + 6 机动 + 5 系统）；**点数合计 197、全点满需 287 → 覆盖率 68.6%，设计上不可全解锁** | B |
| 腿决定运动学 | 坦克跳跃 2 m vs 逆関節 30~80 m；QB 追加初速 317~386 km/h；射击反動滑退倍率坦克 0.0~0.3 | B |

**④ 对策划的启示**

> 能讲清**"难度不一定要做成倍率表，也可以做成一个随时可调、带硬门槛与断崖后果的构建系统"**，
> 并给出**「预算线性、后果折线、门槛单点」**这条可复用的数值分工。

### 4.3 手感与反馈设计（P7）

**① 解决的设计问题**

机炮、导弹、多锁、推进**全在同一秒发生**——如何让玩家分得清"我打中了什么 / 我在被打 / 我快破防"，同时不糊屏、不掉帧？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **反馈是一条数据管线** | 事件 → 表行 → 通道集合；强度/时长/衰减全部表化。**任何要长期调手感的项目都该这么做** |
| 2 | **顿帧只给近战，枪械用"限流"代替** | 机炮 10 发/秒 × 0.05 s 顿帧 = 50% 时间冻结 → 直接变卡顿。**这是取舍，不是遗漏** |
| 3 | **混乱控制 = 限流四件套 + 优先级抢占** | 反馈的本质是**预算分配**，不是强度叠加（优先级 255、补正角 180° 都已顶格 → 设计空间被明确封顶） |
| 4 | **延迟是分层工具，不是缺陷** | **确认要即时、累积要聚合、危险要提前**（冲击值到 20% 就预警破防）。"0 延迟完美反馈"摧毁的是信息分层 |
| 5 | **瞄准辅助做成逐颗子弹的角度锥 + 粘滞** | 而不是一个全局磁吸强度 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 顿帧 | **45 / 712 行**（全是近战）、0.05 s 为主（41/45）、最大 0.12 s；全局动画速率 1%（近乎完全静止） | B |
| 抖动与震动同表 | `PadRumble` 174 行 × 84 B，内部类型名实测为 `CAMERA_RUMBLE_PARAM_ST`（**一行同时定义镜头抖动与手柄震动**） | B |
| 波形池化 | 约 98 个事件 → 约 20 个 `rumbleId` / 约 40 个 `hdPadRumbleId` | B |
| 输入层 | 缓冲 0.4 s、长按 0.4 s、多锁长按 0.5 s、冲刺松手宽限 1.2 s、走跑阈值 0.75 | B |
| 取消窗口 | **32 个触发类型 × 20 个状态位的矩阵**，不是时间轴上的帧区间 | B |
| 瞄准辅助 | 水平补正角众数 **15°**、垂直 **25°**；软锁 450 m、导弹锁 280 m；进瞄准模式 ×2；脱锁后粘滞 1.5 s | B |
| 限流 | 50 m 内命中 SFX 并发 **1**、多段命中间隔 **0.2 s**、伤害数字合并 **0.5 s**、冲击条 0.8 s 淡出 | B |
| 部位可读性 | `hitFEType`（−1/通常/弱点/装甲）110 行中 0×52、1×37、2×20；`addImpactRate` 有 35 行为 0 → **打某些部位不涨冲击值** | B |

**④ 对策划的启示**

> 能给出**「确认要即时、累积要聚合、危险要提前」**三条时间规则，并解释**为什么枪械不该加顿帧**。
> 面试里能把"更爽"拆成通道与预算的人极少。

### 4.4 动作动画与运动系统（P6）

**① 解决的设计问题**

几十种「重量 × 腿型」组合要共用一套动画，又要瞬间响应物理速度，同时看起来像几十吨的机械——**这三件事互相冲突**。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **位移与动画解耦** | 物理算速度、动画只管姿态；**动画位移量按机体总重量插值覆盖**（8650→27000）。一套动画服务大量可配置体型时，这是通用解法 |
| 2 | **重量感做成 8 条并行通道** | 加算动画 / 两段式加速度曲线 / 伺服延迟 / 零件二次运动 / 悬挂行程 / 落地刹车分档 / 音效 / 姿态倾斜。**要"变重"就加通道，别动动作时长**（放慢 50% 会让重量感上升、可玩性下降） |
| 3 | **用二次运动（Jiggler）做"机械 vs 人形"的差异化杠杆** | 必须有「硬限位 + 限位反弹 + 部分骨骼世界固定 + 求解顺序」四件套，**只做纯弹簧会变果冻** |
| 4 | **关键手感做成近似二元开关** | 落地刹车按 55/56 km/h 硬切两档、QB 零转向、角速度按腿型离散切换——**离散档位玩家才读得出来，连续曲线读不出** |
| 5 | **打击表现分级** | 受击 5 类 × 3 表面共 15 个具名事件；破防是"累积冲击值"而非单次伤害 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 位移反向注入动画 | 比例仅 **0.1（10%）**；动画位移按重量 8650→27000 插值 | B |
| 状态矩阵 | **227 行 × 20 个状态列**（事件名本身就是开发者的动作集清单） | B |
| 帧事件 | 开火/命中/无敌帧由 **TAE 帧事件**决定；动画事件时间基准 **1/30 s** | B |
| 数据表只管 | "允不允许、间隔多少"（`shootInterval` 0.01–10 s、QB 冷却 0.30–0.91 s） | B |
| Jiggler | **328 个受控骨骼**、旋转限位 ±45°/±22°、位移限位 ±2 m；平移力上限 580 ≈ 旋转力上限 115 的 5 倍 | B |
| 落地 | 55/56 km/h 硬切两档刹车 150 vs 125 m/s²；落差 ≤1 m 不产生硬直；硬直 0.05–0.5 s | B |
| 破防阈值阶梯 | **[150, 1600, 1600, 2000, 7500, 9000, 13000]**；残留冲击 1.5 s 挥发；抗性来自部件 stability 0–1500 | B |
| 转身速度 | 坦克 **230 deg/s** vs 其他腿型 360 deg/s → **"重装机转不过来"是腿型切换，不是重量连续函数** | B |

**④ 对策划的启示**

> 能说出**"重量感不是把动画调慢，而是 8 条通道的预算分配；要变重就加二次运动与两段加速度"**——
> 把一句体感形容词翻译成可执行、可验收的改动清单。

### 4.5 镜头与相机系统（P1）

**① 解决的设计问题**

三维高速机动中，**「看清自己机体的姿态」与「瞄准精度」互相拉扯**，且「重（惯性/滞后）」与「准」天然对立。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **把瞄准从相机上剥离，交给 FCS 与数据表仲裁** | 相机因此敢做得更慢、更沉、更有惯性。**凡「载具质量感 vs 射击精度」冲突的项目都可用** |
| 2 | **相机状态机按"参数集合差异"切分** | AB 要拉远+模糊、QB 要跟紧+抖动；实现成「基础态 × 叠加修饰的层+权重」，而不是「枚举 + switch」 |
| 3 | **强辅助必须带显式代价** | 硬锁用"信息成本 + 控制成本"约束，否则它会变成唯一解、技巧深度消失。**适用于自动瞄准 / 自动寻路 / 一键连招** |
| 4 | **抖动按"信息"设计而非按"效果"设计** | 先定它要告诉玩家什么，再定方向、频率、时长；位移/旋转/FOV **三条累加器分离**——开火后坐只走位移+FOV，避免污染弹道方向 |
| 5 | **速度感是多通道之和** | FOV、位置滞后、旋转滞后、粒子、后处理、抖动、音效、帧内位移——**单拉一条必露馅** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 锁定相机表 | `LockCamParam` 98 行 × 94 个 f32 槽；列 0（距离）值域 9~100、均值约 29 m；列 5（FOV 变化）25~60 度 | B |
| 可用区间 | 相机距离约 10~60 m、FOV 变化 10~80 度（放大/缩小 10 倍即失效） | C |
| 速度模糊 | `Zoomblur` 仅 7 行，强度 0.0025~0.02（跨 8 倍的"刚好可感知"区间） | B |
| 锁定哨兵值 | 大量字段填 `9999` = "无限"，**不是 9999 米** | B（数值）/ D（语义） |
| 三层速度环 | 相机环 / 机体环（PC 258 行 vs NPC 2124 行）/ 火控环。「**视线已到、机体还在转**」是质量感主来源 | B/C |

**④ 对策划的启示**

> 面试时能说**「相机不是瞄准工具，而是姿态可读性工具，精度应外包给可数值化的仲裁层」**，
> 并论证**「任何强辅助都必须带代价，否则它吃掉整个技巧空间」**。

### 4.6 敌人 AI 与 Boss 设计（P12）

**① 解决的设计问题**

高速机动的 AI 与人类约 **250 ms 的反应时间**天然不兼容——必须靠"可读的预警"来兼容；同时要用最便宜的手段做出敌人体感差异。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **读招优先做在机体动作上，UI 预警只给极少数招式** | 主通道是"动作预备 + 弹药可见飞行 + 音效"。代价：每种武器都要一套可读的预备姿态（成本落在动画与 TA 身上） |
| 2 | **双血条的价值不在"两条"，而在一条单调、一条可回复** | **只要有一个会回退的资源，战斗就会从消耗战变成窗口战** |
| 3 | **随机性放在表现层，不放在判定层** | 部位破坏只抽"掉几档零件"，**绝不抽难度** |
| 4 | **难度旋钮按"改动成本"排序，血量排最后** | 受击反应阶梯 → 转向速度 → 瞄准预测 → 感知 → 遗忘时间 → 开火节奏 → 距离带 → 招式组合 |
| 5 | **距离管理是"绕后"这套核心操作的存在前提** | 没有距离带，QB 就只剩躲伤害，"装配 = 战术选择"的链条会断裂 |
| 6 | **Boss 逐个分配"第一次"的教学职责** | 第一次高度 / 第一次护盾与装配墙 / 第一次部位破坏 / 第一次打你自己 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 受击反应阶梯（逐敌人不同） | 警備MT [10,40,121,221,∞]（**根本不会被吹飞**）vs 四脚MT [1800,2100,…] vs 自机 [150,1600,1600,2000,7500,9000,13000] | B |
| 姿态 | 本体体干 100 / 动作体干 20；停手 5 s 后每秒回 20；冲击值 1.5 s 不用即衰减；**冲击无敌 2.0 s** | B |
| 转向基准 | 玩家与 AC **360 deg/s** vs 量产 MT **90 deg/s**（约 4:1，就是这条旋钮的设计空间） | B |
| 感知 | 视距众数 450 m（264 行）；AI 听觉半径有 **1047/1178 行填 0.1 m ≈ 实际关闭** | B |
| UI 预警极稀缺 | 普通敌人射击预告字段 **1371 行全 0**、告警等级仅 47/1371 启用、另有 102 行明确设为"不显示" | B |
| 部位破坏 | 部位 HP 表 + 8 行加权抽选，**只抽 0 / 10 / 20 三档"表现档位"** | B |
| 受击盒不对称 | 敌 AC 15/3 与玩家 10/3.8 不一致（**肉眼绝对看不出**） | B |

**④ 对策划的启示**

> 能交出一份**「难度旋钮排序表」**，并说清**血量为什么必须排最后**——它同时牵动战斗时长、姿态节奏、弹药经济三条线。
> 这是面试中最能显功力的答法之一。

### 4.7 关卡与遭遇设计（P8）

**① 解决的设计问题**

当玩家同时拥有**高速三维机动**与**自由装配**时，如何用极简数据字段（而不是几何堆料）把路线选择与节奏收回来？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **用时间而不是墙来限制探索** | "限时"在数据上只是一个 f32 + 一个评分权重，却能删掉绕路最优解——**性价比最高的约束手段** |
| 2 | **关卡尺度以"移动时间"计量，而不是米** | 按冲刺速度反推掩体间距、交战距离带与爬升成本。**凡"这个场景好大"的判断都必须换算成秒才有意义** |
| 3 | **把飞行视为"忽略关卡设计的权力"，再用边界收回** | 限高、深渊、峡谷、坑道、最小激活半径——**任何给玩家高机动的游戏都要配套设计"收回权力的容器"** |
| 4 | **检查点把失败成本从"资源"改成"时间"** | 同时是"时间权重 25"这条评分规则能成立的前提——**两条设计必须成对存在**，否则时间压力会被重打成本吃掉 |
| 5 | **引导做多通道冗余，并承认失效场景** | 地标剪影是唯一能在 600 m/s 下可读的信息，而沙尘任务会故意抹掉它——**"这不是 bug，是被设计的紧张感来源"** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 速度尺度 | 冲刺终速 430 km/h（119 m/s）、飞行 408、滑行 600、重力 120 m/s²：**横穿 1500 m 仅 12.6 s，落 1000 m 仅 4.08 s** | B |
| 激活半径 | `activateDistXZ` 中位 **1500 m**（800–8000 m）；垂直生死边界 +250~+5600 m / −250~−7760 m | B |
| 评分系数 | damage **0.167** / bulletCost **0.055** / enemyBonus **1** / **clearTime 25**；49 个任务中 48 个完全一致 | B |
| S 阈值 | **10/49 剧情任务的 RankS 阈值为负**（数据上"怎么打都是 S"）；49/49 都有 `maxClearTime`，中位 **1220 s**（370–1876 s） | B |
| 地图复用 | **21 个真实区域支撑 49 个任务**（约 2.3 任务/图） | B |
| 掩体是资产属性 | `isDamageCover` **5109/5116** 置位，但 `isCoverAutoGenerate` 只 **9/5116** → **掩体是美术摆放的自然产物，近乎零额外工作量** | B |
| 可读性设计 | 攻击会被弹开 `isAttackBacklash` **4609/5116（90%）** → 玩家能"读"出哪里是硬掩体 | B |
| 检查点 | **488/5116 个资产被排除在存档之外**；弹药/修理费按任务配"系数 + 上限" | B |

**④ 对策划的启示**

> 能说出**「限时只是一个 f32 加一个权重，却比加墙更有效」**，以及**「高机动关卡必须配检查点与收权容器」**——
> 这是把**机制、关卡、评分三者连起来讲**的策划语言。

### 4.8 难度曲线与教学（P14）

**① 解决的设计问题**

操作集是组合式的（6 自由度 + 3 射击模式 + 2 近战），却**坚持不给难度选项**——如何不靠说明书教会玩家，并让"打不过"永远有解？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **教学写成"声明式动作谓词"** | 最多 2 个「槽位+动作」AND 1 个扩展判定；玩家**真做出该组合**提示才消失。教学从"点确定跳过"变成"行为验证"。**适用任何有动作状态机的游戏**（连招、载具、建造、RTS 编队） |
| 2 | **同一知识点三种投递形态共享 ID 前缀** | 时停弹窗 / 不打断的 HUD 轻提示 / 事后可查档案——**按场合换形式，而不重写内容** |
| 3 | **"打断预算"独立于内容重要度** | 只有少数条目允许"全周目一次"这种最高打断级别，多数是"每任务一次"（失败重打会再弹 = 救急） |
| 4 | **节奏模板** | 前 20 分钟密集判定提示 → **主动静默 5 分钟** → 失败点补一发针对性弹窗。比全程弹窗或全程不管都省认知预算 |
| 5 | **低失败成本 + 高惩罚强度** | **惩罚注意力，不惩罚钱包**——高失败成本会让玩家为省钱不敢试新装配，直接摧毁"换装解法"这条路 |
| 6 | **官方解法顺序写进数据** | 换装 → 换武器 → 换策略 → 提高操作。把失败归因从"我手笨"改写成"**我配置错了**" |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 教学总量 | 201 行分三条管道：KeyGuide 51 / 时停弹窗 91 / 菜单+档案 72 | B |
| 动作谓词 | 31 行 × 9 字节；54 行教程引用 128 次、覆盖 **25/31** 个谓词 | B |
| 序章节奏 | 0–19 分钟：1401 段 30 行中 **19 行挂 KeyGuide（63%）**；19–27 分钟**刻意撤掉教学** | B |
| 教学预算 | 操作向 122 行（60.7%）/ 装配系统 72 行（35.8%）/ 考试败北 6 行（3.0%） | B |
| 三处教学墙 | 序章 AH12 → 2030 Juggernaut → **2050 Balteus**；三条败北教学全部 `RepeatType=0` | B |
| 打断预算 | `RepeatType` 分布 =（全局一次 36 / 每任务一次 119 / 不限 46） | B |
| 失败成本 | `bulletCost_rate=1.0`、`repairCost_coefficient=2.0`、上限均 200000，**只在任务完成时结算** | B |
| 难度四因子 | 装配 40%→25%，操作 20%→35%，认知 30% 恒定，资源 10% | C |

**④ 对策划的启示**

> 能说出**「教学是一套可判定的动作谓词 + 一份打断预算」**，而不是"教程要做得友好"——
> 面试里这一句立刻区分"读过设计书"和"拆过产品"。

### 4.9 元循环经济与进度系统（P13）

**① 解决的设计问题**

装备驱动的游戏如何在 **20+ 小时**里持续给出目标感，同时**不让"打得差"变成不可逆的亏损**？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **三条互不重叠的解锁管道并行** | 钱（商店，主干 248 件）、条件解锁（21 个非卖品）、令牌→佣兵等级（95 个令牌）。**规模比 24 : 248 : 95 就是设计意图的自白——商店为主、令牌控节奏、条件解锁当彩蛋** |
| 2 | **用"性能税"而不是"失败惩罚"接入成本维度** | `成本 = 原始消耗 × 系数`，再取上限。**系数决定惩罚哪类行为**（修理 2.0 = 惩罚挨打），**上限决定最坏情况有多坏** |
| 3 | **零风险试炼场，且只产出主线买不到的资源** | 竞技场给 OS 点 → 玩家因此**不会跳过练习** |
| 4 | **多周目加视角不加难度** | 把分支选择做成周目内容，一份关卡资产产出三周目的新鲜感，**用"不满足"换留存** |
| 5 | **评价权重就是设计者的价值取向** | 时间压倒一切，"跑得快"是唯一的 S |
| 6 | **PvP 奖励只给身份展示（名牒），不给战力** | 避免平衡外溢破坏 PvE |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 性能税 | 弹药费 **58/59** 剧情行统一 rate 1.0 / 上限 200,000；修理费系数 2.0 / 上限 200,000；**双上限合计 400,000，而 59 行里有 46 行基础报酬低于 400,000** | B |
| 官方对照实验 | **唯一全 0 的例外是脱狱关**（那一关你没用自己的机体）→ 等于一次"取消弹药费"的自然实验 | B |
| 评价权重 | **时间 25 : 击破 1 : 受伤 0.167 : 弹药 0.055**（时间是受伤的 **150 倍**） | B |
| S 阈值 | 13/111 行 S 阈值 < 0 → **必然 S**（其中 12 行在剧情区），用于给演出/教学关免除评价压力 | B |
| 竞技场 | 41 场首通合计 **3,165,000**，重赛恰为首通的 **50%**；**OS 点 41 行全部绑定"竞技场击破"** | B |
| OS 点缺口 | 合计可得 **197** 点，全点满需 **287** → 覆盖率 **68.6%，设计上不可全解锁** | B |
| 令牌兜底 | 95 个合计 208 点，满级需 175 点 → **33 点冗余，漏拿几个也能满级**（防卡死） | B |
| 商店缺口 | 全目录 **62,052,000**，单周目可得约 **18,213,000** → **只能买约 29%**，"全收集"被刻意设计成跨周目目标 | B |
| 互斥分支 | 8 个互斥任务组（其中一组 3 选 1）+ 6 个 ALT 任务 → **第 1 周目必错过 1,516,000~3,160,000** | B |

**④ 对策划的启示**

> 能说出**"经济系统的每个系数都在表达态度"**——修理系数 2.0 是"**惩罚挨打而不惩罚开枪**"；
> "负阈值 = 必然 S"是**用数值给关卡免除压力**。这类细节极少有人能从数据里读出来。

### 4.10 UI / UX 与信息设计（P10）

**① 解决的设计问题**

**信息完整性与视觉清晰度不可兼得**——既要暴露几十个数字，又不让屏幕中心被噪声淹没。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **不靠"隐藏"，靠"分级"** | 中心只留"我现在能不能打"（准星/锁定框/伤害数字），机体状态与弹药推到边缘，脱战后按写死的秒数淡出。**任何高频动作游戏的 HUD 都适用** |
| 2 | **显示"判定所依据的量"，而不是判定结果** | 锁定框大小写实地反映"离锁上还差多远"，玩家不用教程就学会 280 m 是导弹锁分界线。**可迁移到潜行视野、仇恨范围等一切数值判定** |
| 3 | **信息层级做在数据层，而非代码分支** | 同一属性有精简版与全量版并存，列表页 3~4 个数、详情页十来个——**这是"更多信息 ≠ 更好"的自我承认** |
| 4 | **用难度旋钮代替难度菜单** | 把难度交给可配置的操作项（自动锁定切换、推进长按/切换、自动装配），而不是三档台阶 |
| 5 | **组件复用** | 一个警告组件以三个槽位挂到 4 个界面；同一属性定义在 95 个槽位复用 → **UI 从"画页面"变成"搭积木"** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 锁定候选区 | 画面水平 **45% × 垂直 55%**；通常锁 450 m、导弹锁 280 m；多锁需长按 0.5 s，单次 4 个、总数上限 10 个 | B |
| 时间预算 | 伤害数字累积窗口 0.5 s；血条淡出 1.5 s（归零 0.3 s）；脱锁后保留 1.5 s | B |
| 反馈时长 | 战斗内瞬时反馈集中在 **0.3~2.0 s（中位 ≈1.0 s）**；菜单转场全部 ≤0.5 s；**淡出普遍短于淡入**（作战线 2.0 s 进 / 0.5 s 出） | B |
| 选项菜单 | 总量仅 **62 条**；**无字号设置、无色盲模式**；字幕只有 ON/OFF | B |
| HUD 可调 | 位置 / 缩放 / 不透明度，共 4 个槽位（默认 + 自定义 1/2/3） | B |
| 配装界面 | **248/508 行属性带"大者优/小者优"判定**、30+ 种数值格式 → 系统就是为"精确数字 + 优劣方向"而建 | B |

**④ 对策划的启示**

> 能把"信息取舍"讲成**"分级 + 定时 + 把判定量可视化"**，而不是笼统夸 HUD 干净——
> 这套语言可直接用于任何**界面评审**。

### 4.11 音频设计（P11）

**① 解决的设计问题**

30 Hz 战斗里每帧可能产生 **5~10 个音效事件**，必须在有限并发预算内既不糊成一坨、又不埋掉关键信息。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **先设计调度器类别，再设计音效资产** | "一直响"的循环层与"点一下"的一次性层分成两套调度器；前者用连续参数控，后者靠并发槽位 + 重播冷却硬控。**独立游戏最常犯的错是先做 200 个 wav** |
| 2 | **音频参数维度要正交，不要做成 10 层 if 树** | 武器音色拆成 4 个独立维度同时生效（武器类型 14 × 射击分类 38 × 材质 17 × 攻击力档 3） |
| 3 | **把"体量"写成参数，而不是靠听感调** | 低频 + 震动双通道、距离不衰减、同一事件三层距离变体 |
| 4 | **动态音乐先定义"状态枚举"，再定义"谁负责把状态推回去"** | 105 行的过场表就是一张**状态回推表**——这是独立游戏最容易漏的一环 |
| 5 | **高速场景用"距离分档 + 碰撞点统计"代替手摆混响触发器** | 避免机甲一帧飞 100 m 时穿过 5 个触发器 |
| 6 | **语音按独立资源池 + 独立空间处理 + 独立混音目标对待** | 而不是"加了个人声" |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| BGM 状态 | **8 个**：normal / in_combat / heat_up_1~5 / death → **战斗强度是一把 6 档连续量** | B |
| 重播冷却 | 弹着音最短间隔 **0.56 s**；反制推进音 0.4 s；"致命一击音"专门留了 **0.6 s** 延迟预算 | B |
| 单条攻击限流 | 挂 4 个限流秒数；弹药 / 落地 / 飞行上限分别为 0.45 / 1.0 / 1.0 s | B |
| 带宽取舍 | 联机对战中**超过 600 m 的地图着弹音直接省略**——用音频预算换 CPU 与带宽 | B |
| 动态混响 | 按距离分档：50–290 / 290–620 / 620–900 / 900–1024 m，室外默认干声 | B |
| 平滑时间 | 连续参数变化统一 **100 ms** | B |
| AI 听觉参数 | 半径 30 / 100 / 150 m，优先级 300，声事件存活 1 s（**但见 §6 的冲突说明**） | B |

**④ 对策划的启示**

> 能把"哪些信息该走耳朵"讲成**一套带宽论证**——全向、毫秒级、多信道并行，
> 而视觉只有约 100° FOV 且一次只能突出一个焦点。**这个角度在面试里几乎没人讲。**

### 4.12 美术方向与渲染表现（P9）

**① 解决的设计问题**

面对「可换装 + 玩家自定义涂装」带来的**资产组合爆炸**与**跨平台 60 fps** 的双重约束，如何既保证画面统一可读、又能被运行时降级？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **风格首帧定死，性能运行时谈** | 19 个画质项做成可按 FPS 自动升降的阶梯 + **不对称迟滞**。跨平台游戏的"降级"应做进设计，而不是留到优化阶段 |
| 2 | **可读性优先级：亮度分层 → 轮廓 → 时间闸门 → 屏幕中心留白** | **颜色编码是最后一道防线，不是第一道** |
| 3 | **玩家自定义外观靠「5 层材质栈 + 参数覆写 + 5 通道分区配色」** | 美术只画一张部位遮罩，其余全是数据——**把 UGC 当数据问题而非资产问题** |
| 4 | **打击反馈先做频率闸门，再做美术** | 否则优化阶段会被迫砍掉一半美术量 |
| 5 | **发光与反光分工** | 自发光是**信息通道**（状态/功率感），反光是**材质通道**（真实感），二者不可互替 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 动态画质 | `LoadBalancerParam` 33 行：30 fps 档阈值 30.60/31.60，60 fps 档 60.60/61.60；**降 5 帧 / 升 20 帧**；降后冷却 30、升后冷却 10 | B |
| 可降项 | **19 个可独立升降画质项**，其中 ParticleHalf 实测 5↔13（约 2.6 倍跨度） | B |
| 玩家涂装 | 46 行材质预设 + 24 行旧化预设，5 通道配色（Base/Sub/Support/Optional/Device） | B |
| 命中矩阵 | `HitEffectSfxParam` **71 行 × 240 B = 25 槽**；金属命中用满 10 个不同 ID，**能量盾命中只复用 2 个 ID**（预算投在可视度最高的通道） | B |
| 频率闸门 | 50 m 内近失 SFX 最多 **1** 个、多段命中间隔 **200 ms**、贴花寿命 10 s | B |
| 阴影 | 阴影相机固定 FOV **45°**；AC 阴影绘制距离 350 m；光追只用于平行光阴影 + AO，**没有光追反射** | B |
| LOD | 两段式：尺寸分桶（100/200/350/∞ m）+ 平台缩放曲线（PS5/XSX 全 1.0；PS4 最狠曲线 0.962→0.475） | B |

**④ 对策划的启示**

> 能讲清**「可读性不靠色相靠亮度差」**，并给出**「先频率闸门、后美术量」**的预算顺序——
> 让策划讨论视觉时不停留在"更酷/更炫"。

### 4.13 剧情与叙事结构（P3）

**① 解决的设计问题**

叙事推进**不能打断**「接单 → 出击 → 交战 → 结算 → 改装」的核心循环，但玩家又必须始终知道"我在为谁打、为什么"。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **把最大的叙事池放在"玩家本来就在做别的事"的时间轴上** | 战斗中通讯 → 注意力免费。代价：吸收率不可控，**因此必须配一条可选长文通道做冗余** |
| 2 | **按"玩家此刻的消化能力"排信息顺序** | 下一步打哪（100% 送达）→ 正在打谁（短、情绪化）→ 为什么会这样（可读长文）→ 谁在操纵一切（跨周目） |
| 3 | **沉默无脸主角 + 三角色代词化** | 雇主 / 异质他者 / 镜像对手；人格表达**外移到外观系统**（涂装、徽章、贴花） |
| 4 | **分支实现成"数据可用性"，而不是"演出分支"** | 完成一个 → 另一个从菜单消失；存档只存"已完成任务集合"→ **天然可存档、可回放、零演出成本** |
| 5 | **把"选边"接到核心循环上** | 每条分支给专属机体部件，**让叙事决定变成构筑决定** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 通讯通道 | 战斗中通讯 **5965 条 / 248,181 UTF-16 码元**、单条均长 41.6，**占全部菜单文本池 58.3%**，是第二大通道的 6.6 倍 | B |
| 长文通道 | 档案 51 条、均长 371.9（comm 的 8.9 倍）；邮件 46 行 | B |
| 唯一 100% 送达的通道 | 任务简报表约 260 条串 ≈12,800 码元（**只占台词池 5.2%**） | B |
| 本地化切分 | `TalkParam` 6013 行 × 64 字节；**按"文件 = 通道"切分**（会話 5965 vs 5964） | B |
| 分支在数据层的形态 | `MissionSystemMsgAnswerParam` 40 条实体记录、**行宽仅 16 字节** → "选择"是指针跳转，不是文本 | B |
| 结构 | 主线 5 章、已核实决策组至少 5 处；`MissionParam` 111 行 vs 三张任务文本表各 67 条 | B |
| 三结局 | Ch5 同一分歧点二选一；**第三结局独占 NG++** 且需指定路径 + 竞技场；分支各给专属部件（HAL 826 / ALBA / Coral 武器） | B |

**④ 对策划的启示**

> 能提出**「把分支做成资源可用性、把最贵的信息放在玩家已经在操作的时刻」**，
> 并像算预算一样给出每条叙事通道的**边际成本与送达率**——这套"叙事投放预算表"的说法在面试里几乎没人讲。

### 4.14 世界观与设定体系（P4）

**① 解决的设计问题**

设定既要撑起玩法（装备、任务、结局），又**不能要求玩家先读百科才理解**；预算有限时，**设定必须"被手碰到"**。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **核心设定优先选"能被多系统各引用一次"的实体** | Coral 同时是：能源资源 / 政治争夺对象 / 准生命体 / 结局标的 / 主题载体（**五重功能**）→ 用索引效率摊薄跨管线成本。<br>**自检法**：把它分别写进道具描述、任务目标、结局条件，看三句话是否都成立 |
| 2 | **势力不是被介绍的，是被遭遇的** | 靠"关卡里出现什么敌人 + 通讯里谁在说话 + 委托是谁下的"三条通道；**唯一走 UI 的是企业**（装配界面厂商栏） |
| 3 | **给玩法发"叙事许可证"** | 可替换的主角需要一套**可折旧的身份**（强化世代、编号呼号、雇主合同），使玩法上的任何"重来"都不产生叙事矛盾 |
| 4 | **环境叙事做"规模证明"，而不是"信息传递"** | 尺度只能靠**可行走面积**传达，文字做不到 |
| 5 | **主题靠"不可兼得的任务分岔"让玩家付代价**，而不是靠台词说教 | 核心设定**永不给出本体论结论**，把张力交给玩家的选择成本承担 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 台词 : 词典 | **6013 : 2**——`TalkParam` 6013 行 vs `UnlockParam_Archive_Terms` 仅 2 行（4 列全为 0） | B |
| 解释系统总量 | `ArchiveParam` 57 行（Logs 50 / Terms 2）；`MailParam` 46 行 | B |
| 表达系统远大于解释系统 | `EmblemPieceSpec` **997 行**、`DecalParam` 248 行 vs Archive 57 行 | B |
| 两套命名法 | 企业名取历史兵器/地名/量词/人名；机体代号用"字母段 + 数字段"（AH12 / HA-T-102 / AAP07 / IB-01）→ 传达"**被登记的量产资产**" | B |
| 扩展开口是制度级 | PCA 上级政府未出场、研究院实验记录仅部分回收、Coral 跨星际扩散；**`UnlockParam_DLC` 仅 1 行（ID=0）** → 挂点在解锁表而非文本表 | B / D |

**④ 对策划的启示**

> 能说出**「如果一个设定无法被玩家的手碰到，就不该把它写出来」**，
> 并用**「同一实体能否被装备、关卡、结局各引用一次」**作为可执行的设定评审标准——
> 比"世界观要自洽"这类空话有说服力得多。

### 4.15 技术实现与数据管线（P15）

**① 解决的设计问题**

内容量巨大（284 武器 / 712 条攻击 / 4120 个特效）时，如何把**"设计意图 → 玩家体验"的改动成本压到分钟级**，同时保证五平台体验等值？

> 这一节只取**设计层**，略去实现细节。

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **把可调的"机制"全部外置** | 手感、反馈、教学判定、解锁条件、菜单布局都是数据 → **平衡改动可按周发、不重发资产**。适用于任何要做长期平衡的长尾产品 |
| 2 | **基准 + 少量覆写做分档，按"硬件族"而非机型切** | 弱机是"**增加中间档**"而不是一刀切降质——目标是每台机器都跑在"刚好不卡"的画质 |
| 3 | **用"命名参数槽位注册表"把美术意图翻译成数据契约** | 美术暴露命名参数，特效/涂装按 ID 驱动它——**"设计意图可被程序消费"的接口设计** |
| 4 | **差异报告必须做到行级/字段级**，不能是文件级 | 否则你永远不知道"这次改动到底动了什么" |
| 5 | **版本纪律：行 ID 一经发布不可复用**（存档引用它） | 废弃表与字段要显式标记，否则数据只增不减 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 数据规模 | **257 张表 / 55,911 行 / 20.11 MB** 承载了全部表现层与规则 | B |
| 外键可被实证 | 判别式外键按同一行的 `refType` 分流后命中率 **85% / 96% / 100%**——"一把武器开火链路"完全可追踪 | B |
| 单列多态 | 318 个值按类型分流后每类命中率 100% → **"一个字段一个含义"的直觉是错的** | B |
| 分档量级 | 弱机 Lv00 缩放 0.6、Lv20 低至 0.25；**强机与基准逐字段零差异**；高端变体与基准仅 **12/152 行**不同（90 字节），弱机 94/152 行 | B |
| 动态降级三件套 | 阈值 + 持续帧数 + 冷却（防档位抖动） | B |
| 数据驱动的代价 | 文件级"58 张表变了" vs 行级"**真正数值改动 28 行**" | B |
| 结构吻合度 | 197 张可比对表 **183 张精确吻合（93%）**；14 张不一致中 8 张是单行表（行宽不可信） | B |

**④ 对策划的启示**

> 能讲**"数据驱动不是技术选型，而是产品决策"**——它同时决定**补丁节奏、Mod 生态、存档兼容性**，
> 而这三件事都是策划的 KPI。

### 4.16 系列演化与商业定位（P16）

**① 解决的设计问题**

**小品类、无竞品、停摆十年的老 IP**，如何用有限产能买到最长生命周期？

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **用"经济缺口"代替"难度墙"驱动重复消费** | 一周目买不满目录 → 重打是**必然**而非可选，且**不加内容成本** |
| 2 | **多周目加视角不加难度** | 靠分支与钱而非血压逼你重打，比"二周目敌人 +100% 血量"优雅 |
| 3 | **把深度藏进参数、把门槛外置到训练与档案** | 老玩家与新玩家的冲突**不在难度，而在信息密度** |
| 4 | **长尾建在"零边际成本表达层"** | 徽章/涂装/铭牌/排行——对服务器、平衡、存档几乎零负担，是**真正免费的 DLC** |
| 5 | **制度化平衡** | 把数值做成可独立热更的快照，让"不重发版本改平衡"成为制度而非临时救火。**小品类对抗大厂内容量的杠杆** |
| 6 | **PvP 只当配菜**（不维护独立 PvP 数值层） | 把产能留给单人内容 |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 销量 | 全球 **2.8M+**（Kadokawa FY2023Q2 财报口径），超系列任一作 | A/B |
| 经济缺口 | 单周目可支配 **15,048,000 ÷ 全目录 62,052,000 = 24.25%**；计入竞技场首通 **29.35%**（口径区间 22.8%–29.4%） | A |
| 竞技场 | 41 场首通现金 3,165,000、重赛 1,582,500；**OS 点由独立的解锁表发放** | A |
| OS 缺口 | **287 点需求 vs 197 点可得 = 68.6%**，是精心设计的"永远差一点" | A |

### 4.17 深挖追问：把口号变成数字（P17）

**① 解决的设计问题**

团队文档里最像常识的口号（"机甲不是放大的人""装配即难度""把钱花在高频反馈上"）**既不可验证也不可执行**——
**如何把口号换算成可测、可填、可调的量？**

**② 核心设计决策**

| # | 决策 | 为什么 / 能迁移到哪 |
|---:|---|---|
| 1 | **口号 → 可测量** | 任何"难度/手感/频率"的形容词，先换成一个**能读出来的量**（破防所需命中数、机动预算、频率占比），否则结论不可反驳、等于没说 |
| 2 | **故意违反物理律来造重量感** | 机甲感不由动力学产生，而由"**角速度上限压低 + 加速度驱动的二次运动**"产生。<br>**任何大型单位（怪兽、载具、巨型 Boss）都可照抄：放大后不要等比调参，要挑几处刻意违反** |
| 3 | **用不对称制造取舍轴** | 手臂不提供姿态稳定（20/20 行全 0）→ **"我要稳"与"我要火力"互斥**。<br>任何一种两难，都要在数据里留一处**硬 0** |
| 4 | **预算按频率分配** | 低频组合不是"少做几档"，而是**整行指向同一批资源**；未使用的维度**显式留空**，让"没做"和"做错"一眼可分辨 |
| 5 | **先声明口径** | 同一个结论在不同口径下可以差 **58%**——**口径不写清，下钻就是自欺** |

**③ 关键数字**

| 项 | 值 | 等级 |
|---|---|---|
| 落地时间对照 | 10 m 落地：机甲 **0.408 s** vs 放大的人 **1.429 s（差 3.50 倍）**；重力 **120 m/s²** = 动态相似律预测 54.4 的 **2.20 倍** | B |
| 放弃转动惯量 | 258 行转向数据中 **159 行把角加速度设为"无限"**；**坦克腿是唯一例外**（230/350/450） | B |
| 二次运动 | 死区 50 / 饱和 300 m/s²；351 行绑定 **327 个唯一骨骼名** | B |
| 弹性区间 | 姿态稳定四槽求和 **1097~2677（2.44 倍）**；手臂 20/20 行全 0；AP **5700~17780（3.12 倍）** | B |
| 敌我差距 | 敌人阈值表 57 行 / 11 档 / **48 种唯一阶梯**；敌我差距 4250 ÷ 10 = **425 倍** | B |
| 机动预算 | 满 EN 连 QB **2.0~9.2 次**；QB 占空比 **22.7%~64.7%** | B |
| 预算按频率 | 命中特效矩阵 71 行 → 26 个唯一向量 / 15 组复用（最大 9 行共享）；**最高频组合占 29.6%，拿到的 ID 数是低频组合的 3.7 倍（11 vs 3）** | B |
| 显式留空 | 受击材质 **99.59% 是同一材质**（1227/1232）；**刺突类型 0 行、爆风 5 列全表零值** | B |

**④ 对策划的启示**

> 能讲**"我怎么把一个 slogan 变成表里读得出来的数字"**，并说清**口径如何让同一结论偏移 58%**——
> 这是**数值/系统岗最硬的表达力**。

## §5 可迁移的设计模式（28 条）

> 这些模式**跨维度通用**，是这份拆解最值钱的部分。
> 每条都写成「**做法 → 适用场景**」，可以拿去评审任何游戏。

### A. 冲突解决类（怎么处理"两个目标打架"）

| # | 模式 | 来源 |
|---:|---|---|
| 1 | **当一个系统同时被两个目标拉扯时，砍掉不属于它的那个职责**（相机不做瞄准，瞄准外包给可数值化的仲裁层） | P1 |
| 2 | **强辅助必须带显式代价**，否则它会变成唯一解、吃掉整个技巧空间（硬锁的信息成本 + 控制成本） | P1 |
| 3 | **"难"和"准"天然对立时，把"难"转移到不需要精度的维度**（姿态系统让时机比准度重要） | P2 |
| 4 | **两个目标都要，就让它们共享同一个预算池**（EN 同时供机动与能量火力 → 真实取舍） | P2 |

### B. 数值设计类（怎么把感觉变成数）

| # | 模式 | 来源 |
|---:|---|---|
| 5 | **预算用线性求和（好懂好算好做 UI），后果用折线曲线（有手感有断崖）** | P5 |
| 6 | **惩罚曲线要缓，门槛要硬**（3 倍重量只掉 35% 速度；但超重直接禁止出击） | P5 |
| 7 | **让"重"有好处而不只是惩罚**——两端都要有正反馈，玩家才会真的做选择 | P5 |
| 8 | **关键手感做成近似二元开关，而不是连续曲线**（落地刹车 55/56 km/h 硬切）——**离散档位玩家才读得出来** | P6 |
| 9 | **线性系数乘法 + 中性点**（防御 1000 = ×1.0）→ 让玩家能心算 | P2 |
| 10 | **在数据里留一处"硬 0"来制造两难**（手臂不提供姿态稳定） | P17 |
| 11 | **用不对称制造取舍轴**，比用"数值高低"更有效 | P17 |

### C. 信息设计类（怎么让玩家读懂）

| # | 模式 | 来源 |
|---:|---|---|
| 12 | **三级信息规则：确认要即时、累积要聚合、危险要提前** | P7 |
| 13 | **显示"判定所依据的量"，而不是判定结果**（锁定框大小 = 离锁上还差多远） | P10 |
| 14 | **信息分级，而不是信息隐藏**（中心留决策、边缘留状态、脱战淡出） | P10 |
| 15 | **可读性优先级：亮度分层 → 轮廓 → 时间闸门 → 中心留白**；**颜色是最后一道防线** | P9 |
| 16 | **教学写成可判定的动作谓词**（玩家真做出该动作，提示才消失） | P14 |
| 17 | **同一个知识点准备多种投递形态，共享 ID**；按场合换形式而不是重写内容 | P14 |
| 18 | **"打断预算"独立于内容重要度**——内容再重要，也不能都做成时停弹窗 | P14 |

### D. 预算与砍量类（内容太多怎么办）

| # | 模式 | 来源 |
|---:|---|---|
| 19 | **先做频率闸门，再做美术量**——否则优化阶段被迫砍掉一半工作 | P9 / P7 |
| 20 | **预算按频率分配**：高频组合拿多份资源，低频组合整行复用同一批 | P17 |
| 21 | **未使用的维度显式留空**，让"没做"和"做错"一眼可分辨 | P17 |
| 22 | **"行为模板 + 参数包"**：25 个对象只需 8 个模板 → 数量远小于行为数，维护便宜而体验差异大 | P5 |

### E. 结构与数据类（怎么让项目能长期维护）

| # | 模式 | 来源 |
|---:|---|---|
| 23 | **把可调的机制全部外置成数据**：手感、反馈、教学判定、解锁条件都要能改而不重发版本 | P15 |
| 24 | **数据按"档位"建模，不按"字段"堆** | P3（主文档架构） |
| 25 | **分支做成"数据可用性"，而不是"演出分支"**——天然可存档、可回放、零演出成本 | P3 |
| 26 | **行 ID 一经发布不可复用**（存档引用它）；废弃表与字段要显式标记 | P15 |

### F. 元循环与长尾类

| # | 模式 | 来源 |
|---:|---|---|
| 27 | **用"经济缺口"代替"难度墙"驱动重复消费**——不加内容成本就能让重打成为必然 | P16 |
| 28 | **长尾建在零边际成本表达层**（徽章/涂装/铭牌），而不是靠不停加内容 | P16 |

## §6 口径与冲突：同一份数据为什么会有四个答案

> ⚠️ **这一章是整份文件里"最不像拆解、但最该学"的一章。**
> 拆解 17 份报告的过程中，汇总者一共发现了 **12 处口径冲突**。它们**大部分不是错误，而是口径不同**——
> 这恰恰是策划工作里最容易被忽略、也最容易翻车的地方。

### 6.1 四个真实案例（都经我本机复核）

#### 案例 ① 「剧情任务有多少个？」——四个答案，四个都对

| 口径 | 结果 | 说明 |
|---|---:|---|
| `missionType == 0` | **62** | 剧情任务的表行数 |
| `baseReward > 0` | **58** | 有报酬的任务 |
| `chater >= 1` | **60** | 归属于章节的任务 |
| P16 交接单口径 | 59 | 金额能精确对上、行数差 1–2 |

**本机实测 `missionType` 分布**：`0 × 62`（剧情）/ `2 × 42`（竞技场）/ `3 × 7`（训练）= **111 行** [B]

> **教训**：引用"AC6 有多少个任务"时，**必须说清是哪一种任务**。
> 62 + 42 + 7 = 111 才是全表；单说"62 个任务"是把竞技场和训练关排除掉了。

#### 案例 ② 「冲击免疫时长是多久？」——两个值都对，因为对象不同

| 表 | 值 | 说明 |
|---|---|---|
| `EnemyCommonParam.addImpactDisableTimeSec` | **2.0**（1 行） | 敌人侧 |
| `TentativePlayerParam.addImpactDisableTimeSec` | **[1.5, 2.5]**（2 行，rid 0 和 1） | 玩家侧，两个 rider 各一个值 |

**P6 报告写 1.5 s（玩家侧），P7 报告写 2.0 s（敌人侧）——两份都没错，是取的不同的表。** [B]

> **教训**：AC6 的数据是**玩家 / NPC 双轨**的（`Bullet` vs `Bullet_Npc`、`AtkParam_Pc` vs `AtkParam_Npc`…）。
> 引用任何数值前，**先问"这是谁的"**。

#### 案例 ③ 「敌人攻击有没有 UI 预警？」——P12 纠正了 P7

| 报告 | 说法 |
|---|---|
| P7 | 把 PC 攻击表的 `alertLevel=1`（34 行）与 `shootIndicationType=1`（33 行）称作"敌方攻击预警等级/射击预告" |
| **P12（纠错）** | 实测 **NPC 表该字段 1371 行全 0**、告警等级仅 47/1371 启用、另有 102 行明确设为"不显示" |

**结论：这是 PC 一系攻击动作的稀缺通道，不能当作通用的敌方预警机制。** [B]

> **教训**：**同一字段名在 PC 表和 NPC 表里可以完全不是一回事。**
> 当两份报告冲突时，**采信做了全量统计的那一份**，而不是抽样观察的那一份。

#### 案例 ④ 「声音是不是 AI 的输入？」——两个报告结论相反，但可以调和

| 报告 | 说法 | 证据 |
|---|---|---|
| P11 | 声音是 AI 的输入 | `AiSoundParam` 听觉半径 30 / 100 / 150 m |
| P12 | AI 听觉实际关闭 | 听觉半径字段 **1047/1178 行填 0.1 m** |

**调和口径**：**"声事件广播"与"AI 感知参数"是两套通道。**
命中/开火会广播声事件（P11 说的是这个），但 AI 的听觉**感知字段本身没启用**（P12 说的是这个）。
**总案采用的口径：声事件会广播，但 AI 是否响应由脚本决定，不由这个半径字段决定。** [B]

### 6.2 其余八处（简表）

| # | 冲突 | 处理 |
|---:|---|---|
| 5 | **帧率口径**：P6 记动画事件基准 1/30 s，P7 把 0.05 s 顿帧称"3 帧"（隐含 60 fps） | **本文所有"帧"均按 60 fps 折算**；涉及动画事件时明确标 30 Hz |
| 6 | **伤害类型数量**：P2 说"三大伤害类型"，P5 说"四种属性（实弹/EN/爆炸/珊瑚）" | 并存：**三种"伤害类型"用于机制**，珊瑚是**第四种属性**。P5 早期版本按旧 paramdex 写成 Physics/Magic/Fire，已废弃 |
| 7 | **"热"是不是独立资源**：P2 判定"独立热量条"无法证实（D），P5 实测"冷却性能"落在 EN 回复延迟与发电机输出缩放上 | **采信 P5：热已折叠进 EN**。任务书里"五大资源（EN/热/弹药/AP/姿态）"的表述应改为**四大资源** |
| 8 | **QB 定性**：P6 称"纯位移工具"，P8 指出位移仅 3.9 m | **统一为"短距闪避，主要价值是规避弹道而非位移"**，两者是同一事实的两种措辞 |
| 9 | **±45° 限位**：早期写作常态 | **是极值不是常态**（160/351 行为 0、中位 −2°、仅 2 行为 −45°） |
| 10 | **命中矩阵维度**：早期称"二维矩阵" | **实为四维**：受击材质(64 行) × 攻击属性×概念(32 列) × 攻击类型(5) × 威力档(5)；且 25 列中爆风 5 列全表零值（实为 20 列） |
| 11 | **敌人硬直阈值的位置**：主文档早期记在 `NpcParam.stabilityVal` | **实测该字段仅 2/1232 行非零**，真实位置是 `DamageLevelConvThresholdParam`（57 行、rid = 敌人 ID） |
| 12 | **P11 内部数字漂移**：结论区写 441/646 行，验证表写 447/649 行 | 引用时**只用"数百行"的量级表述**，不引用精确值 |

### 6.3 从这 12 处里提炼的三条纪律

| # | 纪律 | 为什么 |
|---:|---|---|
| 1 | **引用任何数字前，先声明口径**（范围 / 对象 / 单位 / 帧率） | 案例 ① ② ④ |
| 2 | **玩家侧与 NPC 侧永远分开统计** | 案例 ② ③，AC6 全表都是双轨的 |
| 3 | **冲突时采信"做了全量统计"的那一份，而不是"抽样观察"的那一份** | 案例 ③ ⑪ |

> **这三条可以直接搬到你的作品集和面试里**：
> 当你能主动说"这个数字我用的是 X 口径，换成 Y 口径会变成 Z"，面试官对你的信任度会立刻不同。

## §7 AC6 自己的代价与争议

> **为什么必须读这一节**：前面 17 个维度几乎都在讲"AC6 设计得多精妙"，这是典型的**幸存者偏差**。
> **面试官如果问"你觉得 AC6 有什么问题"，只会背优点的人会立刻露怯。能说出代价的人，才显得真的研究过。**

| # | 争议点 | 具体是什么 | 证据 | 你的评价抓手 |
|---:|---|---|---|---|
| 1 | **无难度选项** | 游戏不提供难度设置，只能靠"换装"自行调节 | 实测：选项菜单 **62 条属性里没有任何难度项**；**没有字号设置、没有色盲模式** [B] | 支持者说是"设计完整性"（难度是表达的一部分）；反对者说是可及性问题。**客观地说：它把"调节难度"的门槛从"菜单点一下"提高到了"理解装配系统"——这对新手是真实的墙** |
| 2 | **平衡补丁推翻既有经验** | 1.02 补丁削弱 Balteus 并大幅加强一批武器 | 社区实测与媒体报道 [C] | 这是**长线平衡的必然代价**：削弱让更多人通关，却让"打过原版 Balteus"失去可比性。**对做拆解的人还有副作用：你测的数据可能已被版本改过** |
| 3 | **新手墙在"装配"而非"操作"** | 卡关时官方希望你换装，但新手往往不知道该换什么 | 实测存在 `AutoAssembleEvaluate`（自动配装评分）→ **官方知道这是难点并给了兜底** [B] | **这是"设计很好但传达失败"的典型**：机制本身优雅（装配即难度），但**没教会玩家使用它**。做复刻时如果要改进，**这里最值得改** |
| 4 | **信息密度过高** | HUD 同时呈现 AP/姿态/四武器/锁定/雷达/EN/目标 | 实测 `MenuPropertyLayoutParam` **2512 行**在描述这些槽位 [B] | 核心玩家觉得"专业"，新玩家觉得"糊"。AC6 的解法是**状态驱动显隐**，但**没有提供整体简化档位** |
| 5 | **任务结构重复** | 大量任务是"到地点 → 清敌人 → Boss"，关卡辨识度不均 | 21 个区域支撑 49 个任务（约 2.3 任务/图）[B] | 这是**内容产能与工期**的问题，不是设计能力问题。**但它提醒你：机制漂亮 ≠ 内容耐玩** |
| 6 | **PvP 与 PvE 的平衡冲突** | 同一套数值要同时服务单机与对战 | 实测 `MultiPlayCorrectionParam` **仅 2 行**——**官方也只能靠"额外修正表"来隔离两套平衡** [B] | 这是所有"PvE 数值直接搬进 PvP"游戏的**通病**。**你的复刻如果只做单机，可以完全跳过这个坑** |

### 怎么用这一节（三个具体做法）

1. **面试时主动提**：讲完"ACS 姿态系统多精妙"之后，补一句——
   > "但它的代价是新手不知道该换装，官方只能靠自动配装兜底。**这一句的含金量高于前面十句赞美。**"
2. **作品集里做取舍说明**：明确写"我复刻时会加一个新手引导的装配推荐，因为原版这里存在传达缺口"——
   **这展示的是设计判断力，而不只是实现能力**。
3. **警惕你自己的拆解被版本淘汰**：本文数据取自本机特定版本。**任何"XX 武器最强"的结论都可能已经过期**——
   所以全文**只讲结构，尽量不下"哪个强"的判断**。

## §8 策划面试：怎么用这份拆解

### 8.1 五个可以直接讲的故事

| # | 故事 | 讲法（三段式） | 用到的章节 |
|---:|---|---|---|
| 1 | **"难度不一定要做成菜单"** | ① AC6 没有难度选项 ② 它把难度做成了装配系统（硬门 + 软门 + 资源门三层约束）③ 代价是新手不知道该换什么 | §4.2 + §7 |
| 2 | **"用数字否决一个方案"** | ① 有人提"TTK 做短一点更爽" ② 但机制链需要 3~4 环 × 单环 2~4 秒 ③ 所以 TTK 低于 8 秒，我给玩家设计的第二血条永远打不满 | §2 + §4.1 |
| 3 | **"反馈的本质是预算分配，不是强度叠加"** | ① 机炮 10 发/秒 × 0.05 s 顿帧 = 50% 时间冻结 ② 所以顿帧只给近战，枪械用限流 ③ 确认要即时、累积要聚合、危险要提前 | §4.3 |
| 4 | **"经济系统的每个系数都在表达态度"** | ① 修理系数 2.0 而弹药系数 1.0 ② 这是"惩罚挨打、不惩罚开枪" ③ 上限 200,000 决定最坏情况有多坏 | §4.9 |
| 5 | **"买断制单机怎么做出长尾"** | ① 不靠赛季通行证 ② 靠"经济缺口"（一周目只能买 29%）让重打成为必然 ③ 长尾建在零边际成本的表达层（2300 行徽章/涂装/贴花） | §4.16 |

### 8.2 三种"少见的说法"（面试里几乎没人讲）

| # | 说法 | 为什么稀缺 |
|---:|---|---|
| 1 | **"哪些信息该走耳朵"是一套带宽论证** | 音频是全向、毫秒级、多信道并行；视觉只有约 100° FOV、一次只能突出一个焦点。**大多数人只会说"音效很重要"** |
| 2 | **"叙事投放预算表"** | 每条通道有边际成本与送达率：战斗中通讯占文本池 58.3% 但吸收率不可控；任务简报只占 5.2% 却是唯一 100% 送达的通道 |
| 3 | **"我怎么把一个 slogan 变成表里读得出来的数字"** | 把"机甲不是放大的人"变成"10 m 落地 0.408 s vs 放大的人 1.429 s，重力是相似律预测的 2.20 倍" |

### 8.3 一条自检：你的回答有没有"可证伪性"

| 不合格的回答 | 合格的回答 |
|---|---|
| "AC6 的战斗手感很好" | "AC6 的顿帧只给了近战（45/712 行），因为枪械加顿帧会变成卡顿" |
| "它的 HUD 信息量很大但不乱" | "它把信息分成三级：中心留决策、边缘留状态、脱战按固定秒数淡出" |
| "难度设计很巧妙" | "它没有难度菜单，难度在装配界面；三层约束里只有总重是硬门" |
| "经济系统很平衡" | "弹药费率全 1.0 而修理系数 2.0，且只在任务完成时结算" |

> **规律**：**每个形容词后面都应该跟一个数字或一条规则。** 这是这份拆解能给你的最直接的迁移能力。

## §9 自己动手验证的方法

> 这份总案的每一条都来自本机数据。**你也可以自己查**——这是"可证伪"的前提。

### 9.1 三条命令解决 90% 的验证需求

```bash
cd <repo>

# ① 查任意表、任意字段的取值分布（同时给出"全体"与"非零"两种口径）
python tools/check_field.py <表名> <定义名> <字段名>
# 例：查推进器的 QB 冷却时间
python tools/check_field.py EquipParamBooster EquipParamBooster QB_ReloadTimeSec

# ② 位域字段必须按位读（按整字节读会得到完全相反的结论）
python tools/check_bit.py <表名> <字段名>

# ③ 全库终校：确认本文引用的结构数字仍然成立
python tools/verify_doc.py        # 预期：通过 203 / 203
```

### 9.2 想深挖时的两份资源

| 资源 | 位置 | 能给你什么 |
|---|---|---|
| **AC6 专用 paramdex** | `<WORKSPACE>\tools\WitchyBND\Assets\Paramdex\AC6\` | 228 个字段定义（字段名 + 字节偏移 + **日文显示名/描述**）、266 个**开发者行名注释**、374 个枚举定义 |
| **开发者行名** | 同上 `Developer Names/*.txt` | 开发者自己写的注释，例如"ジャガ撃破カメラテスト"（打 Juggernaut 的相机测试）→ **能告诉你每一行数据是干什么的，包括测试残留** |

> 想图形化浏览这些表，可以装社区编辑器 **Smithbox**。

### 9.3 四个"数据挖掘纪律"（都是踩过坑得来的）

| # | 纪律 | 踩坑记录 |
|---:|---|---|
| 1 | **位域必须按位读** | 按整字节读 `isEnableAutoHoming` 得到"568/568 全开"，按位读是 **0/568**——结论完全相反 |
| 2 | **警惕遗留表** | `GameAreaParam` 其实是魂 1 数据、`PlayRegionParam` 是魂 3、`ThrowParam` 的引用 ID 在 AC6 里**一个都不存在**——这些表结构合法、数据非空，但**不是 AC6 的机制** |
| 3 | **统计口径必须写明** | 同一字段剔除哨兵值（−1）/ 仅正数 / 含 −1，会得出**三个不同的中位数** |
| 4 | **"字符串出现过" ≠ "结论成立"** | 用"关键词是否出现"做判断，会导致**连续四次把正常内容误判为错误** |
