## 2. 正确的判据：三条可证伪的检验

改用**数据本身**说话，不再依赖"文档里有没有这个词"：

| # | 判据 | 做法 | 排除什么 |
|---:|---|---|---|
| **①** | **结构自洽** | 行宽是否与 paramdex 期望一致 | def 匹配错 → 后续结论不可用 |
| **②** | **内容非空** | 所有非 padding 字段的最大「非零非哨兵」率 | 空壳表（全 0 / 全 −1） |
| **③** | **外键自洽** | 按 paramdex 日文显示名把字段映射到目标 ID 空间，统计命中率 | 遗留表（ID 指向别的游戏） |

判决规则：

```
命中率 < 50% 且 唯一值 >= 5   →  LEFTOVER  遗留嫌疑
最大非零率 = 0                →  EMPTY     空壳
其余                          →  IN_USE    在用
（字段被标注废弃 → 不参与判定，单独归入 DEPRECATED）
```

> ⚠️ **50% 是启发式阈值，不是自然常数。** 所以报告和脚本**始终同时输出原始命中率**，读者可以自己复核，不必接受一个标签。

## 3. 四类假阳性 —— 我实际犯的四个错

这一节是本文最有价值的部分。**每一次我都以为找到了问题，每一次都证明是我错。**

### 假阳性 ① 目标空间选错：用单表 vs 用联合空间

**症状**：`NpcParam`（AC6 核心表，1232 行）被判为"遗留表"。

**排查**：

```
NpcParam.RetargetReferenceChrId （リターゲット参照キャラID）
   对 NpcParam 单表：        0 / 117 =   0.0%   ← 看起来是遗留
   对「角色联合空间」：    117 / 117 = 100.0%   ← 完全合法
   唯一值：只有 3 个（3000 / 3020 / 3400）
```

**根因**：角色 ID **同时出现在多张「按角色索引」的表里**（模型 / 转向 / AI / 材质 / 音效…），`NpcParam` 只是其中之一。只对单表验证，必然得到假阳性。

**修正**：改用**角色联合空间** = 9 张按角色索引表的行 ID 并集（4,749 个）：

```
ChrModelParam · ChrActTurnParam · ChrActTurnParam_Npc · NpcThinkParam ·
NpcMaterialParam · AiSoundParam · RuntimeSoundParam_Npc ·
AttackActionParam_NPC · EquipParamWeapon_Npc · BehaviorParam_NPC
```

### 假阳性 ② 同型错误重演：子弹 ID 也是双轨的

**症状**：修完 ① 之后，`Bullet_Npc`、`LookAtParam_Npc`、`LookAtParam` 三张表又被判为遗留。

**排查**：

```
Bullet（玩家）  =   568 行
Bullet_Npc      = 2,537 行
并集            = 3,093       交集只有 12 个  ← 两套独立 ID 空间！

Bullet_Npc.intervalCreateBulletId （間隔指定発生弾丸ID）
   对 Bullet 单表：          0 / 111 =   0.0%
   对「子弹联合空间」：    111 / 111 = 100.0%   ← 完全合法
```

**根因**：和 ① 是**同一个错误的重演** —— 玩家侧与 NPC 侧是两套平行表（`Bullet`/`Bullet_Npc`、`AtkParam_Pc`/`AtkParam_Npc`、`EquipParamWeapon`/`EquipParamWeapon_Npc`）。

**修正**：`WEAPON` 与 `BULLET` 空间同样改为联合。

### 假阳性 ③ 字段级废弃 ≠ 表级遗留

**症状**：`LookAtParam.predictionBulletId` 命中率只有 77.1%，被算作"表有问题"。

**排查**：读 paramdex 原文 →

```xml
<Field Def="s32 predictionBulletId = -1">
  <DisplayName>【廃止予定】ターゲット予測に用いる弾丸ID</DisplayName>
```

**它标着【廃止予定】。** 废弃字段的值**不再维护**，所以它的命中率既不是 100% 也不是 0%，**这个数字本身没有诊断意义**。

而且 `LookAtParam` 的预测字段是**成族废弃**的：`predictionBulletId`、`predictionMaxTime`、`predictionShootObserveTime`（后者还额外标了【無効中】）。

**修正**：从 paramdex 提取废弃字段集合，**这些字段不参与遗留判定**，而是单独归入"字段级废弃"清单（见 §4）。
**关键区分：字段废弃是字段级结论，不能推出表级结论。**

> 🐛 **顺带修掉一个解析 bug**：`<Field Def="s32 predictionBulletId = -1">` 的 Def **带默认值**。
> 用 `split()[-1]` 取名字会拿到 `-1`（实测：废弃字段清单里出现了名为 `-1` 的"字段"）。
> 正确写法是先按类型切、再按 `=` 切：`re.match(r'^(\w+)\s+(.+)$', def).group(2).split('=')[0]`。

### 假阳性 ④ 全局 ID 空间**没有区分度**

**为什么要单独记一条**：这是最容易"看起来很聪明"的做法 —— 把所有 257 张表的行 ID 并成一个大集合（36,508 个），凡是取值落在里面就算合法。

**实测：它会把真遗留判成合法。**

| 字段 | 对 CHR 联合空间 | 对**全局**空间 | 真相 |
|---|---:|---:|---|
| `ThrowParam.DefChrId` | **31.7%** | **95.1%** | 真遗留 |
| `ThrowParam.AtkChrId` | **39.6%** | **91.7%** | 真遗留 |
| `NpcParam.RetargetReferenceChrId` | 100.0% | 100.0% | 合法 |

**原因**：ID 空间越大，小整数越容易偶然命中。36,508 个 ID 让 1000~9999 区间的值几乎必然"命中"。

**结论：判据的粒度必须匹配语义。**
- 全局空间（36,508）→ **无区分度，禁用**
- CHR 联合空间（4,749）→ 可用
- 单表（1,232）→ **漏报，禁用**

### 附：第五类假阳性——没读上下文就下结论

我在文档里搜到 `AppropriateType_Energy` 被 P10 报告引用 4 次，且该字段在 `EquipParamProtector` 上标着【廃止予定】，于是怀疑 P10 出错。

**读了原文才发现我错得离谱**：

```

| 3300 | 【ARM】腕部積載許容量 | @572 AppropriateType_Energy | @568 armMaxWeight |
```

**P10 恰恰是在论证"首偏移读法会导致张冠李戴"，它举 `AppropriateType_Energy` 当反例。** 我的关键词命中，命中的是别人写的反例。

**这条和第 1 节的"表名匹配"是同一个病**：**把"字符串出现了"当成"结论成立了"。**

### 4.1 两条最有设计价值的

**① `EquipParamBooster` 的加速度字段族被终速模型取代**

```
f01_dashBoostStartAccelMPSS          【地上B】開始加速度[m/s^2]（※終端速度により廃止予定）
f02_dashBoostMaxAccelMPSS            【地上B】最高加速度[m/s^2]（※終端速度により廃止予定）
f07_flyBoostHorizontalStartAccelMP   【空中B】水平開始加速度[m/s^2]（※終端速度により廃止予定）
f08_flyBoostHorizontalMaxAccelMPSS   【空中B】水平最高加速度[m/s^2]（※終端速度により廃止予定）
```

**这是一条关于 AC6 运动模型的直接证据**：推进器从"加速度驱动"改成了"终速驱动"。
它和主文档已有的实测（`dashBoost_EndSpeedKMH` 260~430、`flyBoost_EndSpeedKMH` 260~430）**互相印证** —— 有效字段全是 `*EndSpeed*`，废弃字段全是 `*Accel*`。

`damageDamp` / `spelDamageDamp` / `fireDamageDamp` / `thunderDamageDamp` / `darkDamageDamp` / `staminaDamp` / `knockbackDamp` —— **7 个伤害类型的衰减率全部废止**。

> **使用方式**：做任何字段取值前，先跑 `python tools/audit_table_usage.py --table <表名>`，看该字段是否在废弃列表里。
> **它现在也写进了 CSV**（`data/table_usage_audit.csv` 的 `deprecated_field_count` / `fk_skipped_deprecated` 两列）。

## 5. 唯一经得起复核的遗留表：`ThrowParam`

### 5.1 实证

```
表 ThrowParam : 131 行 × 132 字节
def 匹配: ThrowParam (name+size)  期望 132          ← 结构合法
内容画像: 最大非零率 100.0%                          ← 有真实数据，不是空壳

外键 AtkChrId（投げ側キャラID）→ CHR 联合空间    19 /  48 =  39.6%   唯一值 39
                                        只对 NpcParam 单表   0 /  48 =   0.0%
外键 DefChrId（受け側キャラID）→ CHR 联合空间    26 /  82 =  31.7%   唯一值 43
                                        只对 NpcParam 单表   0 /  82 =   0.0%
                              （两个字段合计：单表 0/130，联合 45/130 = 34.6%）
```

**它确实有内容**（`escHp` 投技挣脱 HP 43/131 非零，值 5/25/30/50；`atkAnimId` 130/131 非零），**不是空壳表**。
但**即使给它最宽的合理空间（角色联合），仍有 60~68% 的引用找不到归属**。

**对照基准**（合法字段应该长什么样）：

| 字段 | 对正确空间 | 唯一值数 |
|---|---:|---:|
| `NpcParam.RetargetReferenceChrId` | **100.0%** | 3 |
| `Bullet_Npc.intervalCreateBulletId` | **100.0%** | 59 |
| `Bullet_Npc.HitBulletID` | **98.5%** | 827 |
| **`ThrowParam.DefChrId`** | **31.7%** | 43 |
| **`ThrowParam.AtkChrId`** | **39.6%** | 39 |

### 5.2 判定

**`ThrowParam` 是魂系遗留表** —— 数据从 Souls 引擎继承，AC6 既不使用也没清理。

它命中本项目已记录的 **「第 6 坑：遗留表陷阱」**，同族已知案例：`GameAreaParam`（魂1数据）、`PlayRegionParam`（魂3）、`NpcAiActionParam`（行名是 R1攻撃）。

### 5.3 ⚠️ 索引纠错（重要，但**我没有改**）

`docs/05_提示词集/AC6拆解_提示词集.md` 附录 A 把 `ThrowParam` 定性为：

```
| 弹丸与弹道 | `Bullet`、`BulletShotgunParam_PC`、`CylinderParam`、`ThrowParam` | 弹速、散射、追踪、投掷物 |
```

**两处不准确**：

| # | 索引写的 | 实际 | 影响 |
|---:|---|---|---|
| 1 | 「**投掷物**」 | **投技 / 抓取**（投げ側/受け側キャラID、投げ抜けHP、投げアニメID） | 定性错误，会误导后续 AI 去分析"投掷物弹道" |
| 2 | 无可用性标注 | **很可能是遗留数据**（外键 60~68% 无归属） | 可能被当成 AC6 机制来拆 |

**脚本设计要点**（都来自本次踩的坑）：

| 设计 | 原因 |
|---|---|
| 外键用**联合空间**，不用单表 | 假阳性 ①② |
| 废弃字段**不参与**遗留判定 | 假阳性 ③ |
| 输出**始终给出原始命中率**，不只给标签 | 50% 阈值是启发式 |
| `MIN_UNIQUE_FOR_LEFTOVER = 5` | 唯一值太少 = 系统性引用，不是遗留 |
| 明确拒绝全局 ID 空间 | 假阳性 ④ |

## 8. 不确定项（诚实清单）

| # | 不确定 | 影响 | 怎么查 |
|---:|---|---|---|
| 1 | **42 张 NO_DEF 表未验证外键** | 中 —— 可能有其他遗留表藏在里面 | 补 def 匹配（尺寸 + 字段名重叠） |
| 2 | 50% 阈值是**启发式** | 中 —— 边界样本可能翻转 | 看 CSV 里的原始命中率自行判断；`ThrowParam` 31.7%/39.6% 离边界不远 |
| 3 | CHR 联合空间**是否完整**（目前 9 张表） | 中 —— 漏了表会让命中率偏低 | 找出所有"行 ID 是角色 ID"的表 |
| 4 | 废弃标记的**人工判读** | 低 | paramdex 是日文原文，「廃止予定」= 预定废止，语义明确 |
| 5 | `ThrowParam` 是"完全不用"还是"少用" | 低 | 48/131 与 82/131 非零，说明表内有相当多行有值；但它引用的角色在 AC6 里不存在 |

## 9. 一句话总结

> **我提出的"37 张表从未被拆"是错的，"7 组完整系统待拆"基本不成立。**
> 真正站得住的只有三件：**① 1 张遗留表（`ThrowParam`）**、**② 53 个废弃字段（15 张表）**、**③ 一套能防住四类假阳性的判据**。
>
> 而这三件里，最有用的不是任何一条结论，而是**第 ③ 件** —— 因为前两件是"这次查出来的"，第 ③ 件是"下次不会再错的"。
>
> **核心教训一句话**：**字符串出现过 ≠ 结论成立。**
> 无论是"表名在文档里出现过"、"关键词在报告里出现过"，还是"值在 ID 空间里能偶然命中"——都不能当证据。**必须读上下文、必须用语义匹配的粒度、必须让每一步都能被证伪。**
