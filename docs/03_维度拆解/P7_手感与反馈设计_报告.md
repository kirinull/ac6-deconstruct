# 《装甲核心 6：境界天火》拆解 · P7 手感与反馈设计（Game Feel / TA 重点）

> 读者定位：大四、目标技术美术（TA）、计划从策划岗入门。
> 本文所有带「实测」字样的结论，均在文末 **§11 实测证据** 附有实际执行的命令与原始输出片段。

## 0. 结论先行（TL;DR，12 条）

| # | 结论 | 等级 |
|---|---|---|
| 1 | AC6 的「手感」不是靠调参调出来的，而是一条**数据管线**：事件 → 参数表行 → 通道集合。反馈的强度/时长/衰减全部落在可版本管理的表里，代码只负责消费。 | B |
| 2 | **顿帧（hitstop）在 AC6 是近战专属机制**：AtkParam_Pc 712 行中只有 **45 行** hitStopTime ≠ 0，且这 45 行**全部是近战武器**（刀 / 锤 / 桩 / 薙刀 / 匕首 / 电棒…），**没有任何枪械或子弹攻击设置顿帧**。 | B |

| 4 | **镜头抖动与手柄震动同源**：PadRumble.param 的尾部类型名是 CAMERA_RUMBLE_PARAM_ST，174 行 × 84 B（本机实测）。一行数据同时定义「镜头怎么抖」和「手柄怎么震」。设计者是把抖动当作**跨模态反馈事件**在管理。 | B |

## 1. 方法：这一维度能拿到什么、拿不到什么

**能拿到**（本机 <WORKSPACE>/ac6_merge/van/regulation-bin/*.param，257 张表 + AC6 专用 paramdex <WORKSPACE>/tools/WitchyBND/Assets/Paramdex/AC6/）：

- 全部**数值与枚举语义**：paramdex 的 Defs/*.xml 给出「字段名 + 字节偏移 + 类型 + 日文显示名」，Tdfs/*.tdf 给出枚举含义，Developer Names/*.txt 给出开发者给每一行写的用途注释。
- 表与表之间的**外键关系**（例如 Bullet.shootCameraRumbleParamId → PadRumble 行 ID）。

**拿不到**（必须诚实标注）：

- **代码侧的时序实现**：顿帧到底冻结谁（只冻受击者动画？双方？镜头？粒子？）在数据里看不出来，只能从「字段名 + 数值语义」反推。
- **曲线资产本体**：rumbleId 指向的手柄震动波形、镜头抖动曲线，以及 TAE 动画、FFX 特效资源，都在 regulation 之外。
- **音频中间件的实际混音**：只能看到 Wwise Switch 的字符串映射，看不到实际音源与音量。
- **帧级实测**：本机不能跑游戏，所有「多少毫秒」的量级都是从秒制参数换算或行业经验来的。

## 2. 输入层拆解

### 2.1 输入缓冲 / 取消窗口 / 长按判定：一张表看完

**四段式（输入缓冲）**

- **设计意图**：AC6 的动作是不可打断的重动作（QB、AB、近战突进都有硬直）。如果没有缓冲，玩家必须在硬直结束的那一帧精准按键；有了 0.4 s 缓冲，玩家可以提前一拍操作，命中率大幅提升，而**不会**让动作变得更灵敏。
- **实现手段（可观察）**：precedeInput_InputTimeSec 一个 f32 控制寄存时长；与 PadHoldTimeSec = 0.4 同值，说明这是同一套节拍下的参数族。
- **玩家体验 / 结果**：连段时不会按键吞掉，但也意味着**输入不能被即时取消** —— 手感是重的，不是灵敏的。
- **可复用结论**：缓冲时长应当 ≥ 一个动作硬直的量级，且**同一游戏内所有长按类判定最好用同一个值**（AC6 的 0.4 s / 0.5 s 高度集中），这极大降低了玩家的学习成本。

### 2.2 取消窗口：状态矩阵，不是时间区间

| 表 | 结构 | 实测 | 含义 |
|---|---|---|---|
| AttackActionParam_PC | 418 行 × 100 B，57 字段 | 每行 32 个 triggerActionType_00..31（トリガーN アクションタイプ）+ behaviorJudgeId | 每个攻击动作声明 32 个条件判定类型，由行为系统在运行时判断当前是否允许触发某个后续行为。 |
| BehaviorChangeStateMatrixParam | **227 行 × 32 B**，20 个 state00..state19 位 + TransitionActionAiType + NoticeStateID | state00 地上 74 行置位、state04 落下 78、state13 VOB 54、state01 ダッシュ 55…… | 一张**状态 → 允许 / 禁止**的矩阵。20 个状态位就是取消白名单。 |

**四段式（取消窗口）**

- **设计意图**：机甲动作多（QB / AB / 近战 / 射击 / 切武器 / 装填 / 盾 / 浮游 / 坦克态 / VOB…），用时间轴取消点逐个标注是组合爆炸；改用**状态矩阵 + 触发类型**，可以一次声明 N 个动作 × M 个状态的可取消性。
- **实现手段（可观察）**：行为 ID（behaviorJudgeId）→ 动作表（AttackActionParam）→ 触发器类型（32 个）→ 状态矩阵（20 位）。
- **玩家体验 / 结果**：玩家感知到的「QB 能取消射击后摇，但射击不能取消 QB」这类规则，本质是矩阵里的一个位。
- **可复用结论**：**取消窗口应当用状态机可达性建模，而不是用帧区间建模**。前者可扩展、可校验；后者每加一个动作都要手工对齐帧数。TA 的价值在于把这张矩阵做成可视化工具（见 §10.1）。

附加实测（AttackActionParam_PC 分布）：alertLevel = 1 有 34 行（敌方攻击的预警等级）、shootIndicationType = 1 有 33 行（**射击预告显示**）、isReloadInputExcludeTrigger = 1 有 18 行（装填时排除触发器输入）、isTaeShootTimingOnly = 1 有 2 行。这三类字段说明「敌人攻击的可读性」也是数据驱动的。

**四段式（瞄准辅助）**

- **设计意图**：AC6 是高速三维射击，玩家无法逐发精确瞄准；它把帮助分散到**四个层级**：① 锁定选择层（软锁 / 硬锁 / 瞄准放大）；② 子弹发射层（开火补正角锥）；③ 弹道层（自导转向率、速度补偿）；④ 近战层（突进自导 + 相机保障锁定）。
- **实现手段（可观察）**：每层都是独立字段，且**按武器 / 子弹逐行配置**，不是全局难度选项。
- **玩家体验 / 结果**：玩家感觉武器粘得住敌人，但轻武器与重武器的粘性不同（15° vs 60° 补正角），这是武器个性的一部分。
- **可复用结论**：**瞄准辅助应当按武器 / 弹种粒度给，而不是按玩家设置粒度给**。全局 aim-assist 强度滑条会把武器差异抹平；AC6 的做法是让每把武器的补正角锥成为它的隐性手感属性。

> **D 级提醒**：lockShootLimitAng 的精确运行时语义（是「子弹向锁定目标偏折的最大角度」还是「允许自动锁定的目标角度范围」）我无法从数据表确证。字段日文名是「射撃補正角度」、说明是「射撃補正角度（水平）」。**验证方法**：在 PC 版用一个 15° 与一个 180° 的子弹对比无锁射击时的弹道偏折；或反编译读取该字段的消费者。

## 3. 输出层：反馈矩阵

**四段式（同源抖动）**

- **设计意图**：让视觉抖动和手柄震动共享同一个事件定义与包络，避免两个通道各自演化、互相打架。
- **实现手段（可观察）**：一个 CAMERA_RUMBLE_PARAM_ST 行里同时有 rumbleId（振动图案）与 hdPadRumbleId（HD 触觉图案），加上 lifeTimeSec / beginDist / endDist / priority / targetType / 4 个场景增益（airRateSelf、landRateSelf、airRateAnother、landRateAnother）。
- **玩家体验 / 结果**：屏幕上抖和手上震是同一个事件的两种表达，节拍一致。
- **可复用结论**：**给反馈系统建一个「事件表」而不是给每个通道建表**。TA 工具应当以事件为中心，一屏看到该事件在 10 个通道上的全部参数。

即 **10 格网格 = {强, 弱} × {30f, 90f, 40f, 20f, 10f}**。玩法事件另外用 101–121 这一批图案（103 = QB 系列、101 = 推进点火 / 小着地 / 段階加算被弾、102 = 跳跃 / 解除悬停 / 100%加算被弾、109 = 大着地 / 大よろけ / 吹っ飛び開始、106 = 小よろけ、112 = 格闘大命中…）。

**可复用结论**：**给策划的不是「随便画一条曲线」，而是一个受限的图案网格**（2 强度 × 5 时长 = 10 格）。这直接抑制了「每条事件都手绘一个震动」的资产爆炸，也让玩家能学会「这条震动 = 大事件」。

> **D 级提醒**：开发名里的 30f / 90f / 40f / 20f / 10f 我假定是帧数（60 fps 下 = 0.5 / 1.5 / 0.667 / 0.333 / 0.167 s），但实测这些行的 lifeTimeSec 是 1.0 / 1.6 / 2.0 / 2.3 / 4.0 s，**不吻合**。所以 f 到底指什么（波形采样帧数？包络段数？）无法从本机数据确认。**验证方法**：解包手柄震动波形资源比对采样长度；或对比 lifeTimeSec 与曲线的实际衰减时间。

### 4.2 全局还是局部？—— 数据层面的证据

- HardHitStopTimeRatePercent 是 **GameSystemParam（全表 1 行）** 的字段 → 说明存在一个**全局的硬直时间缩放比**。
- 但时长 hitStopTime 是**逐攻击行**的 → 每次命中的停顿时长是局部的。
- NpcParam.hitStopType 是**逐敌人**的 → 「谁会被停住」是按敌人配置的。
- AtkParam.isMultiHitArmorHit_DisableHitStop 是**逐攻击**的 → 「打装甲时不顿帧」也是按攻击配置的。

**推断（C 级）**：AC6 的顿帧至少在实现上是「**受击方动画速率被乘上一个小于 1 的系数，并持续 hitStopTime 秒**」，而不是「整个渲染 / 物理世界的时间被缩放」——否则不可能有敌人级别的 hitStopType 差异化，也不会单独有 isMultiHitArmorHit_DisableHitStop。**验证方法**：PC 版在一次近战命中顿帧的瞬间观察：① 爆炸粒子是否也停了；② 远处敌人的动画是否停了；③ 相机是否继续响应输入。

### 4.3 时长量级与「持续开火如何避免糊」

**近战顿帧量级**：0.05 s（**3 帧 @60fps**）是绝对主力；例外只有三个：チェーンソー強攻撃フィニッシュ 0.07 s、電磁ハンマー弱攻撃①② 0.10 s、**爆裂パイル強攻撃①-1 0.12 s（7 帧）**。配合 1% 的播放速率，**0.05 s 实际上 ≈ 3 帧的画面冻结**。

- **设计意图**：机炮 / 霰弹每秒产生 10+ 次命中事件。如果每次都播全量反馈，信道会饱和，玩家反而读不到哪一发重要。
- **实现手段（可观察）**：在三个层级各自限流 —— ① 音频层（50 m 内只允许 1 个命中 SFX、0.2 s 最小间隔）；② 数值展示层（0.5 s 内伤害数字合并累加）；③ 冲击条层（0.8 s 后开始淡出、0.4 s 合并窗口）。
- **玩家体验 / 结果**：连射时听到的是节奏化的哒哒哒而不是白噪音；伤害数字是累加后跳一次，不是满屏乱飞。
- **可复用结论**：**「打击感」的反面是「信道预算」**。TA 做手感系统时，第一件工具应该是信道占用看板（当前 1 秒内：SFX 并发数 / 粒子上限 / 震动抢占情况），而不是曲线编辑器。

## 5. 反馈延迟预算：AC6 把重量放在哪

### 5.1 业界典型预算（**C 级**，行业经验值，非本机数据）

| 通道 | 感知即时的阈值 | 典型工程预算 |
|---|---|---|
| 输入 → 画面变化 | 约 100 ms 内被视为因果相关 | 1–3 帧（16.7–50 ms @60fps） |
| 输入 → 音效 | 约 20–30 ms 内被视为同期 | ≤ 2 帧音频缓冲（约 20–45 ms） |
| 输入 → 触觉 | 约 30 ms 内 | 尽量同帧 |
| 视觉后处理 / 镜头 | 可容忍 1–2 帧滞后 | 做插值时另计 |

**AC6 自己的延迟预算不在这 257 张表里**（D 级，需实测：PC 版用 240 / 1000 fps 高速摄像 + 输入宏，逐帧数）。这是本维度**最值得用真机实测补上的一环**。

### 5.2 AC6 把重量感放在哪：从数据看它的选择

关键观察：**TentativePlayerParam 里没有任何「输入延迟」字段，但有一大堆响应曲线字段**。

| 重量来源 | 字段 | 实测 | 说明 |
|---|---|---|---|
| 转身加速曲线 | ChrActTurnParam.baseTurnSpeedDPS、turnAccelDPSS、reverseTurnBrakeDPSS、timeTurnRate_*、paramEndIntpTimeSec | 258 行 × 168 B 的完整曲线系统 | 转向不是开关，是加速 / 时间双重插值。 |
| 机体朝向 vs 摇杆 | TurnStartAngleDeg_90/180、DelayTurn_MaxTurnAngDegPerSec = 720 deg/s | 45° / 110° | 大幅转向需要转身动画，有节拍。 |
| 加速方向插值 | BoostParam.boostDirLerpRate = 0.1 /Frame、counterBoostDirLerpRate = 0.17 /Frame | 逐帧插值 | 推进方向追不上输入 → 惯性感。 |
| 相机滞后 | lockCamParamLerpRate = 0.15、CamLockInterpolationFactor = 40、lookTargetOffsetLerpSpeed = 0.01 rad/s | 0.15 / 40 / 0.01 | 相机追着看，永远慢半拍。 |
| 开枪后坐 | ShootReboundParam：reboundLength **−0.01 ~ −0.30 m**、animFrame **3–30**（均值 6.4）、10 组 boundKeyN_boundFrame / boundRate% 关键帧 | 51 行 × 196 B | 后坐是**关键帧驱动的位移**（首帧 1 帧内约 90–100% 位移，第 2–3 帧回收），而不是简单的正弦抖。 |
| 近战突进前摇 | BladeHomingParam.accelTime ≤ 2 s、maxSpeedKMPH ≤ 1500 | 见 §2.3 | 扑过去需要时间。 |
| 惯性消除 | AtkParam.isDamageReactionCancelInertia、damageReactionDisableGravityTimeSec | 存在 | 受击时是否清惯性、是否临时关重力。 |

**四段式（重量 vs 迟滞的平衡）**

- **设计意图**：让玩家觉得在驾驶一台 10 米高的机器，但**不能让玩家觉得按了没反应**。
- **实现手段（可观察）**：AC6 的做法是 **「输入不延迟、响应有曲线」** —— 输入采样与判定仍然即时（precedeInput 只是缓冲，不是延迟），但机体姿态、朝向、相机、后坐全部走插值 / 关键帧。同类对比：没有任何一个字段叫 inputLag 或 responseDelay。
- **玩家体验 / 结果**：按 QB 会立刻进入 QB 状态（无延迟），但机身朝向变化、相机追尾、落地姿态都有重量。玩家抱怨的是机体转不过来，而不是操作不跟手。
- **可复用结论**：**重量感应来自状态转换的完整性，不来自输入延迟**。给策划的建议是：要重量，加 turnAccel / lerpRate / 后坐关键帧；**永远不要**用人为输入延迟做重量（那会产生迟滞感，玩家会归因为游戏卡 / 优化差）。

## 7. 正反馈与负反馈的对称性

| 对称设计 | 玩家输出（我打人） | 玩家输入（我被打） | 对称点 |
|---|---|---|---|
| 事件表 | PadRumble **9500 / 9501 / 9502**「格闘攻撃（当てた）小 / 中 / 大」 | PadRumble **9510**「格闘攻撃（食らった）」 | **打人有 3 档，挨打只有 1 档** —— 不对称：玩家的输出需要更细的分级，输入只需要知道挨打了。 |
| 镜头抖动 | AtkParam.playerToEneHitCamRumbleId = 9500 / 9501 / 9502（持 19 / 18 / 16 行） | AtkParam.cameraRumbleDefenseID（−1×704，仅 8 行用 10） | 同样是打人细、挨打粗。 |
| 顿帧 | 近战命中**攻击方**有 hitStopTime | **受击方**有 receiveDmgHitStopType = 1（全行） | **同一事件在攻守两侧各有一份配置** —— 这就是一致语言的实现方式。 |
| 冲击值 | AtkParam.impactPower / residualImpactPower | NpcParam.guardImpactCutRatePercent / justGuardImpactCutRatePercent / impactPaGuardCutRate / EquipParamProtector.stability | 攻击方给冲击力，防守方给削减率 + 安定性能。 |
| 部位材质 | 攻击方 atkType（攻击属性[SFX]） | 防守方 materialSfx1/2、materialSfx_Weak1/2、defenseMaterialSfx_Weak1/2 | **同一条 SFX 判定链两侧各有入口**。 |
| 阵营冲击修正 | SpEffectParam.atkPlayerImpactCorrectRate / atkEnemyImpactCorrectRate | SpEffectParam.defPlayerImpactCorrectRate / defEnemyImpactCorrectRate | 攻 / 守 × 玩家 / 敌 = 4 个修正倍率，**四象限对称**。 |

**四段式（对称性）**

- **设计意图**：玩家的打人和被打必须用同一套词汇（音色、节奏、优先级），否则玩家无法建立直觉。
- **实现手段（可观察）**：攻守两侧各有同名 / 同义字段（impactPower ↔ *ImpactCutRatePercent，atk*ImpactCorrectRate ↔ def*ImpactCorrectRate，cameraRumbleID ↔ cameraRumbleDefenseID）。
- **玩家体验 / 结果**：玩家能从声音 / 震动立刻判断是我打中还是我被打 —— 因为两者共用同一个材质与强度映射，只在**事件 ID 和时值**上分叉。
- **可复用结论**：**对称不是镜像参数，而是共享词汇表 + 不对称分级**。AC6 在打人上给 3 档（小 / 中 / 大），在挨打上给 1 档 —— 因为玩家对自己的输出需要精度，对承受的输入只需要存在感。这是很值得抄的一条。

**四段式（材质管线）**

- **设计意图**：让「打在什么上」听起来 / 看起来 / 震起来都对，而不需要美术 / 音频为每一对（武器 × 表面）手工做资源。
- **实现手段（可观察）**：用「攻击材质 × 防御材质」的概念对做中间层，再用「攻击姿态 × 大小」做输出矩阵，最后用 Wwise Switch 把数值索引翻译成中间件字符串。
- **玩家体验 / 结果**：打在盾上有能量盾音色（990902），打在 PA 上有白色波纹（990912），打装甲上（hitFEType = 2）HUD 给装甲样式。
- **可复用结论**：**任何多对多的反馈映射都应插入一个「概念 / 组合」中间表**。它把 O(N×M) 的资源配置压缩到 O(N+M)，也让「新增一种护盾」这样的需求变成加一行。这是 TA 最该学会的数据结构思维。

### 8.3 近战专属反馈：为什么近战爽而射击稳

AtkParam_Pc 里 HitRumbleId 与 cameraRumbleID **取值完全一致**，且规律极其清楚：

| 取值 | 行数 | 是谁 |
|---|---|---|
| **10** | HitRumbleId 27 行 / cameraRumbleID 28 行 | 全部是**弱攻击**（Laser Blade 弱、Dagger 弱、Beam naginata 弱、Plasma broadsword 弱、PA Breaker 弱、Explosive pile 弱、Chainsaw 强フィニッシュ、Electromagnetic baton 弱…） |
| **11** | 18 行 | 全部是**强攻击**（Dagger 强、Laser Lance 突進フィニッシュ、PA Breaker 强、Electromagnetic baton 强、Explosive pile 强①-1…） |
| 0 | 9 行 | wall slam damage、[Proto] Barrier / RECON / Flare / Smoke 等杂项 |

> **D 级**：cameraRumbleID = 10 / 11 的消费者未知。三种可能：① 指向表外的镜头抖动曲线资产；② 指向游戏内部硬编码的弱 / 强两档抖动；③ 废弃数据（本作改用 playerToEneHitCamRumbleId 走 PadRumble 的 9500 / 9501 / 9502）。**验证方法**：PC 版用弱 / 强近战各打一次，比较镜头抖动幅度是否只有两档；或反汇编搜索该字段的读取点。

## 9. 分析三问

### ① 如果删掉顿帧，玩家体验会怎么变？

**只在近战命中上删**（AC6 的现状已经给出答案的一半）：AC6 的枪械 / 导弹**本来就没有顿帧**，而它们的手感依然实。所以顿帧**不是反馈系统的地基，而是近战专属的咬合补丁**。

删掉后可以预测的变化（C 级）：

- 近战与射击的反馈语言差异消失 → 近战的重量差异主要靠 0.05 s 的三帧冻结来建立；失去它，近战会退化为「挥空了但敌人掉血了」。
- 顿帧同时是一次命中确认：0.05 s 的冻结让玩家看清刀确实碰到了。没有它，高速近战（QB 突进中斩击）的命中确认只能靠 HUD 与音效。
- 但**不建议在枪械上补顿帧**：机炮 10 发 / 秒 × 0.05 s 顿帧 = 50% 时间在冻结，会直接变成卡顿。AC6 用限流（§4.3）而不是顿帧来解决连射，是正确取舍。

**验证路径**：本机有完整的 AtkParam_Pc（712 行 × 1040 B），把这 45 行的 hitStopTime 置 0 做成 mod 即可对比 —— 这是成本最低、收益最直接的一次实验。

### ② 如果所有反馈通道的强度都拉满，会怎样？

必须**按通道拆**，因为每个通道「先坏在哪」不同。下表用实测数据的**上限**说明设计空间边界：

| 通道 | 拉满后的值（实测上限） | 先坏在哪 | 等级 |
|---|---|---|---|
| 顿帧时长 | 0.12 s（实测最大）→ 若 10× = **1.2 s** | 近战变成定格动画，输入响应被吃掉 72 帧；连击节奏完全崩溃 | B+C |
| 顿帧播放速率 | 1%（已接近 0）→ 再降无法更低 | 已经到底，说明设计者就是要看起来完全停住 | B |
| 镜头抖动寿命 | lifeTimeSec 上限 99 s（1 行）、常用 1–4 s → 10× = 10–40 s | 相机永远在震，玩家晕动症、无法瞄准 | B |
| 震动优先级 | priority = 255（已顶格） | 所有事件抢占同一通道，后到者永远打断前者 → 反馈失去层级 | B |
| 命中 SFX 并发 | HitInsDamageNearSfxNumMax = 1 → 10× = 10 | 音频削波 / 爆音，机炮变成白噪音 | B |
| 多段命中 SFX 间隔 | 0.2 s → ÷10 = **0.02 s** | 每 tick 都发声，音频引擎过载 | B |
| 伤害数字合并窗 | 0.5 s → 10× = 5 s | 数字卡住不动，反馈延迟感知明显 | B |
| 冲击条淡出 | 0.8 s → 10× = 8 s | 冲击条常亮，玩家无法分辨这一发涨了多少 | B |
| 自动瞄准补正角 | 180°（已有 14 发用满）→ 已是极限 | 180° = 子弹会朝反方向的目标飞 → 完全失控 | B |
| 近战自导转向率 | 1500 °/s，个别 32767（≈无限） | 近战变成自动追踪导弹，玩家失去走位意义 | B |

**结论**：AC6 的设计空间是**被明确封顶**的 —— 优先级 255 顶格、补正角 180° 顶格、顿帧 0.12 s 是最大值、SFX 并发 1 是最小值。**「拉满」不是调参失败，而是没有层级**。反馈系统的本质是**预算分配**：一个时刻只允许一个最强事件，其它降级。

### ③ 如果给玩家 0 延迟的完美反馈，会怎样？

AC6 反而在信息上做了**分级延迟**，而且这些延迟是刻意的：

| 信息 | 延迟 / 时值 | 设计理由 |
|---|---|---|
| 命中确认（HitFE） | 立即，持续 **1.0 s** | 必须即时，否则手感断裂。 |
| 被击警告（DangerFE） | 立即，持续 **2.0 s** | 比命中提示长一倍 —— 玩家在被击中时注意力被分散，需要更长的可见窗口。 |
| 伤害数字 | **合并 0.5 s** | 连射时累加后跳一次，而不是每发都跳。**这是故意延迟的典型**。 |
| 瞬时冲击条 | **0.8 s 后淡出、0.4 s 合并窗** | 让玩家看到这一波打进了多少，而不是逐帧跳动。 |
| 破防预警 | 冲击值到 **20%** 阈值即开始示警 | **提前量**：不是等破防了才告诉玩家，而是提前告知。 |
| 敌人警戒状态 | Search / Battle 图标各 **2 s** | 给玩家反应时间。 |
| 冲击无敌 | addImpactDisableTimeSec = **2.0 s**（EnemyCommonParam 实测 2.0；TentativePlayerParam 默认 2.5） | 从硬直状态出来后有约 2 秒不吃冲击值 —— 防止刚站起来又被踉跄的无限循环。 |
| 反无限连 | endPermanentStunStateValue = **1000** + AtkParam.addEndPermanentStunValue（0–1000，1000×19 行） | 累积到 1000 就ハメ抜け（脱离被连击锁定）。 |

**结论**：**「0 延迟完美反馈」的问题是它摧毁了信息分层**。玩家需要的是：哪些信息必须即时（命中 / 受击）、哪些必须聚合（数字 / 冲击条）、哪些必须提前（破防预警）。**延迟是实现分层的工具，不是缺陷**。反馈设计的三条时间规则：**确认要即时、累积要聚合、危险要提前**。

**有没有更简单的替代方案？**

- 替代 A：全局震动强度滑条 + 全局命中特效缩放。**为什么没用**：它会把武器差异、材质差异、部位差异全部抹平，AC6 的整个读战场能力会消失。
- 替代 B：统一的重反馈 + 长冷却。**为什么没用**：AC6 的事件密度太高（机炮 / 导弹 / 多锁 / PA / AB 同时发生），长冷却会导致大量事件被静默丢弃，玩家失去因果认知。
- 替代 C（AC6 实际选择）：事件表 + 通道分层 + 限流 + 优先级抢占。代价是必须有一份事件词典和一套工具链 —— 这恰好是 TA 的战场。

## 10. TA 转化

### 10.1 手感调参工具设计（给策划的实时面板）

**目标**：把 §8 的数据管线搬进编辑器，让调手感从「改表 + 重启 + 肉眼比对」变成「拖滑条 + 即时预览 + A/B 对照」。以下设计针对 **UE5 + 本机 regulation 数据**（本机已有完整 paramdex 字段定义与 257 张表的解析工具，见 §11）。

#### （1）数据接口

| 项 | 设计 |
|---|---|
| 数据源 | <WORKSPACE>/ac6_merge/van/regulation-bin/*.param（Souls LONGDATA 行格式：24 B 行头 + 行数据） |
| 读取 | 复用本机 tools/param_inspect.py 的 parse()：**走 didx 字段求 rowsize**（= didx[1] − didx[0]），并取 data 起点 = min(didx)。已验证 771 张中 768 张结构自洽 |
| 字段名 | 复用 tools/paramdex_fields.py：从 Paramdex/AC6/Defs/*.xml 取「字段名 + 字节偏移 + 类型 + 日文显示名」；枚举名从 Tdfs/*.tdf 取（shift_jis 解码） |
| 行语义 | 从 Paramdex/AC6/Developer Names/*.txt 取行名 —— **这是面板里最值钱的一列**，策划能直接看懂 9500 = 格闘攻撃（当てた）小 |
| 写回 | 按字段偏移原位写。**不要重建文件**（行头含 didx / noff，重建极易错位） |
| 版本管理 | 每次写回前 dump 一份 JSON 快照，改动以补丁 JSON 提交，而不是提交整个 .param |

**一个必须记住的坑（本机实测）**：不要用「文件大小 ÷ 行数」或「尾部类型名偏移 − 64 ÷ 行数」估算行宽 —— 两者都会把 24 字节行头算进去，每行虚高 24 字节。必须走 didx。

#### （2）面板结构（四区）

| 区 | 内容 | 交互 |
|---|---|---|
| **A. 事件矩阵区** | 行 = 事件（直接读 PadRumble 的 174 行开发者名，就是一份现成的事件词典）；列 = 10 个通道（顿帧 / 镜头抖动 / 粒子 / 音效 / UI / 动作中断 / 材质 / 震动 / 后处理 / 时间缩放）。格子显示该事件在该通道上的**驱动字段 + 当前值 + 是否为预定义网格** | 点格子 → 右侧属性栏；支持「按通道」和「按事件」两种转置视图 |
| **B. 通道预算区（本工具的核心差异化）** | 实时显示：① 当前 1 秒内触发的事件数；② 每个通道的并发占用（对照 GraphicsParam.HitInsDamageNearSfxNumMax / Dist）；③ 震动优先级冲突列表（哪些行 priority 相同、谁抢谁）；④ 时长审计（顿帧 >0.12 s / lifeTimeSec >4 s 的行高亮） | 红色阈值线可配置；点条目直接跳到源行 |
| **C. 曲线 / 网格编辑器** | 对「受网格约束」的通道（震动波形）只允许从 {强, 弱} × {30f, 90f, 40f, 20f, 10f} 的 10 格里选，禁止自由绘制；对「关键帧」通道（ShootReboundParam 的 10 组 boundKey）给帧-速率曲线编辑器 | 直接编辑 boundKeyN_boundFrame / boundKeyN_boundRate |
| **D. 管线可视化区** | 把 §8.2 的链路画成可点击的图：攻击属性 → 概念 ID → SfxId → Wwise Switch 字符串。选中一条链路能看到全链路的值 | 反向查询：给定一个 SfxId，高亮所有会产生它的（武器 × 表面）组合 |

#### （3）工作流（推荐）

1. **建基线**：加载 regulation → 导出全部相关表为 JSON → 记为 baseline。
2. **选事件**：在矩阵区点「近战命中 → 顿帧」→ 面板自动筛选出 AtkParam_Pc 里 hitStopTime ≠ 0 的 45 行（本工具应当内置这类「查询预设」）。
3. **改值**：滑条范围应**从数据推导**（例如顿帧滑条范围 = [0, 实测最大 0.12]×1.5，而不是 0–1 秒），避免策划调出设计空间外的值。
4. **热重载 + 即时预览**：写回 .param → 游戏侧监听文件变化 → 重载该表 → 在训练场立即复现。
5. **A/B 对照**：面板记录两次快照，支持「同一动作播 A / B 两版并排录制 + 逐帧对比」。
6. **提交**：导出补丁 JSON + 生成的对照视频，一起进版本库。

#### （4）三条设计原则（来自 AC6 数据的教训）

- **不要给自由滑条，要给受约束的选择**。AC6 里 51 个攻击共用同一个 DL 阶梯、10 个关卡事件共用同一组震动图案 —— 说明「少选项 + 高频复用」才是可控的手感。
- **面板必须显示预算**。手感的敌人不是「不够强」，是「信道饱和」。
- **面板必须显示优先级冲突**。priority 是抢占式的，两个 255 同时触发时谁赢是 undefined 行为 —— 工具应当提前报错。

## 14. 一页速查（面试 / 作品集可直接引用）

- **顿帧**：只给近战；45/712 行；0.05 s（3 帧）为主，最大 0.12 s；全局速率 1% → 近乎完全静止；受击方 1232/1232 全部开启；打装甲时可逐攻击关闭。
- **抖动同源**：PadRumble = CAMERA_RUMBLE_PARAM_ST（174 × 84 B）；一行同时定义镜头与该手柄震动；默认 lifeTime 1.0 s、priority 100；100 / 120 / 140 / 180 / 255 五档抢占。
- **波形池化**：约 98 个事件 → 约 20 个 rumbleId / 约 40 个 hdPadRumbleId；关卡事件用 {强, 弱} × {30, 90, 40, 20, 10}f 的 10 格网格。
- **瞄准辅助**：逐弹补正角锥（水平众数 15°、垂直众数 25°）+ 弹道自导（deg/s + 起始距离 / 时间 + 插值）+ 自身速度补偿（上下最多 100%）+ 近战突进自导（≤1500 km/h、≤1500 °/s、±42.7°）；软锁 450 m、瞄准 ×2、粘滞 1.5 s、击杀重锁 250 / 450 m。
- **输入**：缓冲 0.4 s、长按 0.4 s、多锁 0.5 s、超冲刺松手宽限 1.2 s、跑松手 0.1 s、走跑阈值 0.75、快转 0.2 / 180° / 0.2 s。
- **取消窗口**：32 个触发类型 × 20 个状态位的矩阵，不是帧区间。
- **混乱控制**：SFX 并发 1 / 50 m、多段 SFX 间隔 0.2 s、伤害数字合并 0.5 s、冲击条 0.8 s 淡出 / 0.4 s 合并、破防预警在 20%。
- **姿态**：冲击值 → 7 档阈值阶梯（逐敌人）→ 10 种 DL 阶梯（逐武器）→ DL2 顿帧 / DL3 小踉跄 / DL4 大踉跄 / DL5 吹飞；残余冲击 1.5 s 挥发；反无限连阈值 1000。
- **材质管线**：攻击属性 × 防御材质 → 概念对（64 行）→ 攻击姿态 × 大小矩阵（71 行 × 25 槽）→ SfxId → Wwise Switch 字符串（5 张映射表）。
- **重量 vs 迟滞**：AC6 从不延迟输入，只给响应曲线（转身加速 / 推进方向插值 / 相机插值 / 后坐关键帧）。
