# P5 · 装配（Assembly）与机体数值系统拆解

> 对象：《装甲核心6：境界天火》（ARMORED CORE VI FIRES OF RUBICON）
> 读者定位：大四学生，目标技术美术（TA），计划从策划岗入门
> 本报告所有"实测"结论均附本机执行的命令与原始输出片段（见 §1 与各节代码块）
> 证据分级：A=游戏内可观察/官方 · B=社区实测或 AC6 专用 paramdex 定义 + 本机复现 · C=合理推断 · D=不确定（附验证方法）

## 0. 结论先行（TL;DR）

1. **装配在 AC6 里不是"换装备"，而是"改运动学与资源预算"。** 12 个槽位里有 5 个（头/核心/手臂/腿/推进器）直接往角色运动参数表里写外键：`EquipParamProtector.legs_MovementParamId → MovementAcTypeParam.rid`、`legs_TurnParamId → ChrActTurnParam.rid`、`legs_boosterId → EquipParamBooster.rid`。换腿＝换一整套移动/转向/跳跃参数，而不是改几个数字。[B]
2. **存在三层约束，不是一层。** ①总重 vs `legs_payload`（腿载重上限，硬约束，**超了默认不能出击**）；②两个手臂武器的合计重量 vs `armMaxWeight`（腕部積載可能重量，**软约束**）；③EN 负荷 vs 发电机 `energyMax`。[B/实测]
3. **"超重不能出击"这条硬规则在数据里有直接证据**：`CharaInitParam` 里有一项 OS 强化字段 `osReinforceLevel_OverWeightOk`，其 DisplayName 是「OS強化レベル変更_**脚部積載重量過多出撃制限解除**」——即"解除腿部积载重量超多的出击限制"。对应 `OsReinforce` 表 rid=4010「Weight Control」，**1 级、3 点**。[B/实测]
4. **重量→性能是非线性的，但用的不是"指数曲线"，而是 5 段折线表**（`CalcCorrectGraph`，169 行 × 80 字节）。同一张表里有两套彼此独立的修正：**总重修正**（输入＝总重 kg，行 260–283）与**超重修正**（输入＝载重比 %，行 290–297）。超重修正只在解放出击限制后才可能触发。[B/实测]
5. **推进器之外还有一层"效率乘数"**：核心提供 `quickBoosterOutputCorrRate`（76–126%）、`generatorOutputCorrRate`（83–126%）、`generatorCoolPerf`（70–112%）。换核心不等于换 AP，而是在缩放推进器和发电机的输出。[B/实测]
6. **自动配装的评价函数完全数据驱动**：`AutoAssembleEvaluate` 20 行 × 16 字节 = 5 组预设，每行只有两个字段（`propertyID` + `weight`）。方向（越大越好/越小越好）来自 `MenuPropertySpecParam.CompareType`（0=----、1=large、2=small）。这是一套可以直接抄的"可配置评分器"。[B/实测]
7. **OS 强化 20 项 = 5 攻 + 4 防 + 6 机动 + 5 系统**，点数只来自竞技场解锁（`OsReinforcePoint` 41 行合计 **197 点**），而全点满需要 **287 点** → 结构性取舍，不是"全解锁"。[B/实测]
8. **腿决定的不只是载重**：落地刹车倍率（0.9/1.0/1.2/1.3）、射击反動滑退倍率（坦克 0.0–0.3，四足空中 0.3）、QB 追加初速（逆関節 317–386 km/h）、跳跃高度（坦克 2 m，逆関節 30–80 m）。**射击反動倍率是"坦克/四足能不能站桩输出"的开关**。[B/实测]
9. **只有 3 条腿内置推进器**（`legs_boosterId = 63300000/63340000/63360000`，正好是 3 条坦克腿），对应 `EquipParamBooster` 里 3 行 weight=0 的 "TANK BUILT-IN"。[B/实测]
10. **扩展槽（Expansion）不是免费的**：4 个扩展件（Assault Armor / Pulse Armor / Pulse Protection / Terminal Armor）在 `EquipParamWeapon` 里 `assembleMenuCategory = 7`，weight=0、EN 负荷=0——它们不占重量与 EN，**唯一的成本是 OS 点数**。[B/实测]

## 4. 非线性：`CalcCorrectGraph` 到底怎么用

### 4.1 表结构与插值模型（实测）

`CalcCorrectGraph` 169 行 × 80 字节，字段（paramdex）：

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0–19 | `stageMaxVal0..4` (f32×5) | **5 个断点的输入值** |
| 20–39 | `stageMaxGrowVal0..4` (f32×5) | **每个断点处的输出倍率** |
| 40–59 | `adjPt_maxGrowVal0..4` (f32×5) | 调整系数（AC6 相关行实测全为 1） |
| 60–75 | `init_inclination_soul` / `adjustment_value` / `boundry_inclination_soul` / `boundry_value` | 魂系成长曲线参数，**AC6 相关行实测全为 0** |

**模型的可靠结论**：AC6 的移动/机动修正只用 **5 段折线**（断点 + 断点倍率），段内线性插值，超出最后断点取末值（末值即"下限"）。`adjPt_maxGrowVal` 与 four soul 字段全 0，说明这套曲线是"移植的容器、只用了前半部分"。[B/实测]
**不确定的部分（D）**：段内是线性插值还是别的插值、超界是否真的 clamp，需要逆游戏或逐点实验确认。

**关键观察（三条都改变了设计理解）**：

1. **它是"递减但很缓"的。** 总重 40000→120000 kg（3 倍），地面推进速度只掉到 65%。也就是说：**重量对速度的惩罚远小于直觉**，AC6 用"载重上限"而不是"速度滑落"来限制超重。这是典型的"把约束做成门，而不是做成斜坡"。[C]
2. **断点不均匀**：260 的断点是 40000 / 62500 / 75000 / 80000 / 120000。第二个断点（62500）之后有一段很短（62500→75000）却掉了 7.5%，然后 75000→80000 只掉 7.5%，再到 120000 掉 12.5%。**"中段陡、后段缓"** —— 在设计上意味着"中量级机体的每一公斤都比超重机体更贵"。[C]
3. **坦克有独立曲线（224–227）**，且它的斜率更缓（末值 0.6 vs 0.65）。坦克的转向/漂移参数由 `MovementAcTypeParam` rid 300/310/320 与 `ChrActTurnParam` rid 13000000+ 单独给出。[B/实测]

**用真实部件验证（`_p5_build.py`）**：一套 NACHTREIHER 轻量二足（总重 55730 kg）落在 40000–62500 段，地面推进速度修正 ≈ **0.948**；一套 BORNEMISSZA 重坦克（143650 kg）落在末段，地面推进 ≈ **0.650**。也就是说"最重配装只损失 35% 推进速度"，但"最重配装根本装不进去"（见下）。[B/实测]

### 4.5 回答任务书的原始问题

> **"重量对性能的影响是线性的吗？有没有阈值/断点？收益曲线是递增还是递减？"**

- **不是线性的**，而且**不是一条曲线，是两条串联的曲线 + 一条独立的臂载重曲线**。
- **有断点**：总重曲线断点 40000 / 62500 / 75000 / 80000 / 120000 kg；超重曲线断点 100% / 105% / 110% / 130% / 150%；臂载重曲线断点 0 / 5000 / 10000 / 30000 / 50000 kg。
- **递减，但整段很平**（3 倍重量只掉 35% 速度）；**"更重"的收益在曲线 280/281 上是递增的**（踢击伤害 ×2、未知重量加成 ×1.25）——**这是"重有重的好处"的正反馈设计**，不只是惩罚。[B/实测]

## 8. 自动配装：评价函数怎么设计

### 8.1 表结构（实测）

`AutoAssembleEvaluate.param` 20 行 × 16 字节，paramdex 名为 `AssemEvaluateParam`（同名表在 regulation 里叫 `AutoAssembleEvaluate`）。字段只有两个：

| 偏移 | 类型 | 字段 | 含义 |
|---|---|---|---|
| 0 | s32 | `propertyID` | **指向 `MenuPropertySpecParam` 的条目 ID**（即"要评分的数值"） |
| 4 | f32 | `weight` | 该数值在评分里的权重 |

### 8.2 五组预设（逐行实测）

| 组 | rid | propertyID | 对应 UI 数值 | weight | 优劣方向（CompareType） |
|---|---|---|---|---|---|
| A | 0 | 0 | （占位/空行） | 1.000 | — |

| A | 13 | 3012 | 耐TE装甲 | 0.100 | 1=large |
| B | 20 | 3000 | AP | 0.300 | 1 |
| B | 21 | 3010 | 耐KE装甲 | **1.000** | 1 |
| C | 30 | 3000 | AP | 0.300 | 1 |
| C | 31 | 3011 | 耐CE装甲 | **1.000** | 1 |
| D | 40 | 3000 | AP | 0.300 | 1 |
| D | 41 | 3012 | 耐TE装甲 | **1.000** | 1 |
| E | 50 | 103 | 重量 | 1.000 | **2=small** |

**结论**：`AutoAssembleEvaluate` 定义的是 **5 套"体质"预设**——A=全防御均衡（AP 权重 1.0，三抗各 0.1）、B/C/D=针对单一伤害类型的抗性特化（该抗性 1.0 + AP 0.3）、E=综合机动（重量/EN/QB/冷却/跳跃/推进效率）。

**评价函数（推断 C，但有充分依据）**：
```
score(build, preset) = Σ_i  weight_i × normalize_i( property_i(build), direction_i )
```
- `direction_i` 来自 `MenuPropertySpecParam.CompareType`（实测：0=----、1=large、2=small；例如 103 Weight=2、3706 QB リロード=2、3000 AP=1）。
- `normalize_i` 的分母（各数值的 min/max 区间）**不在表里**，必须在代码里硬编码或由全装备池动态计算 → 这是唯一没做成数据驱动的一环。

### 8.3 对新手意味着什么（四段式）

- **设计意图**：把"我不懂这 30 个数字"变成"从 5 个体质里挑一个，然后按一个按钮"。
- **实现手段**：表驱动评分 + 5 套预设 + 全身部件穷举（部件池：头 24 + 核 19 + 臂 20 + 腿 25 + 推进器 13 + FCS 10 + 发电机 15 + 武器 ~130，暴力穷举约 10^13 组合，实际必然用了剪枝或分部件贪心 —— **推断 C**）。
- **玩家体验**：新手能立刻拿到"过得去"的机体，但仍需要手动微调武器（因为预设 E 里没有武器项，`propertyID` 列表完全不含武器攻击力）。
- **可复用结论**：**"评分表 + 方向来自被评分对象的定义"是一种非常省事的做法**——新增一个可评分数值不需要改评分器，只需要在 `MenuPropertySpecParam` 里加一行并指定 CompareType。这正是数据驱动 UI 的教科书式应用。

## 9. 装配即难度：为什么 AC6 不用难度选项

| 维度 | 传统难度选项 | AC6 的"配装即难度" |
|---|---|---|
| 调节对象 | 敌人 HP/伤害倍率 | 玩家自己的十三个数值轴 |
| 调节时机 | 开局一次性 | 每次死亡后的装配界面（**随时、零成本**） |
| 反馈速度 | 慢（要重打一遍才知道） | 快（装配界面直接显示三层约束条） |
| 玩家学到什么 | "我要更小心" | "我的伤害类型不对 / 我的 EN 不够 / 我超重了" |
| 数值实现 | 全局倍率表 | `CalcCorrectGraph` 非线性 + 三层约束 |
| 数据证据 | — | `Assembly` 的预算条驱动全部决策；`AutoAssembleEvaluate` 提供"保底解" |

**"卡关"的解法从操作转向了什么？** 转向 **伤害类型匹配 + 资源预算**：

1. **伤害类型匹配**：三条伤害通道（KE/CE/TE）× 四种属性（实弹/EN/爆炸/珊瑚）——你的武器属性 vs Boss 的抗性分布。数据上这由 `defensePhysics/Magic/Fire/Thunder` 与武器的 `attackBase*` 决定，不需要改难度。
2. **资源预算**：EN 负荷决定你能不能持续开火/机动；载重决定你能带多重的东西；臂载重决定你能不能双持重武器。
3. **机动力与稳定性取舍**：逆関節提升跳跃但牺牲稳定；坦克提升载重与抗反動但失去跳跃。

**为什么不做难度选项？** 因为**配装本身就是一个连续可调的难度旋钮，而且它同时是游戏的表达载体**（你在装配界面的每一次取舍都是"我是什么风格的佣兵"的声明）。给一个全局难度倍率反而会**让装配系统失去意义**——这是 AC 系列从 1997 年起就确立的身份。[C]

## 10. 分析三问

### ① 如果没有重量限制会怎样？

- **立即后果**：所有"重"部件（BORNEMISSZA 49800 kg 腿 + VE-60LCA 14820×2）变成无成本选择，**轻量部件彻底失去存在理由**（因为轻量件在 AP/抗性上更差）。
- **数据上的证据**：曲线 260–283 的惩罚非常缓（3 倍重量只掉 35% 速度），也就是说**重量本身几乎不构成约束**——真正构成约束的是 `legs_payload` 这个"门"。删掉重量限制等于删掉整条腿的取舍轴。
- **更根本的**：`legs_payload` 是**腿与武器之间的唯一耦合**。删掉它，腿部选择就退化为"选 AP 最高的那条"。
- **结论**：重量限制不是"惩罚机制"，而是**组合空间的划分器**——它决定了"哪些武器和哪些腿能同时存在"。

### ② 如果部件不能互换（固定机体）会怎样？

- **立即后果**：游戏变成"用固定机体打固定 Boss"的动作游戏，`AutoAssembleEvaluate`、`EquipmentLineupParam`、`ShopLineupParam`、`PartsTokenParam`、`OsReinforce` 五张表全部作废。
- **数值上的损失**：核心的 3 个效率乘数（QB 传递/发电机传递/冷却）之所以存在，就是因为核心要和**别的部件**做乘法。固定机体系列里这些字段毫无意义。
- **可验证的替代品**：AC6 的**竞技场（Arena）**其实是"固定机体"的对照组——41 个对手各自是一套固定配装，玩家用可变配装去打。这恰好证明：**固定机体的乐趣来自"读对手的破绽"，可变机体的乐趣来自"造工具"**。
- **结论**：模块化不是"内容量"，而是**难度调节的手段本身**。

### ③ 如果所有部件数值都是线性叠加会怎样？

- **立即后果**：`CalcCorrectGraph` 的 169 行中，约 60 余行 AC6 相关曲线全部退化为 1.0 倍率。
- **设计上的损失**：
  - 曲线 292（超重时 QB 时长 → 0）这类**断崖**消失 → "超重"不再是一种状态，只是"慢一点"。
  - 曲线 260 的**中段陡、后段缓**消失 → 中量级机体失去"每公斤更贵"的特性。
  - 曲线 280/281（重 → 踢击伤害 ×2）消失 → 少了一条"重有重的好"的正反馈。
- **最关键的损失**：**线性叠加下没有"阈值"和"状态"**。AC6 的设计大量依赖"过线才发生"（过 100% 载重 → 不能出击；过 EN 出力 → 不回复；过臂载重 → QB 恢复变慢）。线性系统只能产生"更多/更少"，产生不了"能/不能"。
- **反例（本作里确实存在线性部分）**：AP、三抗、重量、EN 负荷**都是简单求和**。也就是说 AC6 的做法是：**"预算"用线性求和（好懂、好算、好做 UI），"后果"用曲线（有手感、有断崖）**。这个分工非常值得抄。[C]

| `retargetModelId` | Protector @402 s16 | 二足 0 · 逆関節/四足 −1 · 坦克 300 | **重定向源角色 ID**（「脚部専用_リターゲット元にするキャラID」） |
| `legAnimCategoryOffset` | Protector @435 u8 | 大多数 0，LAMMERGEIER/42F = 1 | 「脚によるアニメオフセットID（a0X0_000000のID）」——**动画集偏移** |
| `coreTypeWepAnimOffset` | Protector @836 u8 | 「コアによる武器アニメオフセットID」 | **核心也会改武器动画**（不同核心的武器持握姿态不同） |
| `walkAnimSpeedRate` / `runAnimSpeedRate` | Protector @840/844 f32 | 0.90 / 0.95 / 1.00 / 1.10 | **按腿长缩放动画播放速度**，保证脚不打滑 |
| `isHeavyWeightAddAnim` (bit0) | Protector @835 u8 | 手臂 20/20 = 1；腿 5/26 = 1（TIAN-QIANG、VE-42A、VERRILL、VP-424、LAMMERGEIER/42F）；头/核全 0 | 「【腕・脚専用】重量級加算アニメ判定対象か」——重量级姿态的加算动画开关 |

**TA 要理解的做法**：FromSoft 没有为每条腿做一套动画，而是**用"动画集 ID + 播放速率 + 重定向源"三个 ID 把 25 条腿压缩到少数几套共享动画**。这是典型的 **Animation Blueprint + Retarget + Play Rate 驱动**。落地到自己项目上：

1. 用 **UE5 IK Retargeter**（或 Unity Humanoid）建立一份"标准骨架"，所有腿部件共用同一套 `walk / run / boost / land / qb` 动画，靠 `walkAnimSpeedRate` 调整播放速率来补偿腿长差。
2. **脚部接触必须做 IK**——数据侧的证据是本作存在 `FootIKParam`（68 行 × 64 B）与 `FootIKSetupParam`，手部同理有 `HandIKParam`（47 行 × 64 B）。**不要用纯 FK 做不同腿长的落地**，否则不同腿型在同一条动画下脚会悬空或插入地面。
3. `retargetModelId` 的思路值得直接抄：**给每个"骨架变体"一个 ID，部件只引用 ID**，而不是把动画硬绑到部件上。

### 11.2 挂点 socket 规范

AC6 的挂点系统有一张**专门的 VFX/挂点表**：`ThrustersParam_PC`（103 行 × 700 B）。字段命名直接暴露了挂点清单：

```
main / subFront / subBack / subLeft / subRight
qbFront / qbBack / qbLeft / qbRight
lift                        ← 上升喷嘴
tankFront / tankBack / tankDriftLeft / tankDriftRight      ← 坦克专用
quickTurnLeft / quickTurnRight                             ← 快速转身
assaultBoost                                               ← 突击推进
```

每个挂点有一组：`_SFXID`（s32）、`_SlotNO`（s16，管理槽位号）、`_Scale`（f32）、以及位域 `useRPCType:1 / IsHorizontal:1 / IsFollowDmyPoly:1 / IsEraseActionEnd:1 / camouFlageShow:1 / DoPlaySFXForTankLeg:1`。

**关键设计点**：

- `IsFollowDmyPoly:1` = **是否跟随 dummy poly**——即特效挂在"骨骼上的一个 dummy 位置"还是"部件空间固定点"。这正是 socket vs. bone-attach 的开关，而且是**数据驱动**的。
- `DoPlaySFXForTankLeg:1` = **同一套参数在坦克腿上要不要播**——一条位域解决了"坦克腿的喷嘴布局完全不同"的分类问题。
- `IsEraseActionEnd:1` = 动作结束时是否删除特效——生命周期也进数据。
- `camouFlageShow:1` = 隐身时是否隐藏——**同一个挂点要响应游戏状态**。

**部件如何引用挂点**（实测）：

```
CORE BD-011 MELANDER      thrustersParamIDForPC = 37100
CORE 07-061 MIND ALPHA    thrustersParamIDForPC = 60100
CORE IB-C03C: HAL 826     thrustersParamIDForPC = 80100
ARMS AR-011 MELANDER      thrustersParamIDForPC = 37200
LEGS LG-011 MELANDER      thrustersParamIDForPC = 37300
LEGS VE-42A               thrustersParamIDForPC = 50100
BOOSTER (全部玩家件)       thrustersParamIDForPC = 10
```

**即：每个槽位的部件各自引用一个挂点配置行；核心负责"机体上的辅助喷嘴"（不同核心给出 37100 / 60100 / 80100 三档），手臂/腿各有自己的（37200 / 37300 / 50100），推进器统一用 10。** 这套"每槽位一份挂点配置 + 位域开关"的规范，就是"任意组合不出错"的核心工具。[B/实测]

**还有两个细节字段值得抄**：

- `backunitAjustHeight`（Protector @860 f32）「肩武器装備時のスライド量[m]」——**装肩武器时整机滑移量**，用来避免肩武器和头部/核心视觉冲突。无值时为 0。
- `DecalCamDistOffset`（Protector @564 f32）「デカール貼り付け時のカメラ距離オフセット」——贴花工具在不同部件上自动调整相机距离。**"工具相机随资产尺寸自适应"的现成范例**。

### 11.3 材质实例与涂装遮罩

| 数据 | 位置 | 实测 | TA 用途 |
|---|---|---|---|
| `materialSetId` | Protector @52 s32 | 每部件一个 | **材质集 ID** → 指向 `EquipMtrlSetParam`（实测 28 行 × 52 B） |
| `EquipMtrlSetParam` | 独立表 | 28 行 | 材质/涂装槽定义（每个部件声明自己能涂几块、哪些影响） |
| `AssetMaterialSfxParam` | 独立表 | 44 行 × 128 B | **材质 → 音效映射**（不同材质被打中的音效不同） |

### 11.4 装配预览相机与打光

真实证据：

| 表 | 实测 | 用途 |
|---|---|---|
| `GarageCameraAnimParam` | 7 行 × 196 B | 装配库（Garage）里的相机动画 |
| `GarageCutsceneParam` | 3 行 × 80 B | 出撃/装配过场的镜头 |
| `DirectionCameraParam` | 存在 | 方向性镜头 |
| `DecalCamDistOffset`（Protector @564） | 每部件不同 | 贴花工具相机距离 |
| `cutsceneCamOffset`（Protector @864 f32） | 「汎用出撃_カメラオフセット[m]」 | **部件影响通用出击镜头** |

**TA 要点**：AC6 的装配预览是 **"相机动画 + 部件级偏移"**，而不是"一个固定角度看所有机体"。因为**机体尺寸跨度极大**（腿从 11200 kg 到 49800 kg，高度差可能 2 倍以上），固定机位必然导致轻量机体在画面里很小。落地做法：

1. 相机用**包围盒自适应**（`GetComponentsBoundingBox` → 按半径调整距离），而不是硬编码距离。
2. 打光用**三点光 + HDRI**，但**推进器/发光件要单独一层**（AC6 里 EN 武器和推进器焰是自发光，装配界面里需要有对应的高光/泛光表现）。
3. **部件级相机偏移字段保留**（`cutsceneCamOffset`、`DecalCamDistOffset` 的思路），应对"肩武器特别宽/头部特别高"的个例。

### 11.5 部件 LOD 与绘制预算

| 数据 | 实测 | 说明 |
|---|---|---|
| `PartsDrawParam` / `_ps4` / `_ps5` / `_xb1` / `_scarlett` | 各 **152 行 × 144 B**，内部类型名都是 `PARTS_DRAW_PARAM_ST` | **同一份绘制参数、五个平台变体** |
| `AssetGeometryParam` | 存在 | 部件几何资产参数 |
| `ChrModelParam` | 62 行 × 12 B | 角色模型对应表 |

**TA 要点**：**"部件的绘制参数按平台分表"**（`PartsDrawParam` 系列 5 张表同结构、同内部类型名），意味着基座主机上的部件剔除/阴影/材质质量是被独立配置的。自己项目里对应的做法：

1. 每个部件 prefab 带一份 `PartsDrawParam` 式的绘制配置（cast shadow / 距离剔除 / LOD bias）。
2. **12 槽位同时在场 = 至少要保证 12 个 SkinnedMesh 的合并或 ISM 化**。AC6 是单机体，但敌方 AC（`EquipParamWeapon_NPC`、`NpcEquipPartsParam` 都存在）可能同时出现多台 → **必须做部件级 GPU instancing 或合并**（同款 MELANDER 腿在场景里出现 3 次时应共享绘制）。
3. `PartsDrawParam` 有 152 行、而部件总数远超 152 → **绘制参数是"共享档位"，不是"每部件一份"**。这也是必须抄的做法：不要让美术给每个部件单独配 LOD。[B/C]

### 11.6 数据驱动的装配 UI（可直接抄的结构）

AC6 的装配界面之所以能显示几十行数值而不用为每行写代码，是因为三层拆分：

```
第 1 层  参数表         EquipParamWeapon / Protector / Booster / Generator / Fcs
第 2 层  取值规格       MenuPropertySpecParam (508 行 × 108 B)
         - extract0/1_Target      : 从哪张表取（Weapon/Armor/booster/FCS/generator）
         - extract0/1_MemberType  : 按什么类型读（s8/u8/s16/u16/s32/u32/f32）
         - extract0/1_MemberTailOffset : 尾部偏移（必须减 sizeof）
         - extract0/1_Operation   : 0=直读 / 1=C0*Para+C1 / 2=C0/Para+C1
         - extract0/1_Constant0/1 : 单位换算常数
         - CompareType            : 0=---- / 1=large / 2=small
         - FormatType / IconID / CaptionTextID / HelpTextID
第 3 层  显示缓存       computed_f00..computed_f_last（【表示用】Float_XX）
```

**单位换算常数就藏在 Constant 里**（实测）：

| 显示项 | 常数 | 换算 |
|---|---|---|
| 巡航推力（3700） | ×16.67 | m/s → km/h |
| QB 喷射时间（3704） | ×0.033 | 1/30 秒 → 秒 |
| 冷却性能（3502/3503） | 1000 / 值 | 秒 → "性能分"（**倒数，越大越好**） |
| 导弹锁定性能（3600） | −100×值 + 200 | 时间系数 → 0–100 性能分（**反向线性**） |
| EN 武器适性（3505） | ×1000 | 内部整数 → 展示值 |
| 格斗适性（3303） | 直读 u32 | 无换算 |

**"倒数"和"反向线性"两种非线性映射在 UI 层解决**，游戏逻辑仍用原始物理量——这是让"数值是给机器读的、显示是给人读的"分离的经典手法。[B/实测]

## 12. 四段式小结：装配系统的四条可复用结论

1. **设计意图**：让玩家用"造工具"代替"练技术"来解决卡关。
   **实现手段**：12 槽位 + 三层约束（硬门 + 软门 + 资源门）+ 5 段折线后果曲线 + 数据驱动 UI。
   **玩家体验**：每次死亡后回到装配界面，试错成本接近 0。
   **可复用**：预算用线性求和，后果用折线；把"能/不能"的单点门槛单独抽出来（本例的 `legs_payload`）。

2. **设计意图**：让"重"有代价也有好处（不是单纯惩罚）。
   **实现手段**：曲线 260–283 缓降（速度）× 曲线 280/281 上升（踢击伤害 ×2、重量加成 ×1.25）× 曲线 290–297 断崖（超重时 QB 失效）。
   **玩家体验**：明显感觉"越重越像坦克，直到某条线之后彻底变残废"。
   **可复用**：**惩罚曲线要缓，门槛要硬**。缓的惩罚提供手感，硬的门槛提供决策。

3. **设计意图**：让"部件数量"远小于"行为数量"，降低维护成本。
   **实现手段**：25 条腿 → 8 个 `MovementAcTypeParam` + 6 个 `ChrActTurnParam` 元型；部件的差异用几十个 f32 表达。
   **玩家体验**：换腿像是换了一台机器（因为确实换了一整套参数）。
   **可复用**：**行为模板 + 参数包**（Template + Data Asset）。这是 TA/策划协作的标准接口。

4. **设计意图**：让数值可以被玩家读懂。
   **实现手段**：`MenuPropertySpecParam` 的 extract 规格 + 单位换算常数 + 显示缓存字段。
   **玩家体验**：装配界面每一行都能对上"它能干什么"。
   **可复用**：**UI 不自己算，只读"已算好的显示字段"**。这在工程上把"计算"和"展示"解耦，代价是需要一层回写。
