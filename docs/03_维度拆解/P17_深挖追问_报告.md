## 1. 下钻 a：「机甲不是放大的人」（5.1 节）

### 1.1 第一层：它具体指哪个系统、哪个参数、哪个时间点

原文只给了四条形容词式对照（转向/加速/空中/重量感）。下钻后，**这句话至少对应 5 个具名系统**，且每个都绑定到一个可读的参数和一个具体的时间点：

| 系统 | 参数（本机字段名） | 所在表 | 实测值 | 它描述的是「哪个时刻」 |
|---|---|---|---|---|
| 转向 | `baseTurnSpeedDPS` / `turnAccelDPSS` | `ChrActTurnParam` (258×168B) | 160 行 = 360 / 9999999；坦克 3 行 = 230/230、320/350、400/450 | 玩家推杆后**转向建立的那一瞬**：多数腿是"瞬到速度"，坦克腿是"慢慢爬" |
| 脚部接地 | `raycastDistanceUp/Down`、`ankleRotationGain` | `FootIKSetupParam`(86×132B) / `FootIKParam`(68×64B) | 射线 2.6~35 m（中位 5.0/7.7）；踝关节增益 {0.15,0.25,0.3,0.5}，中位 0.25 | **踩上坡道的那 1 帧**：脚掌只跟随 15%~50% 的坡度 |
| 二次运动 | `minAccelMPSS`/`maxAccelMPSS`、`moveAccelScaleX`、`rotDecayValueX` | `JigglerBehaviorParam`(49×64B) / `JigglerBehaviorSlideParam`(33×80B) | 死区 50、饱和 300 m/s²；位移力去零中位 360（max 580）；阻尼去零中位 5 | **一次急加速/急停后的 0~1 秒**：零件被"甩"出去再弹回 |
| 输入响应 | `boostDirLerpRate`/`counterBoostDirLerpRate` | `BoostParam`(2×128B) | 0.10 / 0.17（Rate/Frame），反向推进生效角 90° | **按下推进后的第 1~22 帧**：方向以每帧 10% 收敛（90% 收敛 ≈ 22 帧） |
| 重力 | `MovementGravity` / `FallMaxSpeedKMH` | `TentativePlayerParam`(2×2112B) | **120 m/s²** / **2160 km/h** | **关掉推进器之后的整个下坠过程** |
| 位移量修正 | `charaWeightMin/Max`、`moveMin/Max` | `AnimMoveCorrectionParam`(22×64B) | 权重窗 [8650, 27000]；位移 [35,60]（19 行）与 [60,110]（2 行） | **动画位移被按重量插值的那一刻**（即"重装机步子迈不开"） |

**这一层的验证方法（我怎么知道说的是对的？）**
1. 命令：`python tools/paramdex_fields.py <表名>` 拿字段名/偏移/类型 + 自写脚本按偏移取值（脚本 `_scratch/p17_A.py`，输出见 1.4）。
2. 结构自洽校验：6 张表**全部 SIZE MATCH**（86×132、68×64、258×168、2×128、2×2112、22×64、351×164、49×64、33×80），行宽与 paramdex 声明字节数一致 ⇒ 偏移可信。
3. **反证**：我原以为 `FootIKSetupParam.originalGroundHeightMS`（"原点→地面高度[m]"）能当腿长，实测 **86/86 行全为 0** ⇒ 该字段未使用，**不能当尺度基准**（这就是"看起来最像那么回事的字段其实是死的"）。

### 1.2 第二层：它是怎么实现的

**(1) 转向：数据层把"转动惯量"这一项删掉了。**
`ChrActTurnParam` 258 行里 **159 行 `turnAccelDPSS` = 9999999**（引擎里等效无限大）。

物理上，等比放大的物体转动惯量 I ∝ m·L²，同比例角推力下角加速度 ∝ 1/L²；放大 5.56 倍应使角加速度掉到 **3%**。AC6 的做法是**反过来把它设成无穷**——即"重量感"不由动力学产生，而由**同时存在的另一个量**（`baseTurnSpeedDPS` 低上限）产生。坦克腿是唯一例外（230/350/450 的真实角加速度 + `reverseTurnBrake` 250/580/1600），所以"坦克像开船"。

**(2) 二次运动：驱动量是**加速度**，不是速度/位移。**
`JigglerBehaviorParam` 的 4 个驱动字段（`minAccelMPSS`/`maxAccelMPSS`/`minSpeedKMH`/`maxSpeedKMH`）构成一个"死区 + 线性区 + 饱和"的映射；`JigglerBaseParam` 351 行把 **327 个唯一骨骼名**绑到这些行为参数上，并额外提供**角度硬限位**（`limitAngleDeg_MinX/MaxX`, s8）与**位置硬限位**（`limitOffset_MinX/MaxX`, f32）以及**限位反弹率**。资源流向：

```
骨骼名(351 行, 327 唯一) --behaviorParamId--> JigglerBehaviorParam(49)   [旋转解算]
                        --behaviorSlideParamId--> JigglerBehaviorSlideParam(33) [平移解算]
机体加速度向量 ---> 死区(50) --> 线性 --> 饱和(300) --> 力/力矩 --> 限位(--> 反弹 0.01~1.0)
```
**注意两个硬限位的真实分布**：`limitAngleDeg_MinX` **160/351 行是 0**（不晃）、中位 −2°，只有 **2 行**是 −45°；`limitOffset_MinX/MaxX` 的 ±2.0 m 只出现在 37/24 行里。也就是说"±45° / ±2 m"是**极端值，不是常态**（主文档 5.8.4 的写法会让人误以为是通用配置）。

**(3) 重力：120 m/s² 不是"放大的人"该有的数。**
用 A 级观察取尺度因子 S ≈ 10 m / 1.8 m = 5.56：
* 「等比放大 + 时间尺度不变」预测 g = 9.8 m/s²（不变）→ 实测 120 = **12.2 倍**；
* 「动态相似（Froude）」预测 g = 9.8·S = 54.4 m/s² → 实测 120 = 预测的 **2.20 倍**；
* 同一高度 10 m 落地：机甲 **0.408 s**，放大的人 **1.429 s**（差 **3.50 倍**）；
* 下落终速 2160 km/h = **600 m/s**，是人形跳伞终速（≈55 m/s，D 级）的 **10.9 倍**——即**刻意不设上限**。

**(4) 位移量修正：一张只有 21 条有效行的表，定义了"重装机步子迈不开"。**
`AnimMoveCorrectionParam` 22 行中 21 行有效（rid 0 是空行），权重窗口**全表统一** [8650, 27000] kg，位移 [35,60]（19 行）/ [60,110]（2 行，animId 26800/26810），`calcGraphParamId` 全 = 20，`charaId` = 1。线性插值斜率 = (60−35)/(27000−8650) = **每 1000 kg 约 1.36 单位位移**。
**▶ 我怎么知道这一层是对的？** ① 表结构校验：22 行 × 64 B 与 paramdex 声明一致（SIZE MATCH），字段偏移可直接用；② charaWeightMin/Max 的 21 个有效行**共用同一个权重窗口**（[8650,27000]，唯一值 2 个），说明这是「整机·按重量」的一条全局修正，而不是逐动画配置——若某行权重窗口不同，「按重量插值」的解释就要推翻；③ 证伪实验：游戏里把机体重量配到 8650 以下与 27000 以上各录一次同一条移动动画，量位移是否卡在 35 与 60 两端（不随重量继续变化）。

**程序要实现的 5 个状态点（按帧序）**
1. **t0 起步帧**：目标方向以 `lerp = 1-(1-rate)^n` 收敛（rate=0.1/帧 ⇒ 90% 用 22 帧）。
2. **t0 同帧**：模型弹簧把 mesh 相对逻辑位置偏移，上限 +1.5 m / −3.0 m，插值 0.9。
3. **t1 转向建立**：若 `turnAccelDPSS ≥ 1e6` ⇒ 直接给角速度；否则按角加速度积分（坦克分支）。
4. **t2 接地帧**：射线（上 5 m / 下 7.7 m）→ 踝关节角 = 坡度角 × `ankleRotationGain`(0.25)；抬脚增益 0.10 / 落地增益 0.50 分开。
5. **t3 每帧**：加速度模长 → clamp 到 [50,300] 归一化 → 驱动 Jiggler 的 rot/move 两个求解器 → 限位 → 反弹。

**TA 能调试的（这一条是 a 对 TA 最值钱的部分）**
* 3 个 Debug Draw：FootIK 射线、踝关节目标角 vs 实际角、Jiggler 的加速度输入与力输出；
* 一张"通道开关表"：把 8 条重量感通道（加算动画 / 两段加速度 / 伺服延迟 / Jiggler / 模型弹簧 / 落地刹车分档 / 音效 / 姿态倾斜）做成可单独关闭的开关，用于 A/B；
* 一个参数面板（对应主文档 4.4）：把上表 14 个字段直接暴露。
**▶ 我怎么知道这一层是对的？** 这层的每个字段都来自 B 级实测（见 1.4 原始输出），但「该给什么起步值」是**设计建议**：验证方式是**对照实验**——在 UE5 里按表值起步，然后**每次只改一个**并录屏（三组典型：ankleRotationGain 0.25 vs 1.0；MovementGravity 120 vs 9.8；Jiggler 生效区间 [50,300] vs [0,50]）。能在三组内看出「机甲感」差异的字段才值得留在面板上，剩下的应从面板移除。

## 2. 下钻 c：「装配即难度」（5.6 节）

### 2.1 第一层：把它换算成三个可测量

原文只说了“约束互相牵连”和“卡关了去换装”。下钻后，**“难度”必须落到三个能读出来的量**，否则这句话不可测：

| # | 可测量 | 定义式 | 数据来源（本机字段） | 实测区间 |
|---|---|---|---|---|
| ① | **破防所需命中数 N** | N = 目标姿态阈值 ÷ 单发冲击力 | `EquipParamProtector.stability`(四槽求和) ÷ `AtkParam.impactPower` | **2.2 ~ 5.4 发**（中位冲击 500）→ 弹性 **2.44 倍** |
| ② | **QB 预算** | 满 EN 可连续 QB 次数 = `energyMax` ÷ `consumeFixedEN_QB` | `EquipParamGenerator` ÷ `EquipParamBooster` | **2.0 ~ 9.2 次**（4.6 倍） |
| ③ | **载重余量** | `legs_payload` − Σ部件重量；第二道门 `armMaxWeight` | `EquipParamProtector` @580 / @568 | 载重上限 **100,300 kg**；四槽自重和 **30,430 ~ 104,740 kg**（上限装配已超最重腿的载重） |

> ①的阈值取哪张表，是本条下钻最关键的一步：**技能语（“难度”）→ 表（阈值表）的映射唯一**。见 2.2。
**▶ 我怎么知道这一层是对的？** 三个量都能手算复现：① 的两个输入（阈值 1097~2677、冲击中位 500）来自本机实测（2.4 有原始输出）；② 的两个输入来自发电机/推进器表；③ 的两个输入来自护甲表与载重字段。**唯一需要外部验证的是 ① 的除法关系**（阈值是「累加和」还是「逐级递减」）——用 2.4 结尾给的训练场实测法验证。即使除法关系不成立，③ 的 2.44 倍弹性仍然成立（它是纯实测比值），只是「相当于几次命中」的说法要改。

**程序要实现的一个函数（把“难度”变成可调参的）**

```
QB_budget = generator.energyMax / booster.consumeFixedEN_QB

```

**UI 要用到的“装配对比”增量**：换一件部件时，UI 上要实时刷新的就是 Δ(姿态稳定和)、Δ(AP)、Δ(自重 vs legs_payload)、Δ(EN 负荷 vs energyMax)——**这四个差值就是“装配即难度”的可视化形式**。

**TA 要做的事（这条对 TA 的价值中等，主要是管线）**

## 3. 下钻 d：「把预算花在高频反馈上」（5.9.3 节）

### 3.1 第一层：先把“高频”定义出来

原文的“高频”没有任何判据。**我给一个可算的定义**（口径必须显式，否则这句话不可反驳）：

> **高频度 f(组合) = P(攻击材质) × P(受击材质) × P(攻击类型) × P(威力档)**，四项边际全部来自本机参数表的行数占比。
> 口径限制：这是**参数空间占比**，不是运行时遥测。用它检验“预算分配是否合理”是充分的；用它断言“玩家每分钟看到几次”则不充分。

四个维度各自的实测分布（这是“高频”的全部依据）：

| 维度 | 字段 | 表 | 实测分布（占比 Top） |
|---|---|---|---|
| 攻击材质 | `atkMaterial`(u8 @457) | `AtkParam_Pc` | **鉄製 320/712 = 45%** · なし 13% · EN緑 12% · パルス 10% · レーザー 7% · プラズマ 5% |
| | 同上 | `AtkParam_Npc` | 鉄製 35% · なし 34% · レーザー 11% · コーラル 8% · EN緑 5% |
| 受击材质 | `materialSfx1`(u16) | `NpcParam` | **身体鉄(103) = 1227/1232 = 99.59%** · 身体肉(105) 3 行 · 无 2 行；**盾鉄/盾重鉄/盾エネルギー/身体重鉄 = 各 0 行** |
| 攻击类型 | `atkType`(u8 @450) | `AtkParam_Pc` | 弾丸 41% · 斬撃 31% · 爆風 19% · 打撃 10% · **刺突 0 行** |
| | enum 来源 | `BehaviorParam_AtkType.tdf`（cp932） | 0=斬撃 1=打撃 2=刺突 3=爆風 4=弾丸 |

⇒ 反向：**“铁 ⇒ 盾エネルギー”在受击侧是 0 行敌人使用**（没有 NPC 用 102 材质）——**它的真实频率是 0**，这就是它预算只有 3 个 ID 的原因。
**▶ 我怎么知道这一层是对的？** 四个边际分布都是**可直接重跑的行数统计**（命令见 3.4，输出已贴）。**这条结论最容易被推翻的地方是口径**：若把分母换成「有效攻击行」（剔除哨兵行），占比会变；因此 3.2 只使用**方向性比较**（最高频 vs 频率 0），不拿具体百分比去分配预算。口径本身可证伪：把 param_inspect.py AtkParam_Pc 的逐列统计与本报告 D6 段对比，数字必须逐位相同。

## 4. 三条对比：哪一条对「技术美术」最值钱

| 维度 | a 机甲不是放大的人 | c 装配即难度 | d 高频反馈预算 |
|---|---|---|---|
| 下钻到的系统 | 脚 IK / 二次运动 / 角速度 / 模型弹簧 / 重力 | 数据表 + 阈值 + 载重/EN 经济 | 三级查表 + 25 格矩阵 + ID 预算 |
| 第三层产出物 | **可实现的 AnimNode/AnimDynamics 参数集 + 3 个 Debug Draw + A/B 开关** | DataTable + 派生数值重算器 + 难度面板 | 71×25 预算矩阵调试器 + VFX 规划文档 |
| 需要的技能 | 绑定/动画/物理/手感数值 | 数据管线/系统设计 | VFX 管线/资源预算/规范化 |
| 谁能立刻验证 | TA 自己（改一个重力就能看到） | 需要游戏内训练场实测 | 需要录屏对比或埋点 |
| 面试可讲性 | 中（技术细节强，故事性弱） | 高（“我把难度变成了数字”） | **高**（“我知道该把预算给谁”） |

**回答：这三条里对 TA 技能提升最有价值的是 a「机甲不是放大的人」。**

三个理由：
1. **它是唯一一条把 TA 的独占技能树（脚 IK / 二次运动 / 模型弹簧 / 伺服延迟）全部串起来的结论**，而这几套东西在引擎里各有对应实现（Foot IK 节点、AnimDynamics/PhysicsAsset、位移弹簧）。c 主要练数据管线，d 主要练资源预算——都能自学，但没有“手感”这个反馈回路。
2. **它训练的是“量纲思维”**：哪一类参数（长度/时间/角量/加速度）在放大机体时该变、按什么律变、什么时候该**故意违反**物理（角加速度设成无限、重力给到 12 g）。这是 TA 与策划/程序拉开差距的核心能力，而且可迁移到任何“大型单位”项目（怪兽、载具、机甲）。
3. **它有一条当天就能跑通的验证闭环**：改 `MovementGravity` → 数落地帧数；改 `ankleRotationGain` 0.25 → 1.0 → 立刻看到“海绵脚”；把 Jiggler 生效区间从 [50,300] 改成 [0,50] → 立刻看到“橡皮人抖动”。**能当场证伪的结论，才是能学会的结论。**

> 补充：如果你的目标是**特效/技术美术（VFX TA）**而不是角色 TA，那么答案是 **d**——它给的是“预算分配”的量化方法，而这正是 VFX TA 面试里最难讲清、也最能拉开差距的一环（3.2 的“71 行 → 26 个唯一向量”就是一句能直接说出口的证据）。**c 更适合当“系统设计/数值”岗位的素材，对 TA 的边际收益最低**。
