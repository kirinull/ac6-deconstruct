# AC6 技术实现与数据管线（TA 重点 · 可本地验证）
### 《装甲核心6：境界天火》拆解报告 · P15
> 读者：大四、目标技术美术（TA）、计划从策划岗入门。
> 本文所有"实测"均可复现：命令与原始输出见 **§11 附录 A**。凡未真跑过的，一律标 C/D 级。

## 0. 结论先行（TL;DR）

1. **AC6 的表现层几乎全部是数据**：257 张 param 表 / 55,911 行 / 20.11 MB，装下了武器、判定体、弹道、命中特效、音频 switch、LOD 绘制距离、跨平台画质档、菜单布局、教学判定、解锁条件。**"这个机制为什么这么设计"和"它怎么实现"在这份数据里是同一个问题的两面**——这是 TA 学习本项目性价比最高的一处。
2. **表名本身就是证据**：后缀命名法（`_PC`/`_Npc`、`_ps5`/`_xb1`/`_scarlett`）暴露了"双轨制"（玩家/NPC 各一套表）与"分平台数据"两个架构决策；一张主表串四张子表（`JigglerBaseParam` 里 4 个 behavior 外键）暴露了"组件化二次运动系统"。
3. **同一份内部类型名跨平台复用（实测）**：`PartsDrawParam`、`PartsDrawParam_ps4/_ps5/_xb1/_scarlett` 五张表的文件尾类型名**全都是 `PARTS_DRAW_PARAM_ST`**；`LoadBalancerDrawDistScaleParam_*` 7 张表全是 `LOAD_BALANCER_DRAW_DIST_SCALE_PARAM_ST`。→ **跨平台分档不是代码分支，是同结构不同数据**。
4. **分档的具体量级（实测）**：`LoadBalancerDrawDistScaleParam` 基准 22 行全 1.0；XBox Series S 22 行但 Lv00 缩放 **0.6**；XBox One 46 行、Lv00 0.6 / Lv20 低至 **0.25**；PS4 48 行、Lv20 低至 **0.25**。`PartsDrawParam` vs `_ps5` 只有 **12/152 行**不同（90 字节），vs `_ps4` 有 **94/152 行**不同（2,140 字节）。
5. **数据里有真实的依赖图，不用猜**：`BehaviorParam_PC.refId` 是**判别式外键**——按同一行的 `refType` 分流：`refType=0` → `AtkParam_Pc` 命中 **85%**，`refType=1` → `Bullet` 命中 **96%**，`refType=2` → `SpEffectParam` 命中 **100%**（实测）。这是"一把武器开火链路"的实证。
6. **同一张表里存在多态 ID 池**：`EquipmentLineupParam.equipId` 单列 318 个值，用 `equipType` 分流后 **每一类命中率都是 100%**（武器/防护/推进器/FCS/发电机）。→ 反推设计时"一个字段一个含义"的直觉是错的。
7. **TA 最该抄的一条**：`MaterialExParam` 212 行、**187 个唯一行名**（`Camouflage_Transparency`、`CaterpillarScroll`、`Shininess`、`Color_Main`…），且 **212 行的 `materialId` 全部 = −1**（实测）。它不是"材质表"，而是**"命名材质参数槽位注册表"**：美术在材质里暴露命名参数 → 表里按 ID 注册 → 特效/涂装/伪装在运行时按 ID 驱动它。
8. **口径纪律（重要）**：`行宽 = didx[1]−didx[0]`，**单行表的行宽不可信**（实测 14 张与 paramdex 不一致的表里，8 张是单行表）；**md5 不能当内容改动证据**（本机 van 与 roundtrip 两目录 257 张表 md5 全同，属字节级回写；但 Mod 工具重序列化会改 md5）。
9. **对 TA 的能力映射**：这条管线的日常工作是 **"把美术意图翻译成数据契约"**——参数命名、ID 池管理、变体/分档、外键连通性校验、可复现的解析脚本。**不写渲染代码也能证明 TA 价值**，但必须能读懂二进制结构。
10. **合规**：本地解包研究可以做；**版权资产一律不分发**（模型/贴图/音频/param 原始文件都不行），不碰在线服务、不做联机绕过。

### 2.2 paramdex 与数据的一致性：197 张可比对，183 张精确吻合（B，实测）

```text
## 校验1b: 大小写无关精确解析
可比对 197, 一致 183 (93%), 不一致 14, 无定义 60
```

**必须知道的两个坑（实测）**：

| 坑 | 实测证据 | 正确做法 |
|---|---|---|
| **单行表行宽不可信** | 上表 14 张里 8 张是 `rows=1`（`BudgetParam`、`GameSystemParam`、`SoundParam`、`GraphicsParam`、`NetworkParam`、`EnemyCommonParam`、`MapDefaultInfoParam`、`CutsceneGparamWeatherParam`、`PartsBreakParam`） | 单行表的 `rowsize` 由"字符串表偏移 − didx"推出，会把行尾填充算进来；**单行表要用 paramdef 或手工读字段，别信行宽** |
| **真正需要解释的只有 3 张** | `DecalParam` def 251 vs 实测 252；`ThrustersLocomotionParam_PC` +58（74 行）；`ThrustersParam_NPC` +48（501 行） | 大概率是 paramdef 未建模的尾部 pad 或 paramdef 版本滞后（D 级） |
| **md5 不是内容证据** | van vs roundtrip：`同 md5 257, md5不同但行数据相同 0, 真正不同 0` | 比内容必须**解析后按行 ID 对齐逐字节比** |

### 2.3 文件尾的"内部类型名"是结构同一性的铁证（B，实测）

```text
$ python _p15c.py    # 读文件尾 ASCII
WwiseValueToStrParam_Switch_Weapon_Type    ['hand_gun','sniper','cannon','missile',...,'WWISE_VALUE_TO_STR_CONVERT_PARAM_ST']
PartsDrawParam / _ps5 / _ps4 / _xb1 / _scarlett   ['PARTS_DRAW_PARAM_ST']      # 五个平台同一个类型名
LoadBalancerDrawDistScaleParam / _ps4 / _ps5 / _xb1 ['LOAD_BALANCER_DRAW_DIST_SCALE_PARAM_ST']
EquipParamWeapon_Npc   ['EQUIP_PARAM_WEAPON_ST']      PadRumble  ['CAMERA_RUMBLE_PARAM_ST']
AutoAssembleEvaluate   ['ASSEM_EVALUATE_PARAM']        UnlockParam_Trophy  ['GAMEDATA_UNLOCK_PARAM']
TutorialActJudgeParam  ['TUTORIAL_ACTJUDGE_PARAM_ST']  MercenaryRankTable  ['MERCENARY_RANK_RECORD_ST']
```

**这一列字符串比表名更有信息量**：它是引擎侧反序列化时用的类型名。
- 五张 `PartsDrawParam_*` 共用 `PARTS_DRAW_PARAM_ST` → 同结构、不同数据（**分档=数据**，A/B 级）。
- 所有 `UnlockParam_*` 共用 `GAMEDATA_UNLOCK_PARAM` → 解锁系统是**一套通用 flag 体系**，靠不同表实例化使用场景（宝箱/装备/奖杯/贴花/铭牌…）。
- `PadRumble` 的内部类型是 **`CAMERA_RUMBLE_PARAM_ST`** → 手柄震动复用了相机震动的结构体（省一套 schema + 编辑器，C 级推断：这是常见的"复用最大字段集"做法）。

## 3. 从表名清单反推架构（逐条：表名 → 推断 → 证据/置信度）

### 3.3 表名**不能**证明什么（边界，避免过度推断）

- 表名**不能证明调用顺序**（`AtkParam` 在 `Bullet` 之前还是之后？要靠外键方向推）。
- 表名**不能证明是运行时读取**（很多字段/表是开发期残留，见 §5 案例 5 的 `LBDrawDistScaleParamID` 全 0）。
- 表名**不能证明数值含义**（`weight` 是 kg 还是别的单位，要靠值域 + 游戏内显示交叉验证）。
- 表名**不能证明是同一版本**（paramdef 与 param 可能不同版本，见 §2.2）。

### 4.2 这条链是**实证**的，不是推测（B，实测）

我用 paramdex 提供的**字节偏移**直读源表字段，再把取值集合与目标表的**行 ID 集合**求交：

```text
== 校验2: 跨表外键连通性(用 paramdex 偏移直读) ==
EquipParamWeapon.behaviorVariationId -> BehaviorParam_PC.variationId    130 取值, 命中 128 (98.5%), 未命中 [-1, 1200]
Bullet.atkId_Bullet -> AtkParam_Pc 行ID                                 446 取值, 命中 435 (97.5%), 未命中 [-1, 990, 5060010, 10740000, ...]
BehaviorParam_PC.refType=0 (n=315) vs AtkParam_Pc        命中 267 (85%)
BehaviorParam_PC.refType=1 (n=325) vs Bullet             命中 312 (96%)
BehaviorParam_PC.refType=2 (n=2)   vs SpEffectParam      命中   2 (100%)
AtkParam_Pc.spEffectId0 -> SpEffectParam 行ID            16 取值, 命中 13 (81.2%)
Bullet.spEffectId0      -> SpEffectParam 行ID            15 取值, 命中 13 (86.7%)
AtkParam_Pc.damageLevelConvId -> DamageLevelConvParam     54 取值, 命中 49 (90.7%)
EquipmentLineupParam.equipId -> EquipParamWeapon 行ID    318 取值, 命中 198 (62.3%)  ← 见下
```

**读法（方法论要点）**：

1. **命中率 ~98% 且残差是 `−1`** → 这是真外键，`−1` 是"未使用"哨兵值。**不要把哨兵当脏数据**。
2. **命中率只有 62%** 时不要急着否定结论——`EquipmentLineupParam.equipId` 的 318 个值里有 84 个是 `50000000+`，那是**防护部位 ID 段**。按 `equipType` 分流后：

```text
EquipmentLineupParam:  equipType=0 n=198 -> EquipParamWeapon 100%
                       equipType=1 n= 84 -> EquipParamProtector 100%
                       equipType=4 n= 12 -> EquipParamBooster 100%
                       equipType=5 n= 10 -> EquipParamFcs 100%
                       equipType=6 n= 14 -> EquipParamGenerator 100%
ShopLineupParam:       equipType=0 n=134 -> EquipParamWeapon 87%   (残差为未实装/DLC 条目，C 级)
                       equipType=1 n= 71 -> EquipParamProtector 89%
```

→ **"一个字段一个含义"的直觉是错的**。AC6 用的是**多态 ID 池 + 判别列**：`(equipType, equipId)` 组合才是键。这条经验可以直接迁移到你自己的项目。

3. **同一张表可以有多个语义域**：`EquipmentLineupParam` 318 行覆盖 5 种装备类型；`UnlockParam_*` 14 张表共用一个 schema。

### 4.3 每段"谁负责"的现实切分（C 级，基于岗位职责推断）

## 5. param 表 / paramdef / row / field 的关系

### 5.1 四层关系

```
paramdef（表结构定义，.xml / .paramdefbnd）
   └─ 定义 field：名称 + 字节偏移 + 类型 + 位域 + 数组长度
        └─ param 文件（.param）：一批 row（行），每行按 paramdef 布局铺开
             └─ row：以 rid（行 ID）为键，是"一个实体"（一把武器/一个特效/一条弹道）
                  └─ field：该实体的一个属性值（写在固定字节偏移上）
```

| 概念 | 类比（对 TA 友好） | 本机实测 |
|---|---|---|
| paramdef | **顶点布局声明 / C 语言 struct** | 227 个 `Defs/*.xml`（本机 AC6 paramdex） |
| param 文件 | 一份 CSV/二进制表 | 257 个 `.param`，文件名 = 表名 |
| row | 一行记录 = 一个游戏实体 | 55,911 行（van） |
| rid | 主键，**稀疏分配**（见 §9） | `LockCamParam` 行 ID 为 `0,1,2,3,10,11,12,90,99,110,...`（实测，非连续） |
| field | 列 | `EquipParamWeapon` 619 个字段（paramdex 计算结构 1556 字节，与实测行宽**精确吻合**） |

### 5.2 为什么"改了 paramdef 就能改表结构"

引擎在反序列化时**只信任 paramdef**：

1. **读**：按 paramdef 的偏移依次把字节解释成字段 → 决定内存里的结构体布局；
2. **写/序列化**：按同一份 paramdef 决定每行写多少字节；
3. **编辑器**：按 paramdef 生成表单（这就是 Smithbox / DSMapStudio 能"看到列名"的唯一原因）。

所以：
- 只在 paramdef 里**加一个字段**，工具就会在每行多分配字节 → **行宽变大 → 旧 param 文件全部读不进去**（版本不匹配）；
- 两个程序若持有不同版本的 paramdef，**同一份 param 会解析出不同结果**——这正是社区工具最常炸的地方；
- 反过来，**只改 param 数据不改 paramdef**，结构不变、只变值 → 这就是 mod 最安全的做法。

> **本机实测旁证**：内部类型名（文件尾 ASCII）与 paramdef 的 XML 名一一对应（`BULLET_PARAM_ST` ↔ `BulletParam.xml`，见 §2.3）。**引擎按类型名找 paramdef**，这也是"表名 → 结构"映射的技术依据。

### 5.3 社区工具链一般怎么工作（B/C 级）

| 环节 | 工具 | 干什么 | 本机是否具备 |
|---|---|---|---|
| 解包 | UXM / WitchyBND / Yabber | 从 `.bnd/.dcx` 拿出 `regulation.bin` 与 param 文件 | ✅（257 张 `.param` 已解出） |
| 结构定义 | paramdex（Smithbox/WitchyBND 的 `Assets/Paramdex/AC6`） | 提供 `Defs` + `Names` + `Developer Names` + `Tdfs` | ✅（227 Defs / 256 Developer Names / 266 Names / 374 Tdfs） |
| 读写 | Smithbox / DSMapStudio / Param Editor | 按 paramdef 显示列、按行编辑、回写 | 未在本次任务中使用 |
| 逆向确认 | 自写解析器（本项目的 `param_inspect.py`） | 不依赖 paramdef，用 **didx 推行宽**，做结构自检 | ✅ |

> **为什么一定要自己会写解析器**：paramdef 可能版本滞后（实测 14/197 张不一致），但 `didx` 是文件里的物理事实。**结构问题问文件，语义问题问 paramdef，两者交叉验证**——这是本次任务最实用的一条工程纪律。

## 6. 从数据反推设计的通用方法论 + 5 个可执行验证案例

### 6.1 方法论（六步）

| 步 | 动作 | 本机对应操作 |
|---|---|---|
| 1 | **定位**：把设计假设翻译成"哪个系统的哪个量" | 查 `data/param_系统映射.md` 的 11 个系统归类 |
| 2 | **找表**：按表名前缀/族找候选 | `ls regulation-bin \| grep 前缀` |
| 3 | **定字段**：拿 paramdex 的**偏移**，不要按"第 N 个 f32 槽 × 4"猜 | `python tools/paramdex_fields.py <表名>` |
| 4 | **读值域**：min/max/mean/非零行/唯一值数 | `python tools/param_inspect.py <表名> van` |
| 5 | **找外键**：源字段取值集合 ∩ 目标表行 ID 集合，**算命中率** | 本项目 `_p15d.py` 的做法（见附录） |
| 6 | **对照实验**：三方目录（van / mob / reibis）或平台变体表做 A/B | `python tools/param_inspect.py <表名> mob` |

**排除干扰的 5 条纪律**：
1. `−1`、`0`、`9999`、`99999` 先当**哨兵/未使用**处理，不要当数据极值；
2. 单行表的行宽**不可信**（§2.2）；
3. 行数少的表（≤5 行，共 49 张）样本不足，别对单一值下"设计意图"结论；
4. **同一数值可能在不同表里是不同单位**（`LockCamParam` 列 0 实测 min 9 / max 100，列 1 实测 −70~−40，单位未知 → D 级，需游戏内实测对照）；
5. 任何"看起来很合理"的字段语义，都要用**值域合理性**与**外键连通率**两条独立证据交叉确认。

### 6.2 五个可执行验证案例

#### 案例 1：姿态阈值是固定值还是百分比？
- **假设**：敌人的"被打断/踉跄"阈值不是全局常量，而是**按部件累加的姿态稳定值**。
- **查哪张表**：`EquipParamProtector` 字段 `stability`(s32, @488)、`NpcParam.stabilityVal`、`TentativePlayerParam.stabilityBaseVal`。
- **命令**：`python tools/paramdex_fields.py EquipParamProtector` → 再按偏移读 `stability`。
- **判读**：若 `stability` 在 70+ 个不同取值、且**逐部件**不同 → 是"装备提供的稳定点数"，属**加法模型**；若所有行相同 → 是全局常量。
- **已验证结论**（本项目已核验记录，B 级；本次未重跑）：`stability` 值域 0~1500、逐部件、70 个不同值。
- **陷阱**：别拿 `EquipParamProtector` 的**行宽 / 4** 当字段数——该表 225 个 f32 槽，paramdex 里真正的 f32 字段只有一部分。

#### 案例 2："冲击力"和"累积冲击"是不是两个独立通道？
- **假设**：一发子弹有"瞬时冲击"和"持续累积冲击"两套数值，靠时间去耦合。
- **查哪张表**：`AtkParam` 的 `impactPower`(@528, s32)、`residualImpactPower`(@988, s32)、`hitStopTime`(@24, f32)；`GameSystemParam` 的 `Damage_ImpactLifeTimeSec`(@408, f32)。
- **判读**（本项目已核验记录，B 级；本次未重跑）：`impactPower` 中 −1 为"未使用"，实际 0~6000、中位 315；`residualImpactPower` 233 个非零；`Damage_ImpactLifeTimeSec` = **1.5 秒**。
- **可下的结论**：这是**两个通道 + 一个衰减寿命**：`impactPower` 是瞬时冲击（用于击退/踉跄判定），`residualImpactPower` 在 1.5 秒窗口内累积（用于持续压制）。**这就是"删掉一个字段会破坏机制"的证据**。
- **陷阱**：`impactPower` 的 s32 空间里有 `−1`，统计 min/max 时会把 `−1` 当最小值 → 必须先过滤。

#### 案例 3：自动配装是评分函数吗？
- **假设**：自动配装（Auto Assemble）不是硬编码规则，而是**加权求和**。
- **查哪张表**：`AutoAssembleEvaluate`（20 行 × 16 字节，字段仅 `propertyID`(s32) 与 `weight`(f32)，内部类型名 `ASSEM_EVALUATE_PARAM`）。
- **判读**：**只有两列**这一点本身就几乎证明了加权评分模型（20 行 = 20 个被评分的属性）。若权重和 >0 且可分正负号（吸引力/排斥力），进一步支持"评分最大化解"。
- **验证方法（D 级待做）**：`weight` 的符号分布 + 与 `MenuPropertySpecParam`（508 行，属性定义表）的 `propertyID` 连通率。
- **价值**：这是一条**"用表结构（2 列）反推算法（加权求和）"**的教科书案例。

#### 案例 4：教学系统具备"行为判定"能力吗？
- **假设**：教学关卡的"完成度"不是脚本硬编码，而是**动作序列识别**。
- **查哪张表**：`TutorialActJudgeParam`（31 行 × **9 字节**）。
- **实测解码**（原始输出见附录）：

```text
rid=0  (0,0)(0,0) ext=0   | none
rid=1  (1,1)(0,0) ext=0   | jump
rid=2  (1,2)              | Boost increase
rid=3  (1,3)              | quick boost
rid=4  (1,5)              | assault boost
rid=5  (1,6)              | vertical catapult
rid=8  (1,8)              | Assault boost stop
rid=10 (0,0)(6,4)         | boost move            ← 落在第 2 段槽位
rid=20 (0,0)(0,0) ext=2   | ext=Boost increase    ← 落在扩展槽位
rid=30 (1,30)             | drift turn
rid=31 (1,31)             | hovering
rid=22 (2,106)(3,106)     | 类型 106 未被命名（枚举不完整）
```

- **结论**：每行 = **最多 3 个动作条件**（段 1 / 段 2 / 扩展），类型取自 `TutorialActJudgeParam.txt` 里 31 个已命名行为（jump / quick boost / assault boost / drift turn / hovering / 右手：通常射撃…）。→ **教学具备"识别玩家做过什么动作"的能力**，可以做到"必须先做 A 再做 B"这种复合条件（B 级）。
- **陷阱**：这张表的行宽 9 不是 4 的倍数 → 会让"自检脚本"报异常（见 §2.1）。**不要因此判定文件损坏**。

#### 案例 5：跨平台画质分档具体差在哪？
- **假设**：分档不是"低/中/高"三档枚举，而是**逐部件的距离缩放的逐平台覆写**。
- **查哪张表**：`PartsDrawParam` 与 4 个平台变体；`LoadBalancerDrawDistScaleParam` 与 6 个平台变体。
- **实测**：

```text
PartsDrawParam vs _ps5       行数 152/152, 不同行 12, 不同字节总计 90
PartsDrawParam vs _scarlett  行数 152/152, 不同行 12, 不同字节总计 91
PartsDrawParam vs _xb1       行数 152/152, 不同行 91, 不同字节总计 1124
PartsDrawParam vs _ps4       行数 152/152, 不同行 94, 不同字节总计 2140
  rid=19  lv01_BorderDist: 9999 -> 5999.4 (ps4) / 3999.6 (xb1)
LoadBalancerDrawDistScaleParam: base/ps5/xb1x/xsx = 22 行全 1.0
  ps4 48 行, Lv20 低至 0.25；xb1 46 行 Lv00 0.6 / Lv20 0.25；xss 22 行 Lv00 0.6
```

- **结论**：**"分档"在这款游戏里是"给每个平台发一份数据表"**，而不是代码里的 `if (platform == ...)`。PS5/Scarlett 与基准表几乎一样（12 行差异，多为 `motionBlur_BorderDist` 900→0 这类开关），PS4/XB1 才有大规模距离削减。**Series S 的做法最"省"：行数不变、统一乘 0.6**。
- **陷阱**：**别拿单行表比行宽**（`LoadBalancerNewDrawDistScaleParam_ps5` 只有 1 行，实测行宽 56 不代表真实结构 = 48）。

#### 案例 6（附加）：武器表里到底有几个"真正的连续量"？
- **假设**：都是 f32，所以都是连续量。
- **实测**：`EquipParamWeapon` 的 389 个 f32 槽（= 1556/4，含 u8/s16/s32 被误算）在 paramdex 里对应 **132 个真正的 f32 字段**：
  - **全零未用 59 个**；**单一常量 23 个**；有变化 50 个；
  - 其中有"≥50% 行带小数"的**真连续量仅 15 个**，且**全是时间/速率类**：`magazineReloadTimeSec`、`chargeEndTimeSec`、`chargeReleaseStartTimeSec`、`chargeLv2EndTimeSec`、`bulletReload_Direct_ReloadSpeedUPS`、`justGuardKeepTimeSec`、`paOpen_PerfStayTimeSec`、`heat_ShootDelay`…
  - **`weight` 不是连续设计量**：p50=2800 / p95=6890 / max=14820（235/284 非零，B 级）。
- **结论（TA 用得上）**：**建模时不要照搬"f32 槽位表"**。这张 1556 字节的表里，真正需要美术/TA 参与调参的连续量是"**时间**"，其余是枚举/开关/整数。这条直接决定你导 DataTable 时的列类型选择。

## 7. 从数据反推视觉/音频资产：资产是被数据索引的

### 7.1 材质参数契约：`MaterialExParam`（本报告最重要的一条）

```text
实测：212 行 × 96 字节；paramName[32] (UTF-16) + materialId + materialParamValue0..4
materialId 取值分布 = {-1: 212}     ← 全部为 −1
187 个唯一行名，例如：
  100 Rise_Intensity        200 Damage_Rate         210 Damage_em_power
  300 Camouflage_Transparency 310 Camouflage_Refraction 320 Camouflage_Nonreflect* 
  330 Camouflage_Falloff      340 Camouflage_Emissive   350 Camouflage_FalloffPower
  800/801 CaterpillarScroll*  900 Color_Main 901 Color_Sub 902 Color_Support
  903 Color_Optional  904 Color_Join 905 Color_Device 906 Color_Eye
  907 Device_In*  910 CamouflageRate 911 CamouflageTexSize 912 CamouflageTexture*
  920 Shininess 921 Metalness
```

**解读（C 级推断 + B 级事实）**：`materialId` 全 −1 说明这些行**不绑定任何具体材质**——它们是**参数槽位注册表**（"ID → 参数名"的字典）。真正驱动它的是：

| 驱动者 | 表 | 字段（实测字段名） |
|---|---|---|
| 特效 | `SpEffectVfx` | `materialParamId` / `materialParamInitValue` / `materialParamTargetValue` / `materialParamFadeTime` |
| 玩家涂装 | `PlayerMaterialPresetParam`(46×64) | `Shininess` / `Metalness` / `Glow` / `TexIdLayer0..4` / `MaterialTex_Albedo` / `MaterialTex_Normal_Shininess` |
| 玩家配色 | `PlayerColoringPresetParam`(392B) | `slot0..N_PatternID` / `slot0..N_MaterialProperty_0/1` / `BaseRGBA` / `SubRGBA` / `SupportRGBA`… |
| 掉漆/锈蚀 | `PlayerWeatheringTexPresetParam`(36B) | `Peeling_Int` / `Rust_Int` / `CHG_1stlayer_Shininess` / `CHG_3rdlayer_Metalness` |
| 迷彩 | `PlayerCamouflagePattern`(16B) | `Small`/`Medium`/`Large` + `Slot0..3_enabled` |
| 履带滚动 | `TankBaseParam` | `paramL_texScrollMaterialParamID` / `paramR_texScrollMaterialParamID` |

**对 TA 的意义（可直接写进作品集）**：
1. **"材质参数命名 = 程序与美术的 API"**。名字一旦被表引用（`Camouflage_Transparency`），改动就会炸——所以命名规范必须收紧到"语义 + 单位"级别。
2. **"材质参数要能被时间驱动"**：`InitValue → TargetValue` + `FadeTime` 是这套系统的通用契约。你做的任何效果（受击泛红、过热发光、迷彩渐显）都应该按这个接口暴露参数。
3. **一条经验法则**：**能被数据引用的东西，必须先在数据侧注册**。注册表与实现体分离（`materialId = −1` 的那 212 行）是干净的做法——它让"参数槽位"可以先于美术资产存在。

### 7.2 贴花：`DecalParam`（248×252）

字段既包含**纹理索引**（`textureId` / `normalTextureId` / `diffuseTextureId` / `maskTextureId` / `emissiveTextureId` / `heightTextureId` / `beginIntpTextureId` / `endIntpTextureId`），也包含**渲染开关**（`usePom` / `useEmissive` / `useDeferredDecal` / `usePaintDecal` / `bUseNormal`）、**时间控制**（`lifeTimeSec` / `fadeInTimeSec` / `fadeOutTimeSec` / `appearAssetId`）、**性能控制**（`bDistThinOutEnable` / `distThinOutCheckDist` / `distThinOutMaxNum` / `thinOutOverlapLimitNum`）。

→ **TA 结论**：弹孔不是"一个特效"，而是**"纹理 ID + 材质开关 + 生命周期 + 抽稀策略"的四元组**。注意最后那个 **`distThinOut*`（距离抽稀）**：贴花数量控制在数据里，不在代码里。**这是性能预算进数据表的典型手法，做项目时值得照抄**。

### 7.3 音频：字符串 switch 是硬接口

```text
WwiseValueToStrParam_Switch_Weapon_Type（14 行 × 32B，内部类型 WWISE_VALUE_TO_STR_CONVERT_PARAM_ST）
  0=no | 12=shield | 15=rifle | 16=shot_gan | 17=machine_gun | 18=bazooka | 19=hand_gun
  | 20=sniper | 21=cannon | 22=missile | 23=bayonet | 24=laser_rifle | 25=laser_cannon | 255=item
WwiseValueToStrParam_Switch_Material（115 行，17 个唯一字符串）
  0=no | 1..3=stone_pavement | 4=wood | 5=sand | 6=ice | 7=snow | 11=iron | 12=glass | ...
SeMaterialConvertParam（83 行）：seMaterialId + 名字字符串（stone_pavement/sand/iron/…）
```

**这三张表合起来说明**：
- 游戏侧对音频**只传整数**（武器类别、物理材质 ID）；
- 中间的**字符串表把整数翻成 Wwise 的 Switch 名**（注意 `shot_gan` 是**开发者手写的拼写**，A/B 级实测，说明这是人写的数据而不是生成物）；
- **行 ID 空间（0,12,15…25,255）与游戏侧枚举一一对应** → 改表名 = 改 Wwise 事件结构 = 需要音频同步改工程。

**对 TA 的意义**：音频接口是**最容易被"数据改动"破坏**的地方（一个拼写错误 → 静音）。所以你的资产命名规范里，"材质名 / 武器类别名"要和音频侧的 Switch 名**同源**。

### 7.4 资产被数据索引 → 对 TA 的三条硬要求

| 要求 | 理由（实测依据） |
|---|---|
| **命名规范必须在"数据能引用"的粒度上稳定** | `JigglerBaseParam.strCtrlBoneName[24]` 用**骨骼名字符串**（`L_ClavicleLink`、`運搬用：L_Shoulder`）索引抖动器；骨骼改名 = 351 行动效配置失效 |
| **变体要能"只覆写少量字段"** | 平台变体表证明了这个模式（`PartsDrawParam_ps5` 只改 12/152 行）。TA 做低配/高配时不该复制整张表 |
| **纹理/模型/动画都要有可查 ID** | `DecalParam` 用 8 个 `*TextureId`；`ReTargetAnimSetParam` 用 `BaseAnimId` + 8 个 `ReTargetAnimId`；`Bullet.generateAssetNo` / `generateAssetAnimId` 用资产 ID |

### 8.2 这套设计读出来的 4 个模式

| 模式 | 实测表现 | 可复用结论 |
|---|---|---|
| **基准 + 平台覆写** | `LoadBalancerDrawDistScaleParam` 22 行是基准；ps5/xb1x/xsx 与基准**逐字段零差异**（168 个差异字段只在 xb1/xss 出现） | 分档表的第一版必须"不写就是全平台一致"，否则维护成本爆炸 |
| **平台可以"增加档位"而不只是改数值** | ps4 多 26 行、xb1 多 24 行（行 ID 200+ / 300+），是**额外的质量档** | 高档位数量本身是分档变量：弱机需要更多中间档才能平滑降级 |
| **同代机型可能共用同一份数据** | `_scarlett` 与 `_xb1` 的 `PartsDrawParam` 名字不同但用途相同；`_xss` 用 0.6 缩放而不加档 | 分档颗粒度要按"**硬件族**"而非"机型"来切，避免组合爆炸 |
| **两代实现并存** | `LoadBalancerDrawDistScaleParam`（Lv00..Lv20 = 21 个 LOD 档的缩放表）与 `LoadBalancerNewDrawDistScaleParam`（Begin/End 区间 + 起止缩放）同时存在于 257 张表内 | 新系统上线不删旧表（保守回滚）→ **数据文件的"废弃"需要显式标记，否则后人无法判断谁是活的**（本项目实测的活证据：`PartsDrawParam.LBDrawDistScaleParamID` 152 行**全为 0**，即该外键字段存在但未使用） |

### 8.3 TA 做跨平台项目时的分档参数体系设计（7 条）

1. **一份 schema、N 份数据**：schema 里不出现"平台"二字；平台只在**表实例**层面体现（AC6 就这么干，五张 `PartsDrawParam_*` 共用一个 `PARTS_DRAW_PARAM_ST`）。
2. **基准表 + 差异表**：只存"与基准不同的行"，并写工具校验"差异行数"上限（AC6 的 12 行 vs 94 行就是天然的告警阈值）。
3. **分档维度要正交且可枚举**：AC6 的 `LoadBalancerParam` 把降级拆成 `postProcess*` / `sfx*` / `shadowCascade*` / `dynamicResolution*` 四组开关（实测字段名）——**每个开关独立可关**，才能在帧率波动时逐步降级而不是一刀切。
4. **动态降级要有滞回**：`lowerFpsThreshold` / `upperFpsThreshold` + `lowerFpsContinousCount` / `upperFpsContinousCount` + `downAfterChangeSleep` / `upAfterChangeSleep`（实测字段名）→ **阈值 + 持续帧数 + 冷却时间**三件套，防止档位抖动。
5. **性能预算要能被美术看见**：`PartsDrawParam` 把 `drawDist` / `shadowDrawDist` / `motionBlur_BorderDist` 逐部件暴露，美术能为自己的零件负责。
6. **贴花/粒子这类"数量爆炸源"必须有抽稀参数**：`DecalParam.distThinOut*`（实测字段名）就是范例。
7. **建立"平台差异看板"**：每次提交都跑一遍"基准 vs 各平台变体"的行/字节差异统计（就是 §8.1 那张表），差异异常增大时报警。

### 8.4 分析三问（针对分档）
- **删掉分档会怎样**：弱机要么全程 0.25× 距离（画面糊）要么全程 1.0×（掉帧）。分档的意义是**让每台机器都跑在"刚好不卡"的画质上**。
- **放大/缩小 10 倍**：距离缩放 ×10 → 芯片要渲染 100 倍面积（近似平方关系），必然崩溃；×0.1 → 屏幕内几乎没有物体，玩法失效。**这解释了为什么实测值域被压在 0.25~1.0 而不是 0.05**（唯一例外是 `New_win64` 的 ScaleEnd 可到 0.0，即"极端情况下允许完全剔除"，B 级实测）。
- **有没有更简单的替代**：可以只做"低/中/高"三档枚举（很多项目这么干）。AC6 不用，因为**部件数量巨大（152 个绘制条目）+ 平台众多（7 个）**，枚举档位会导致"改一个零件要在 7 个地方改"。代价是数据量与管理复杂度。

### 9.1 数据驱动架构：优点与代价（实测支撑）

| 维度 | 优点 | 代价（本机实测到的证据） |
|---|---|---|
| 迭代速度 | 改一个数就上线，无需发版 | **依赖不可见**：`AtkParam_Pc.spEffectId0` 指向 `SpEffectParam` 的 4120 行中的某一行，改 ID 无编译报错 |
| 版本管理 | 补丁可以只替换 `regulation` 数据 | **补丁会打乱 ID 池**：Mod 用新增行实现功能（实测 van→mob：`AtkParam_Pc` 712→953、`BehaviorParam_PC` 722→1011、`Bullet` 568→716），一旦官方把同一个 rid 分给了别的实体，**Mod 与存档同时崩** |
| 反序列化/回写 | 工具链成熟（Smithbox 等） | **paramdef 与 param 会版本错配**（实测 14/197 张不一致） |

| 表现层 | 美术/TA 能在不重编译的情况下调参 | **命名/ID 冲突是静默失败**（`shot_gan` 拼写、`materialId = −1` 的语义靠文档） |
| 分析 | 可以被穷尽分析（本次任务就是证明） | 表多且无统一命名（`_PC` / `_Pc` / `_Npc` / `_NPC` 四种混用，实测） |

### 9.2 一次真实的"改动统计"（B，实测）

按"文件是否变化"统计会得到 **58 张表改动**；按"**行 ID 对齐后逐行比对**"统计，van→mob 是 **58 张表有结构/内容差异，其中真正数值改动合计 28 行**，其余是**新增行**（`AtkParam_Pc` +241 行、`BehaviorParam_PC` +289 行、`Bullet` +148 行）。reibis：54 张表、175 行改动。

→ **工程结论**：**"改了 58 张表" 和 "改了 28 行" 是两个完全不同的认知**。做 TA/工具链时，差异报告必须做到**行级、字段级**，而不是文件级（文件级会让人以为改动遍地开花）。这也是为什么 §2.2 强调"md5 不能当内容证据"。

## 10. 分析三问（本维度专项）

**① 如果所有数值都硬编码在代码里会怎样？**
- 开发期：改一个武器数值要重编译（AC6 有 284 把武器 / 712 条玩家攻击 / 4120 个特效 / 6013 条文本）。文本尤其致命——**6013 行 TalkParam 意味着本地化必须与代码解耦**（实测行数）。
- 跨平台：分档会退化成 `#ifdef PLATFORM` 宏。AC6 用 7 份数据表替代（实测），改 Series S 的距离不需要重新出 PS5 的包。
- 社区生态：没有 param 就没有 mod 生态（这是产品的商业决定，不只是技术决定）。
- **但硬编码不是没有优点**：类型安全、编译期检查、无 ID 冲突。AC6 的折中是"**结构硬编码在引擎（paramdef），数据全外置**"。

**② 如果参数表没有版本管理会怎样？**
- 补丁 A 把 `AtkParam_Pc` 的 rid 500 从"步枪第 3 段攻击"改成"霰弹枪"，Mod 还在改 500 → 玩家装上 Mod 后行为诡异且**没有任何报错**（这是 AC6 modding 社区已知问题类型，C 级）。
- 存档：如果存档记录的是 rid 而不是"实体指纹"，官方删行 = 存档里出现空引用。实测证据：所有外键都靠"行 ID 命中"成立（§4.2，连通率 85~100%），**整个系统的正确性建立在 ID 稳定性上**。
- 本机实测到的天然副作用：两代 `LoadBalancer*` 表并存、`LBDrawDistScaleParamID` 全 0 —— **没有"废弃标记"机制时，数据会只增不减**。
- **应有的实践**：行 ID 一旦发布即不可复用（只能废弃）；每次发版维护"ID 分配表 + 字段 diff 报告"；Mod 只允许消耗未使用 ID 段。

**③ 如果表结构频繁变动会怎样？**
- 工具链全面重做（每个版本都要重新生成 paramdef，实测本机 paramdex 就有 14/197 张与数据对不齐）。
- **跨版本工具会静默错位**：行宽变化会让"按第 N 槽 × 4 字节"的解析全部偏移。这正是 `_shared.md` 反复强调"**必须走 didx，不要用文件大小 ÷ 行数**"的根本原因。
- 引擎侧：序列化与内存布局强耦合，频繁改结构 = 频繁改反序列化代码 + 存档迁移。
- AC6 的对策（实测）：**几乎只在表尾追加字段**（`AtkParam` 里大量 `unk*` / `isFSDP` / `multiHitArmorHit_*` 这类后加字段都在高偏移处），并且**保留废弃字段（全零）**——代价是 `EquipParamWeapon` 有 59 个全零 f32 字段（实测）。
