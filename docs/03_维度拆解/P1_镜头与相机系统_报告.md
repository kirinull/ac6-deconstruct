# 《装甲核心6：境界天火》镜头与相机系统拆解


> 拆解对象：ARMORED CORE VI: FIRES OF RUBICON（FromSoftware, 2023）
> 视角：系统策划 + 技术美术（TA）双视角
> 证据分级：**A** = 游戏内可直接观察 / 官方公开；**B** = 社区实测、Wiki、数据挖掘（本文中凡标注"本机实测"的均属 B，来源为本机 UXM 解包后的 `regulation.bin`）；**C** = 基于同类游戏或引擎血统的合理推断；**D** = 不确定，必须给出验证方法。
> 本报告所有数值均来自"可观察量级"或**本机解包数据实测**，未做任何编造。凡我无法从本机数据确认的，一律标 D 并写明验证路径。

## 0. 结论先行

1. **AC6 的相机不是"瞄准工具"，而是"姿态可读性工具"。** 瞄准被整体外包给 FCS 与数据表（`EquipParamFcs`、`LockCamParam`），相机只负责两件事：让玩家在三维高速机动中看懂自己机体的朝向，以及把速度与冲击力翻译成视觉通道。[C]
2. **相机系统是数据驱动的，不是硬编码的。** 本机解包数据里存在 `LOCK_CAM_PARAM_ST`（98 行 × 376 字节 = 每行 94 个 f32 槽），行 ID 覆盖 0~398135，且出现 100000 / 200000 / 300000 / 130000 / 230000 / 330000 这类"章节前缀"式 ID 段。[B，本机实测]
3. **锁定相机是"档位表"结构**：不同目标 / 不同章节 / 不同武器共用同一套字段，靠选行而不是靠代码分支切换手感。列的取值分布呈现出明显的"距离（米）—角度（度）—比率（阻尼）"三类簇。[B]
4. **速度感由至少 7 条独立通道叠加**：FOV 变化、相机位置/旋转滞后、推进器粒子与拖尾、全屏后处理（`ZOOM_BLUR_ST` 有独立数据表）、镜头抖动、音效层、以及"位移本身发生在极少数帧内"。任何一条单独拉满都会露馅。[C]
5. **后处理是可参数化的**：`Zoomblur.param`（内部类型 `ZOOM_BLUR_ST`）仅 7 行，每行的强度字段实测取值 0.0025 / 0.005 / 0.01 / 0.015 / 0.02，另有指数字段 −1.0 / −0.1 / −0.5，其余槽为 0。[B，本机实测]
6. **"镜头抖动"和"手柄震动"在 AC6 里共用一张表**：`PadRumble.param` 的内部参数类型名实测为 **`CAMERA_RUMBLE_PARAM_ST`**，174 行 × 84 字节，行 ID 集中在 9000~9473 区块。[B，本机实测 —— 这条颠覆了"抖动是一套独立系统"的直觉]
7. **硬锁是一次显式的设计交易**：玩家用"相机自由度 + 部分机动控制权"换取"命中稳定性"。这不是技术妥协，而是刻意的 cost 设计。[B/C]
8. **软锁与硬锁的分工是"角度 vs 承诺"**：软锁是屏幕空间的角度吸附（可被遮挡打断、随目标移动自动重选），硬锁是玩家显式按下的"承诺"，一旦建立就以目标为中心解算相机。[B/C]
9. **相机参数里存在哨兵值语义**：`LockCamParam` 第 4 列取值 40~9999，其中 9999 占绝对多数 —— 这是"无限/不限制"的哨兵，不是 9999 米。[B，本机实测 + D 级语义推断]
10. **过场与实机是同引擎实时衔接**：本机数据中 `CutsceneGparamTimeParam`、`CutsceneMapIdParam`、`CutsceneReplaceSfxParam`、`SoundCutsceneParam`、`GarageCutsceneParam` 是 5 张彼此独立的过场参数表，说明过场被当作"可配置的时间/地图/音频环境"来管理，而不是纯预渲染影片。[B]
11. **最值得先验证的一条**：`LockCamParam` 的**列语义映射**（第 0~5 列 ≈ CamDistTarget / rotRangeMinX / lockRotXShiftRatio / chrOrgOffsetZ / chrLockRangeMaxRadius / FovYChange）。一旦确认，整套相机复刻就有了可导入的数据骨架。[D]

## 1. 问题定义：这台相机要同时满足两个互相拉扯的需求

| 需求 | 物理含义 | 对相机的直接要求 | 与另一需求的冲突点 |
|---|---|---|---|
| **看清自己**（机体姿态可读） | 玩家要知道机体朝向、受击方向、推进器状态 | 相机距离不能太近（机体高约 10 m 量级）、俯角要能看到脚下与地面、旋转要稳 | 距离远 → 目标在屏幕上变小 → 瞄准困难 |
| **瞄准敌人**（准星覆盖目标） | 屏幕空间上准星与目标重合 | 相机要能快速指哪打哪、FOV 不能太宽（否则目标角尺寸缩小） | 快速旋转 → 姿态可读性下降、易迷失朝向 |
| **高速机动**（QB/AB） | 位移在极短时间内发生 | 相机要滞后以体现速度，但滞后会导致准星脱靶 | 滞后 ↔ 瞄准精度直接对立 |
| **三维混战**（多目标、空中） | 目标可能在上方/下方/背后 | 硬锁提供"永远看得到目标" | 硬锁剥夺了玩家对相机的控制 |

**AC6 的解法（结论）：把"瞄准精度"从相机上剥离。** 相机的旋转不再等价于弹道方向；弹道由 FCS 在"相机朝向 + 目标"之间做仲裁。因此相机可以放心地做得"更慢、更沉、更有惯性"，从而换取机甲质量感。这是整个相机系统最重要的一条设计决策。[C]

**四段式**
- **设计意图**：让"重"和"准"不再互斥。
- **实现手段**：相机旋转 → 机体朝向 → FCS 仲裁 → 实际弹道，四层解耦；`LockCamParam` 提供每一层的数值档位。
- **玩家体验/结果**：玩家感觉"机体在被我操控"而不是"我在操控一个准星"；射击命中依赖 FCS 属性而非纯手眼协调。
- **可复用结论**：当"载具质量感"与"射击精度"冲突时，优先把精度外包给一个可数值化的仲裁层（FCS/散布/自动瞄准），把相机释放给表现。

**设计意图**：状态机的粒度决定了"手感差异"能不能被表达。AC6 把 AB / QB / 近战 / 硬直拆成独立状态，是因为它们在**同一组参数上需要不同的取值**（距离、FOV 增量、滞后量、抖动模板），而不是因为它们逻辑上不同。
**可复用结论**：状态机应该按"参数集合的差异"来切分，而不是按"玩法逻辑"来切分。逻辑上 AB 和 QB 都是"移动"，但它们对相机的参数要求相反（AB 要拉远+模糊，QB 要跟紧+抖动）。

### 2.1 状态机的三个真实难点

上面那张表看起来很干净，但真做起来，难点不在"有哪些状态"，而在下面三件事：

**难点一：状态是叠加的，不是互斥的。** AB 与硬锁可以同时成立（锁定中开 AB），被击中的硬直可以发生在 QB 过程中，Boss 战可能同时是硬锁态。所以相机系统真实的结构是"**一个基础态（跟随/软锁/硬锁） + 若干叠加修饰（AB/QB/硬直/演出）**"，而不是一个扁平的 12 项枚举。工程上正确的做法是：基础态决定"注视点与距离"，修饰态决定"FOV 增量、滞后系数、后处理权重、抖动模板"，最后按优先级合成。如果有人把 12 个状态写成一个 `switch`，第一次遇到"锁定中开 AB"就会出 bug。[C]

**难点二：进出条件里必须带"宽限时间"（hysteresis）。** 软锁如果"一被遮挡就断"，玩家在柱状掩体密集的关卡里会看到锁定框疯狂闪烁；硬锁如果"一超出距离就断"，高速拉扯战会变成不断解锁重锁。所以真实的判定不是布尔量，而是"条件成立持续 N 帧才切换"。这个 N 没有唯一正确值，它的上界由"玩家能容忍的最长错误状态时间"决定，下界由"最短的合法遮挡时间"决定 —— 这是一个必须靠实测标定的参数。[C]

**难点三：状态切换本身需要混合（blend）。** 从自由态切到硬锁，如果用一帧硬切，画面会瞬间跳到一个新构图；AC6 的做法必然是在若干帧内把"注视点"从一个（机体前方某点）插值到另一个（目标身上）。这个混合期的长度直接决定"锁定手感是果断还是拖沓"。混合期太短 → 突兀；太长 → 玩家觉得锁定"不跟手"。[C]

**四段式**
- **设计意图**：让状态机既能表达差异，又不至于组合爆炸。
- **实现手段**：基础态 × 修饰态的两层结构 + 带宽限时间的条件判定 + 状态间注视点插值。
- **玩家体验/结果**：玩家感知不到"状态"，只感知到"这一刻镜头更贴/更远/更晃"。
- **可复用结论**：相机状态机应当实现为"**层 + 权重**"，而不是"**枚举 + 分支**"；这是它和其他玩法状态机最大的结构差异。

**四段式**
- **设计意图**：让"锁定手感"成为可以按目标类型整行替换的数据，而不是散落在代码里的常数。
- **实现手段**：`LockCamParam` 用 98 行 × 94 列的表，行按目标/章节寻址，列承载距离、角度、比率、哨兵。
- **玩家体验/结果**：打不同敌人（尤其是不同章节的同型号）时相机距离与吸附强度不同，但玩家不会察觉"切换了系统"，只觉得"这场的镜头更贴/更远"。
- **可复用结论**：把相机手感做成 DataTable 行，是让策划能独立调参的最省事方案；代价是必须有人维护"列语义文档"，否则会变成没人敢动的黑盒。

## 4. 锁定系统：软锁 / 硬锁 / 解耦 / 代价

### 4.1 三层结构

| 层 | 归属 | 作用 | 可观察证据 |
|---|---|---|---|
| **L1 候选筛选** | FCS 属性 + 屏幕空间 | 决定"哪些敌人是可锁定的" | 锁定框只在部分敌人头上出现；超出距离/角度即消失 [A] |
| **L2 软锁牵引** | 相机 + 准星 | 准星向候选做有限角度吸附 | 目标横穿时准星会有轻微跟随 [A] |
| **L3 硬锁承诺** | 玩家显式输入 | 相机与机体共同朝向目标 | 按下右摇杆后画面以目标为中心 [A] |

### 4.2 状态转移表

| 当前 | 事件 | 下一状态 | 说明 | 证据 |
|---|---|---|---|---|
| 无锁定 | 敌人进入 FCS 锁定距离 + 角度锥内 + 无遮挡 | 软锁 | 自动，无需输入 | A |
| 软锁 | 玩家按下硬锁键 | 硬锁 | 相机切到目标注视模式 | A |
| 硬锁 | 再按硬锁键 | 软锁/无锁定 | 手动解除 | A |
| 硬锁 | 推动右摇杆左右 | 硬锁（切换目标） | 输入语义从"转相机"改成"换目标" | B/C |
| 硬锁 | 目标死亡 | 回落软锁 | 相机回到跟随 | A |
| 硬锁 | 目标超出距离 | 回落软锁/丢失 | 距离阈值由 `LockCamParam` 列 4 等字段决定（值域 40~9999，9999 = 无限） | B（数据）/ D（映射） |
| 硬锁 | 目标被遮挡 | 延迟后丢失 | "宽限时间"是必须的，否则柱状掩体后抖动 | C |
| 硬锁 | 玩家进入硬直/被击飞 | 保持锁定但相机抖动 | 输入被夺但不解锁，避免"被打了还丢锁"的二次惩罚 | C |

### 4.3 朝向解耦：机体转向相机，还是相机绑机体？

**结论：常规态是"相机主导、机体追相机"；硬锁态是"目标主导、相机与机体同时追目标"。**[A/C]

| 模式 | 相机朝向来源 | 机体朝向来源 | 玩家输入的作用点 |
|---|---|---|---|
| 常规 | 右摇杆直接映射（相机立即转） | 追相机方向的 yaw（受机体转速上限约束） | 输入 → 相机 → 机体 |
| 软锁 | 右摇杆 + 微量吸附 | 追相机方向 | 同上，吸附项叠加 |
| 硬锁 | 由"相机→目标"向量解算 | 由"机体→目标"向量解算（独立解算） | 输入被降级为"目标切换/微调" |

**为什么这样设计**：如果硬锁时相机绑死机体，那么"机体被击退/侧移"会直接带着画面甩出去，玩家失去参照系；如果硬锁时机体不自动朝向，则玩家必须在锁定状态下继续手动转机体，硬锁的价值归零。两条独立解算换来的是**画面稳定 + 命中稳定**可以同时拿到。[C]

这里其实存在**三个独立的速度环**，理解它们是理解 AC6 相机的关键：

| 环 | 输入 | 输出 | 被什么限制 | 数据来源 |
|---|---|---|---|---|
| **相机环** | 右摇杆（或锁定目标点） | 相机朝向 | 玩家手速、旋转阻尼 | `LockCamParam` 的旋转/比率列 |
| **机体环** | 相机朝向（常规态）或目标方向（硬锁态） | 机体朝向 | **机体转速上限**（受配装重量影响） | `ChrActTurnParam`（258 行） |
| **火控环** | 相机朝向 + 目标状态 | 实际弹道 | FCS 属性、武器散布、弹速 | `EquipParamFcs`、`Bullet` / `AtkParam_*` |

三环串联的意义在于：**玩家转视角的速度（相机环）可以远快于机体转身的速度（机体环）**，于是"视线已经甩到敌人身上、机体还在慢慢转过来"这个中间态就出现了。这个中间态是机甲质量感最主要的来源之一 —— 它把"转向"这个动作从"瞬时"变成了"需要时间的过程"。[C]

而火控环是最后一道仲裁：即使相机已经完全对准目标，弹道是否真的飞向目标，取决于 FCS 与武器。这解释了为什么"看起来瞄得很准却打不中"在 AC6 里是可理解、可学习的现象 —— 玩家可以从曳光看到弹道偏离，进而去换更好的 FCS。[C]

`ChrActTurnParam`（内部类型 `CHR_ACT_TURN_PARAM_ST`，258 行 × 168 字节）与 `ChrActTurnParam_Npc`（2124 行）就是机体环的数据来源 —— 它决定了"机体追相机"这一步有多慢，也就是相机能跑多前面。注意 NPC 表有 2124 行而 PC 只有 258 行，说明敌方单位的转身行为被切得细得多（不同机体、不同状态各有一行）。[B]

### 4.4 硬锁的代价（设计上为什么必须给代价）

事实层面：硬锁剥夺了玩家对相机的自由控制，右摇杆被重新映射为切换目标。[A]

推断层面（**C**）：如果硬锁无代价，它会成为唯一解 —— 所有高手的操作都会被简化成"锁住 + 输出"，机动的观赏性与技巧深度一并消失。AC6 用三类成本约束它：
1. **信息成本**：相机被锁死，玩家失去余光与态势感知，容易被第三个敌人偷袭。
2. **控制成本**：切换目标需要额外输入，混战中频繁切换有代价。
3. **参数成本**（D，需验证）：硬锁行对应的 `LockCamParam` 参数（如列 0 的距离、列 6~10 的插值比率）与自由态不同，可能导致相机响应更迟钝。

### 4.5 FCS 数据侧：`EquipParamFcs` 实测

`EquipParamFcs.param`：**19 行 × 208 字节 = 52 个 f32 槽**（无内部类型名）[B]。可观察的离散列：

| 列 | 值域 | 取值形态 | 候选语义（**D**） |
|---|---|---|---|
| 3 | 1~160 | 80/90/100/120/130/140/160 等 | 锁定距离或锁定角度 |
| 8 | 0~800 | 多数 350 | 距离类 |
| 9 | 0~80 | 多数 80 | 角度类 |
| 10 | 0~390 | 多数 390 | 距离/速度类 |
| 18 / 19 | 0~250 / 0~800 | 多数为 0 | 少数机体的特化项 |
| 33 / 34 | 0.72~1.55 / 0.8~1.6 | 连续、每个 FCS 不同 | 修正系数（乘算） |
| 36 / 37 | 恒为 1 | 常数 | 开关/默认值 |
| 39 | 0~120 | 多数 120 | 角度类 |

**四段式**
- **设计意图**：把"锁得远不远、锁得宽不宽"变成可交易的配装属性，让 FCS 成为构筑维度。
- **实现手段**：FCS 表里的距离/角度/修正系数列 + 相机侧 `LockCamParam` 的档位表，两层叠加。
- **玩家体验/结果**：换 FCS 会直接改变"能锁多远、锁定框多大"，而相机的跟随手感不变 —— 这就是"瞄准外包给数据表"的具体兑现方式。
- **可复用结论**：把"可瞄准性"做成装备属性，比做成相机参数更容易平衡，也更容易让玩家理解。

## 5. 速度感的通道拆解

**"很快"不是一个感觉，是至少 7 条通道的和。** 下表把每条通道拆到可实现量。

| 通道 | 物理量 / 参数 | 量级 | 它贡献了什么（缺了会怎样） | 证据 |
|---|---|---|---|---|
| ① FOV 变化（FOV Kick） | 视场角增量（度） | 数十度量级；`FOV-Y 变化`列实测值域 **25~60** | 提供"画面被拉长"的生理线索；缺 → 速度只剩位移，像瞬移 | B（列值）/ A（现象） |
| ② 相机位置滞后 | 相机位置对机体位置的跟随比率/时间常数 | 比率型，`LockCamParam` 列 6~10 实测 **0.01~1.0** | 让机体"冲出画面再被追回"；缺 → 相机像贴在机体上，速度感归零 | B（列值）/ C（用途） |
| ③ 相机旋转滞后 | yaw/pitch 的追平速度 | 未读到具体值 | 转向时画面"甩"出去；缺 → 转向显得轻飘 | D |
| ④ 推进器粒子与拖尾 | 粒子发射率 / 拖尾长度与寿命 | 未读到表；属美术资源侧（AssetMaterialSfxParam / AssetModelSfxParam 共 44 / 364 行） | 提供"速度矢量在场"的证据；缺 → 玩家判断不出加速方向 | B（表存在）/ D（数值） |
| ⑤ 全屏后处理 | `ZOOM_BLUR_ST` 的强度 + 指数 | 强度 **0.0025 / 0.005 / 0.01 / 0.015 / 0.02**；指数 **−1.0 / −0.1 / −0.5** | 把"速度"从物体级提升到全屏级，直接压在视网膜上；缺 → 高速段画面太"干净" | B（实测） |
| ⑥ 镜头抖动 | 见第 6 节 | `CAMERA_RUMBLE_PARAM_ST` 174 行 | 加速瞬间给一次冲击脉冲；缺 → 加速没有"点火"的瞬间感 | B |
| ⑦ 音效层 | BGM/SE/推进音的低频层 | `RuntimeSoundParam_Pc` 165 行、`ThrustersSfxIdParam_PC` 22 行 | 听觉上的速度补偿；缺 → 视觉速度再高也"闷" | B（表） |
| ⑧ **帧内位移** | QB 的实际位移发生在极少数帧 | 数帧量级 | 这是"快"的**本体**，其余 7 条都是它的修饰；缺 → 再怎么修饰都是慢动作 | C |

### 5.1 `Zoomblur.param` 本机实测（B 级数据）

内部类型 `ZOOM_BLUR_ST`，**7 行 × 32 字节 = 8 个槽**。前 4 字节是整型标志（396 / 511 / 255，语义未验证），第 2 槽为强度，第 3 槽为指数，其余 5 槽为 0。

| 行 ID | 槽 0（整型标志） | 槽 1 强度（f32） | 槽 2 指数（f32） | 槽 3~7 |
|---|---|---|---|---|
| 0 | 0 | 0.0 | 0.0 | 0（**全零 = 关闭档**） |
| 100 | 396 | 0.0025 | −1.0 | 0 |
| 1000 | 511 | 0.005 | −0.1 | 0 |
| 2000 | 255 | 0.015 | −0.5 | 0 |
| 2100 | 255 | 0.01 | −0.5 | 0 |
| 3000 | 255 | 0.02 | −0.5 | 0 |
| 9000 | 511 | 0.01 | −0.5 | 0 |

**读法**：强度跨 8 倍（0.0025→0.02），指数有 3 档（−1.0 / −0.1 / −0.5）。这正是"径向模糊"材质的两个标准参数：`strength` 控制 UV 偏移总幅度，`exponent` 控制径向衰减曲线的凹凸。**指数 −1.0 与 −0.5 之间是"只有中心清晰"和"大片区域被拉"的差别。**[B（数据）+ C（解释）]

**四段式**
- **设计意图**：速度必须被"看到"，而不只是被"到达"。
- **实现手段**：8 条通道分别绑定不同的物理量（速度、加速度、角速度、位移帧数），各自独立曲线。
- **玩家体验/结果**：AB 一开，玩家同时收到 4 类信号（画面变宽、机体被落在后面、全屏径向拉伸、低频抖动+音效提升），大脑把它们合成一个"我在飞"的判断。
- **可复用结论**：任何"速度/力量"的感受，都应该至少拆成 "视场 + 位置关系 + 全屏后处理 + 冲击 + 听觉" 五类通道；只做其中一类一定不够。

## 6. 镜头抖动（Camera Shake）系统

### 6.1 关键发现：抖动与手柄震动同表

本机实测：`PadRumble.param` 的**内部参数类型名是 `CAMERA_RUMBLE_PARAM_ST`**（不是 `PAD_RUMBLE_PARAM_ST`）[B]。共 **174 行 × 84 字节 = 21 个槽**，行 ID 为 `0, 55, 9001, 9002, 9009, 9010, 9020, 9030, …, 9473, …`，即主体是一整块 **9000 段** 的稠密 ID 区块。[B]

这条发现的设计含义（**C**）：AC6 很可能**没有独立的"相机抖动"数据表**，而是把"画面抖动"和"手柄震动"绑在同一条驱动路径上，用一个 ID 同时触发两者。好处是"打击的视觉与触觉永远同步"，坏处是两者不能单独调。

槽位可观察（B）：槽 0 为整型（取 0 / 55 / 65535 / 大整数，疑似类型或 ID）；槽 1 取 `1.0 / 50.0 / −1.0`（−1 = 未启用哨兵）；槽 2 取 `5.0 / 60.0`；槽 4 取 `0 / 0.3 / 1.0`；槽 6 / 7 大量为 `−1.0`；槽 8 取 `100`；槽 10~13 取 `100`（百分比形态）。

| 槽位 | 取值形态 | 候选语义（**D**） |
|---|---|---|
| 0 | 0 / 55 / 65535 / 大整数 | 类型或引用 ID |
| 1 | 1.0 / 50.0 / −1.0 | 时长或强度（−1 = 未用） |
| 2 | 5.0 / 60.0 | 帧数（60 = 1 秒 @60fps）或频率 |
| 4 | 0 / 0.3 / 1.0 | 幅度比率 |
| 6 / 7 | 大量 −1.0 | 未用的左右通道 |
| 8 / 10~13 | 100 | 百分比（100% = 满幅） |

### 6.2 抖动分类表

**强度/时长数值我没有可靠来源，全部标 D 并要求实测。** 下表给出的是"分类 + 衰减形态 + 叠加行为"，这些可以从系统设计常识与引擎默认行为推导（C）。

| 类别 | 触发源 | 强度量级 | 时长量级 | 衰减方式 | 方向性 | 证据 |
|---|---|---|---|---|---|---|
| 开火后坐（枪械） | 每次射击 | 低 | 极短（数帧） | 指数，τ 极小 | 有：沿枪口反方向 + 上抬 | D（数值）/ C（形态） |
| 开火后坐（重武器/榴弹/加农） | 每次射击 | 中~高 | 短 | 指数，可叠加成持续震动 | 沿反方向 + 机身俯仰 | D / C |
| 被命中 | 受击事件 | 中 | 短 | 指数 | 有：沿受击方向（方向性反馈是"我知道谁打我"的关键） | D / C |
| 爆炸 | 爆炸半径内 | 高 | 短~中 | 指数 + 低频正弦混合 | 全向 + 距离衰减 | D / C |
| 落地 / 接地 | 落地事件 | 中 | 极短 | 指数 | 垂直向下 | D / C |
| QB（快速推进） | QB 触发 | 中 | 极短 | 指数 | 沿位移反方向 | D / C |
| AB（突击推进） | AB 持续 | 低但持续 | 持续 | 持续噪声（非衰减） | 全向 + 低频 | D / C |
| Boss 招式 / 地图事件 | 脚本触发 | 高 | 长 | 脚本控制包络 | 全向 | D / C |
| 硬直 / ACS 崩溃 | 姿态崩溃 | 高 | 中 | 指数 + 二次脉冲 | 全向 | D / C |
| 近战命中 | 刀刃命中 | 高 | 短 | 指数 + 顿帧 | 沿突进方向 | D / C |

### 6.3 叠加规则

| 规则 | 做法 | 理由 | 证据 |
|---|---|---|---|
| **求和而非覆盖** | 多个抖动同时触发时，位移/旋转/FOV 偏移做**加法** | 覆盖会让"被大爆炸掩盖的小抖动"消失，损失信息密度 | C（同时也是 UE5 默认行为） |
| **总量钳制** | 求和后对位移与旋转做 clamp | 防止连续爆炸把相机甩到不可读的位置 | C |
| **不同通道分离** | 位移抖动、旋转抖动、FOV 抖动走三条独立累加器 | 允许"只抖画面不转头"（例如后坐只用 FOV+位移，不污染朝向） | C |
| **频率分层** | 高频（后坐/QB）与低频（AB/Boss）分属不同噪声源 | 同一时刻有"细碎抖动"和"整体摇晃"两层，质感来源 | C |
| **衰减独立** | 每个抖动用 `amplitude × exp(−t/τ)` 的独立包络 | 让"短促"和"绵长"共存 | C |
| **触觉同源** | 视觉与手柄震动由同一个 ID 触发（`CAMERA_RUMBLE_PARAM_ST`） | 保证视听触三通道同步 | B（表）+ C（机制） |

**四段式**
- **设计意图**：抖动是"事件通知"通道，不是装饰 —— 它告诉玩家发生了什么事、从哪个方向、有多严重。
- **实现手段**：一张 174 行的 `CAMERA_RUMBLE_PARAM_ST` + 事件系统按 ID 触发；位移/旋转/FOV 三条累加器求和后钳制。
- **玩家体验/结果**：玩家在混战中靠"被抖的方向"定位攻击来源；靠"抖的强度"判断威胁等级。
- **可复用结论**：抖动要按"信息"设计而不是按"效果"设计：先决定这条抖动要传达什么，再决定它的方向、频率分层和时长。

### 6.4 把抖动当"信息通道"来设计

上面按触发源分类是工程视角；但从设计视角，更有用的分类是**按"这条抖动要让玩家知道什么"**：

| 抖动要传达的信息 | 需要的通道特征 | 方向性 | 频率特征 |
|---|---|---|---|
| "我正在开火" | 极短、可叠加成节奏、由玩家自己触发 | 沿枪口反方向 | 高频（枪械）/ 低频（重武器） |
| "我被打了，打我的在左边" | 中等强度、明确方向、不可预测 | 沿受击方向 | 中频 |
| "附近爆炸了，但不一定打到我" | 强度随距离衰减、全向 | 全向 | 低频为主 |
| "我在加速" | 持续、低幅、不衰减 | 全向 | 极低频 |
| "我的姿态崩了" | 高强度、二次脉冲、与画面特效绑定 | 全向 | 宽频 |
| "Boss 出手了" | 高幅、长包络、与音效强绑定 | 全向 | 低频 |

这张表的价值在于：**它把"抖动调到多少"变成了"这条抖动要传达什么信息"**。一旦按信息设计，两个看起来冲突的需求（"开后坐要把画面抖起来"和"抖动不能妨碍瞄准"）就有了明确的解法 —— 开火后坐用"位移 + FOV"通道，不用旋转通道，因为旋转通道会污染弹道方向。[C]

**另一个可观察的设计选择**：从本机数据看，抖动表的行 ID 高度集中在 9000 段（9001~9473 共约 165 个 ID），而 0 和 55 是两个孤立的低 ID 行。[B] 低 ID 行只有 2 个（0 号与 55 号），且它们的槽 1 取值为 1.0 / 50.0（与 9000 段的 −1 哨兵完全不同）—— 这暗示低 ID 是"全局/默认"档，9000 段是"逐事件"档。[D]

## 7. 准星 / 锁定框与真实弹道的关系

### 7.1 玩家看到的"准星"到底代表什么

**结论：AC6 屏幕上至少有 4 种不同的"瞄准指示物"，它们代表的东西完全不同。**[A]

| 指示物 | 代表什么 | 与实际弹道的关系 | 证据 |
|---|---|---|---|
| **中心准星** | FCS 的"当前瞄准方向" | 是弹道的**期望方向**，不是保证落点 | A |
| **锁定框（软锁）** | "该目标目前是可锁候选" | 不保证命中，只保证 FCS 会把弹道往它身上修 | A |
| **硬锁框** | "相机与机体已承诺朝向该目标" | 命中率最高，但仍有散布与提前量误差 | A |
| **命中标记 / 伤害数字** | 事后确认 | 是结果而非预测 | A |

### 7.2 FCS 落点偏差的表达手段

FCS 的偏差在 AC6 里被翻译成"可见的物理事件"而不是"隐藏的随机数"：

| 手段 | 表达内容 | 证据 |
|---|---|---|
| 子弹曳光本身可见 | 玩家能直接看到弹道偏了多少 | A |
| 准星形态/颜色随可锁定性变化 | 告诉玩家"现在能不能锁" | A |
| 锁定框的角标显示锁定进度 | 导弹类武器需要"锁多久"的信息 | A |
| 未锁定时弹道仍沿相机前方射出 | 告诉玩家"没锁也能打，只是不追" | A |
| 命中音效与命中特效 | 事后通道 | A |

**关键设计判断**：AC6 让子弹**可见**（曳光弹、慢速弹丸），因此"准星骗人"这件事不会产生挫败 —— 玩家能看到实际弹道，会自己学会"准星是意图，曳光是事实"。这是把"散布"从惩罚变成可学习系统的做法。[C]

**四段式**
- **设计意图**：让玩家能理解"为什么这一枪没中"，而不是感到随机。
- **实现手段**：可见弹道 + 锁定框状态 + 命中反馈，三层冗余。
- **玩家体验/结果**：散布成为可学习、可配装对抗（换 FCS / 换武器）的对象。
- **可复用结论**：当系统引入随机性时，必须提供一条"可见的因果链"，否则随机性会被感知为不公平。

### 7.3 落点偏差的工程建模（复刻用）

要把"准星 ≠ 弹道"做对，需要把偏差拆成三个来源，它们对相机的要求完全不同：

| 偏差来源 | 物理含义 | 表现 | 对相机的要求 |
|---|---|---|---|
| **静止散布** | 武器固有的弹着圆锥 | 停火时准星不抖，开火时弹道围绕准星散开 | 无（相机不动） |
| **运动惩罚** | 开火瞬间机体的速度/角速度越大，散布锥越开 | 边跑边打命中率下降 | 相机必须让玩家**能读出自己在动**（速度感通道 ①~③ 就是为它服务的） |
| **提前量误差** | 弹丸有飞行时间，移动目标需要预判 | 对高速横移目标必须"打提前量" | 相机不需要变，但**锁定框应该提供"目标速度方向"的暗示** |

第三项是 AC6 里最容易被忽略的：因为弹丸可见且有飞行时间，玩家必须自己学会提前量。相机在这里的角色不是"帮玩家打提前量"，而是**不要妨碍玩家观察目标的速度矢量** —— 这反过来约束了相机：如果相机自身也大幅滞后与晃动，玩家就难以稳定判断目标的横向速度，提前量就变成了猜。所以"速度感"和"可瞄准性"的矛盾，最终落在同一个参数上：**相机的滞后量。** [C]

这也解释了为什么 AC6 把"滞后"做成逐档可调（`LockCamParam` 列 6~10 的比率族，实测 0.01~1.0）—— 不同武器（近战/机枪/榴弹/导弹）需要不同的滞后档位。近战需要跟得紧，重火力可以放得松。[B（列值）+ D（映射）]

## 8. 过场与实机的衔接

本机实测存在 5 张彼此独立的过场参数表 [B]：

| 表 | 内部类型 | 行数 | 行大小 | 大致负责 |
|---|---|---|---|---|
| `CutsceneGparamTimeParam` | （无） | 4 | 12 | 过场的时间/GParam 环境（时段） |
| `CutsceneGparamWeatherParam` | `CUTSCENE_GPARAM_WEATHER_PARAM_ST` | 1 | 36 | 过场的天气环境 |
| `CutsceneMapIdParam` | （无） | 74 | 52 | 过场发生在哪张地图 |
| `CutsceneReplaceSfxParam` | `CUTSCENE_REPLACE_SFX_PARAM_ST` | 38 | 4 | 过场中替换的音效 |
| `SoundCutsceneParam` | `SOUND_CUTSCENE_PARAM_ST` | 105 | 40 | 过场音频混音 |
| `GarageCutsceneParam` | `GARAGE_CUTSCENE_PARAM_ST` | 3 | 80 | 机库内的演出 |

**推断（C）**：过场被拆成"时间/天气/地图/音效/混音"五个可配置维度，说明 AC6 的过场是**引擎内实时演出 + 环境参数切换**，而不是"播一段视频"。这解释了为什么过场与实机的画面风格（光照、天气、粒子）能无缝对上。

**衔接方式（A/C）**：

| 环节 | 做法 | 是否可操作 | 是否无缝 |
|---|---|---|---|
| 任务开场 | 相机切到演出轨道，黑边出现，输入锁定 | 否 | 是（同引擎、同场景） |
| 剧情演出中 | 相机完全由关键帧控制；环境参数由 `Cutscene*` 表切换 | 否 | 是 |
| 演出结束 | `View Target` 混合回玩家相机（blend） | 恢复 | 是（有短混合期） |
| 机库 | 展示镜头 + 子窗口渲染（`SUB_WINDOW_CAM_PARAM_ST`） | 部分（可环绕/切换部件） | 是 |
| 结算 | 相机脱离控制，缓慢运镜，UI 淡入 | 否 | 是 |

**四段式**
- **设计意图**：让演出"长在"实机世界里，避免"切到影片"的断裂。
- **实现手段**：把过场需要的环境参数（时间、天气、地图、音效、混音）全部表化，实时切换。
- **玩家体验/结果**：玩家不会觉得被"踢出游戏"，剧情与战斗的世界感连续。
- **可复用结论**：想做无缝过场，先把"环境参数"从"关卡资产"里解耦成可运行时切换的表。

## 9. 分析三问

### 9.1 如果删掉这套相机（比如改成"相机绑死机体朝向"）会怎样？

| 被删掉的部分 | 直接后果 | 连锁后果 |
|---|---|---|
| 相机与机体的解耦（相机主导） | 转向时画面与机体完全同相，失去"机体追不上我的视线"的质量感 | 机甲被感知为"一个贴图盒子" |
| 相机位置滞后 | AB/QB 变成"地图平移"，速度只能靠环境和音效表达 | 高速机动的观赏性大幅下降 |
| 硬锁 | 高速三维混战中玩家要靠手动跟枪，命中率骤降 | 迫使游戏降低敌人机动性，整体节奏变慢 |
| FOV Kick | 画面恒定，长距离加速缺少视觉线索 | 需要靠 UI 数字/速度表代偿，破坏 HUD 简洁性 |
| 相机抖动 | 玩家失去"被打的方向"的信息 | 混战中被动挨打，反馈链断裂 |
| `LockCamParam` 数据表 | 所有手感硬编码，无法按敌人/章节调 | 平衡迭代成本爆炸 |

### 9.2 如果参数被放大 / 缩小 10 倍会怎样？（设计空间边界）

| 参数 | ×10（放大） | ÷10（缩小） | 结论：可用区间 |
|---|---|---|---|
| **相机距离**（列 0，实测 9~100，均值 ~29） | 距机体 300~1000 m：机体变成屏幕上一粒像素，姿态完全不可读 | 距机体 1~3 m：相机进入机体内部，穿插/穿模 | 可用区间大致在 **10~60 m**；AC6 实测一半以上落在此区间 |
| **FOV 变化量**（列 5，实测 25~60 度） | 单次变化 250~600 度：等效于鱼眼/全景，画面畸变到无法瞄准 | 2.5~6 度：玩家几乎察觉不到 | 可用区间 **10~80 度**；AC6 落在其中段 |
| **位置阻尼比率**（列 6~10，实测 0.01~1.0） | 若把 0.01 的档位放大到 0.1：原本"缓慢漂移"的档位变成"紧跟"，速度感消失 | 若把 0.3 缩到 0.03：相机严重滞后，高速时看不到自己 | 可用区间跨两个数量级，**AC6 的 0.01~1.0 已覆盖**；关键在"逐档分配"而非单值 |
| **抖动强度** | 相机位移数十米：画面完全不可用 | 抖动不可见：事件反馈消失 | 上限由"目标是否仍在屏幕内"决定，无固定值 |
| **抖动时长** | 数秒：持续晕眩，方向信息被抹平 | 单帧：看不出方向 | 上限由"下一次同类事件的平均间隔"决定 |
| **Zoomblur 强度**（实测 0.0025~0.02） | 0.025~0.2：全屏糊成一片，丧失可读性 | 0.00025~0.002：几乎不可见 | AC6 的 **0.0025~0.02** 本身就是"刚好可感知"的区间，跨 8 倍 |
| **最大锁定半径**（列 4，9999 = 哨兵） | 若把 9999 当作真实值：锁定范围 10 km，整个战场都锁得住 | 若把均值 40 缩小到 4：只有贴脸能锁 | 哨兵值的存在说明：**这个字段的设计意图包含"无限"这一档** |

### 9.3 它到底在解决什么问题？有没有更简单的替代方案？

**核心问题**：在三维高速机动 + 多目标的混战中，让玩家同时获得"我机体在哪、朝哪"和"我要打谁、打得到吗"两组信息，且两组信息不能互相污染。

| 替代方案 | 为什么看起来更简单 | 为什么 AC6 没用它 |
|---|---|---|
| **第一人称座舱视角** | 直接消除"看清自己"的需求（座舱即自己） | 机甲姿态（腿部/推进器方向）本身就是玩法信息，座舱会切断它；且机动观赏性归零 |
| **俯视 / 等距视角** | 三维朝向问题降维成二维，锁定极其简单 | 失去机甲的尺度感与垂直机动（AC6 的空中战斗是核心） |
| **"永远硬锁"（自动锁死最近敌人）** | 删掉整个软锁/硬锁状态机 | 玩家失去目标选择权，无法"先打脆皮"；也无法表达技巧 |
| **"永远软锁"（只做角度吸附）** | 删掉硬锁，简化输入 | 高速三维混战中手动跟枪不可行，会迫使敌人降速 |
| **准星=弹道（无 FCS）** | 删掉整个散布/仲裁层 | 机甲武器的后坐/散射是"重"的核心表达，删掉等于删掉武器性格 |
| **相机完全硬编码** | 删掉 `LockCamParam` | 无法按敌人/章节/Boss 调整手感，且无法做数据驱动的平衡迭代 |

**结论**：AC6 的方案在"信息完整性"和"实现成本"之间选了偏前者的一侧；替代方案都能省成本，但每一条都会砍掉一个已经存在的玩法维度（垂直机动 / 目标选择 / 武器性格 / 观赏性）。[C]

## 10. TA 转化：在 UE5 里复刻这套机甲相机

### 10.1 组件清单

| # | 组件 / 节点 | 具体做法 | 对应 AC6 的哪一块 |
|---|---|---|---|
| 1 | `USpringArmComponent`（位置） | 设 `TargetArmLength`（对应 `LockCamParam` 列 0，先取 25 m 量级）；开 `bEnableCameraLag=true` + `CameraLagSpeed`（低→滞后大）；`CameraLagMaxDistance` 限制极端情况下的拉伸 | 常规跟随的距离与位置滞后 |
| 2 | **自定义临界阻尼弹簧**（替代 SpringArm lag） | `FMath::SpringInterp(Current, Target, SpringState, Stiffness, CriticalDamping, DeltaTime)` —— SpringArm 的 lag 只沿 arm 轴插值，无法表达"侧向 QB 的甩尾"，所以位置滞后建议自己写：每帧把"机体位置 + 偏移"作为 Target，做一次 spring | QB / AB 的位置滞后 |
| 3 | 双弹簧旋转（yaw 快 / pitch 慢） | 两个独立 `FRotator` 弹簧，yaw 的 Stiffness 高于 pitch；或用 `FMath::RInterpTo` + 不同 `InterpSpeed` | 相机旋转阻尼、朝向解耦 |
| 4 | **速度前瞻 Look-ahead** | 在 spring 的 Target 上叠加 `Velocity * LeadTime`（夹在最大值内）；速度来自 `GetVelocity()` 或推进状态 | AB/高速时的前瞻 |
| 5 | `UCameraComponent` + `SetFieldOfView` | 用 `UCurveFloat`（横轴 = 归一化速度或"是否 AB"）驱动 FOV；或写 `UCameraModifier` 在 `ModifyCamera` 里做 **FOV 加法**（这样多个来源可以叠加） | FOV Kick |
| 6 | **数据表** `UDataTable`（`FTableRowBase`） | 把 `LockCamParam` 的 94 列结构化成 struct，行按"锁定档位 ID"寻址；运行时按当前目标/章节选行 → 这是复刻手感最快的路径 | `LOCK_CAM_PARAM_ST` |
| 7 | 相机状态机组件 | `UENUM` 12 个状态 + `UStateTreeComponent` 或简单 `Switch on Enum`；每个状态持有一份"参数覆盖"（距离、滞后、FOV 曲线、抖动模板 ID） | 第 2 节状态机 |
| 8 | 抖动：`UCameraShakeBase` 子类 × N | 每类抖动一个 Shake 类（后坐/受击/爆炸/QB/AB…），用 `UCameraModifier_CameraShake` 的默认行为；**叠加规则**：UE 默认在 `UCameraModifier_CameraShake::ModifyCamera` 中把同帧活跃 shake 的位移/旋转/FOV **求和**后应用（可直接读引擎源码核对），需要更细的控制就自己写 `UCameraModifier`，按"高频层 + 低频层"两个累加器分别求和再 clamp | 第 6 节抖动系统 |
| 9 | 抖动衰减 | 每个 Shake 用 `Amplitude * FMath::Exp(-Elapsed/Tau)` 的包络（指数）；"持续型"（AB）改用 `PerlinNoise1D` 类型的持续噪声，不做衰减 | 衰减与叠加 |
| 10 | 后处理：径向模糊材质 | Post Process Material：`ScreenPosition` → 减屏幕中心 → `length` → `pow(len, Exponent)` → 乘 `Strength` → 沿该向量偏移 UV 采样 `PostProcessInput0`。**这两个参数直接对应 `ZOOM_BLUR_ST` 的槽 1/槽 2** | Zoomblur |
| 11 | 后处理驱动 | 用 `APostProcessVolume`（Unbound）+ `WeightedBlendables`，或 `UCameraComponent::PostProcessSettings.AddOrUpdateBlendable`；权重由相机状态机每帧写 | 战斗状态驱动后处理 |
| 12 | 锁定框 / 准星 UI | `ProjectWorldToScreen` 算目标屏幕位置；框的角尺寸按 `1/Distance` 缩放（透视投影下目标角尺寸恒定 → 屏幕像素尺寸与距离成反比）；用 `UWidgetComponent`（Screen 空间）或 HUD `DrawLine` | 第 7 节 |
| 13 | 瞄准仲裁层 | 建一个 `UFCSComponent`：输入"相机朝向 + 目标列表 + FCS 属性"，输出"实际发射方向"；散布用锥形随机采样（`FMath::VRandCone`） | FCS 与弹道 |
| 14 | 过场：`LevelSequence` + `CineCameraActor` | Sequencer 的 Camera Cut Track + `SetViewTargetWithBlend` 进出；用 `SetCinematicMode` 屏蔽输入；环境（时间/天气/音效）用 `DataTable` 切换 → 对应 `Cutscene*` 五张表 | 第 8 节过场 |
| 15 | 机库镜头 | `USceneComponent` 做 pivot + `AddControllerYawInput/Pitch` 环绕；配合 `SceneCaptureComponent2D` 做部件预览子窗口 → 对应 `SUB_WINDOW_CAM_PARAM_ST` | 机库 |
| 16 | 调试与调参 | 做一个运行时面板（`UMG` + `ConsoleVariable`）实时改距离/滞后/FOV/抖动，并支持"导出为 DataTable 行" | 复刻 AC6 的调参工作流 |

### 10.2 关键实现陷阱

| 陷阱 | 现象 | 解法 |
|---|---|---|
| 用 `DeltaTime` 直接插值导致帧率相关 | 120 fps 下相机比 60 fps 更"跟手" | 用 `FMath::SpringInterp`（半隐式欧拉，帧率无关）或 `1-exp(-k*dt)` 形式的插值 |
| SpringArm 的 `CameraLag` 与目标锁定冲突 | 硬锁时相机滞后导致目标偏离画面中心 | 硬锁状态下把 spring 的 Stiffness 拉到很高（近似刚性），或直接对"目标点"而非"机体"做弹簧 |
| 抖动污染瞄准 | 抖动直接改相机 rotation 会让弹道跟着抖 | 位移抖动与旋转抖动分离；弹道用"未抖动的相机朝向"计算，或用 `AimDir` 单独维护 |
| FOV 与径向模糊脱节 | FOV 拉大但模糊没跟上，画面"干净地变宽" | 把 FOV 与 Zoomblur 强度绑到同一个 `Speed01` 曲线，保证同步 |
| 过场混合期输入泄漏 | 玩家在 blend 期间仍能开火 | `SetCinematicMode` + 输入路由到 Sequence |

### 10.3 标定流程：如何把 UE5 的参数对齐到 AC6

复刻的最大障碍不是写代码，而是**没有 AC6 的原始数值**。可执行的标定流程如下（这套流程本身就是一个可以放进作品集的工具）：

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1 | 固定一个可复现的场景（同一关卡、同一机体、同一目标），录制 60/120 fps 的素材 | 基准素材 |
| 2 | 让机体静止，量出机体在屏幕中的像素高度 → 结合已知机体高度反推**相机距离** | 距离标定值 |
| 3 | 让目标在同一距离上横移，量出锁定框从"出现"到"吸附"的屏幕角度范围 → 反推**锁定角度锥** | 角度标定值 |
| 4 | 触发 AB，逐帧量同一远处物体的像素尺寸变化 → 反推 **FOV 曲线**（`像素尺寸 ∝ 1/tan(FOV/2)`） | FOV 曲线关键帧 |
| 5 | 触发 QB，逐帧量机体在屏幕中的横向位移与相机横向位移之差 → 反推**位置滞后的时间常数** | 弹簧参数 |
| 6 | 触发各类事件，用"画面特征点位移"逐帧量抖动幅度 → 得到**抖动包络** | Shake 类参数 |
| 7 | 把上面所有结果写回 `UDataTable`（结构对齐 `LockCamParam` 的列语义） | 可复用数据资产 |

这套流程的关键是**第 4 步**：透视投影下，同一物体的屏幕像素尺寸与 `1/tan(FOV/2)` 成正比。只要有一个距离已知的参照物，就能从像素变化反解 FOV 变化，**不需要读取游戏内存**。这是把"感觉"变成"数字"的最实用技巧。[C]

## 13. 一页速查

- **AC6 相机的本质**：不是瞄准工具，是"姿态可读性 + 冲击力翻译器"；瞄准外包给 FCS。
- **数据骨架**：`LockCamParam` 98×94（B）、`EquipParamFcs` 19×52（B）、`Zoomblur` 7×8（B）、`PadRumble`/`CAMERA_RUMBLE_PARAM_ST` 174×21（B）、`SubWindowCamParam` 2×22（B）、`GarageCameraAnimParam` 7×49（B）、`DirectionCameraParam` 6×5（B）、`ChrActTurnParam` 258×42（B）。
- **速度感 = 8 条通道的和**：FOV、位置滞后、旋转滞后、粒子、全屏后处理、抖动、音效、帧内位移。
- **抖动的核心洞见**：视觉与触觉同表（`CAMERA_RUMBLE_PARAM_ST`），叠加用求和 + 钳制 + 频率分层。
- **TA 复刻的最短路径**：先确认 `LockCamParam` 列语义 → 做成 `UDataTable` → SpringArm + 自定义 spring + FOV 曲线 + Shake 类 + 径向模糊 PP 材质 + 相机状态机，六件套即可复现 80% 的手感。
