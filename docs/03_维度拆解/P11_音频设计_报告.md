# 《装甲核心 6：境界天火》音频设计拆解（P11 · 音频总监 / 技术音频视角）

> 读者设定：大四，目标技术美术（TA），从策划岗入门。
> 本文所有"实测"结论均附本机执行的命令与原始输出；证据分级 A/B/C/D 见 §0.3。
> **重要边界**：regulation 里只有"喂给音频中间件的参数"，**没有** Wwise 工程本体（Event / Switch Container / AuxBus / SoundBank）。因此本文凡是谈"混音总线、ducking、优先级树"的部分，只能靠表里暴露出来的**接口面**反向推断，我会逐条标注级别。

## 0. 结论先行

1. **中间件 = Wwise，且是"数据表直连"式集成。** 本机 regulation 里有 **14 张 `WwiseValueToStrParam_*` 表**，每行是一个 `fixstr[32]`，paramdex 的 `<ParamType>` 直接写着 `WWISE_VALUE_TO_STR_CONVERT_PARAM_ST`，日文显示名是「Wwise 参数文字列」。也就是说：**游戏侧算出一个整数，查表变成 Wwise 的 Switch/State 名字符串，再喂给 Wwise**。这是"游戏数值 → Wwise 字符串"的转换层，共 5 条独立铁证（§2）。
2. **AC6 的音频不是"播一段声音"，而是"一张状态机"。** `RuntimeSoundParam_Pc` 的 165 行按 **4 种脚部类型**（行 ID 0/100/200/300）分组、每组 **41 个 ConditionID**；播放行为本身被枚举成 `RUNTIME_SOUND_PLAYER_TYPE` 的 13 个原型（飛行音/動作音/起動音/ワンショット/爆破破片/キャタピラ/ダーティー動作音/ブースト音…）。
3. **"信息性音频"在数据层有实证：声音是 AI 的输入，不只是玩家的 output。** `AiSoundParam` 34 行，每行一个**以米为单位的听觉半径**（30 / 100 / 150 m，`radius` 字段），`priority=300`；`AtkParam_Pc` 里 712 行中有 **441 行 `AppearAiSoundId = 2100`、646 行 `HitAiSoundId = 2010`**——攻击动作会向 AI 广播一个"声事件"。玩家听到的警报音，敌方 AI 也"听到"同类事件。
4. **"几吨重的机器"来自三个可测的通道**：① RTPC `acceleration`（0–300，per-area 注册）驱动ブースト/キャタピラ循环音的滤波与音量；② 脚部类型（`legTypeSeId ∈ {0,100,200,210}`）整组替换脚步/移动音色；③ 距离分层的三变体 SfxId（`410000 / 411000 / 412000`，固定 +1000/+2000 步长）。
5. **手柄震动与"视觉抖动"同源，且是空间化的。** `PadRumble` 174 行 × 84 字节，文件尾内部类型名是 `CAMERA_RUMBLE_PARAM_ST`；paramdex 定义里有 `beginDist` / `endDist`（衰减开始/结束距离，实测均值 690 m / 1638 m）、`priority`（9 种取值）、`airRateSelf` / `landRateSelf` / `airRateAnother` / `landRateAnother`（自己 vs 对手、空中 vs 地面分别给倍率）。**它不是"按键马达响一下"，是一个跟音频同构的、带距离衰减与优先级的反馈通道。**
6. **动态混响是"自动测量 + 距离分档"选出来的，不是手摆球体触发器。** `SoundAutoReverbEvaluationDistParam`（6 行）定义"如何从一堆碰撞点算出一个代表距离"（收集/排除哪些点、点寿命 1.0~1.8 s、最多记录 10/15/20 个点、最大距离间值 0/1/2/5）；`SoundAutoReverbSelectParam`（5 行）把距离分档映射到混响预设：**50–290 m → Room2_Little，290–620 → Room3_Middle，620–900 → Room5_Large，900–1024 → Room7_HugeLarge，室外默认 → Room0_Dry**。
7. **BGM 是"状态"而非"曲目"。** `WwiseValueToStrParam_Switch_BGMStatus` 只有 8 行：`normal / in_combat / heat_up_1..5 / death`（原表内文本，全小写下划线）。**"Heat Up 1–5" 意味着战斗音乐有 5 级强度层**；`SoundCutsceneParam`（105 行）负责过场前后把状态机推回去（`BgmEnemyTypeOnEnd` 实测 = 13000 / 21531 / 22100 / 21560 / 23100）。
8. **有一整套"声音预算"硬约束写在数据里**：`GameSystemParam.Net_MapHitSfxOmitteDist = 600 m`（联机对战中超过 600 m 的地图着弹音直接省略）、`Net_MyTeamHitSfxOmitteCpuExecRate = 1.2`（省略判定本身的执行频率）、`SoundParam.BulletHitSoundRestrictionTime = 0.56 s`（弹着音最短重播间隔）、`AtkParam_Pc.soundRestrictionSec` 有 329 行非零（0.2/0.3/0.45 s 等 6 档）。
9. **SfxId 是可读的数字地址，不是哈希。** `FootSfxParam` 26 行（行 ID = 材质，与 `Switch_Material` 同一命名空间）× 211 个槽，`SfxId = 1×10⁵ + 材质ID×10³ + 槽号`：石=`101000`、铁=`111000`、水=`120000`。`TentativePlayerParam` 的日文注释直接写明「XYYZZZ」的编码规则。**这让声音资源可以用"地址"反查用途，是 TA 级的设计决策。**
10. **不是所有字段都在用。** `NpcParam.SfxResBankId` 在 1232 行里**全是 −1**、`sfxSize` 全是 0（普通）、`isHitRumble` 位**0/1232 置位**。魂系继承下来的布局留着，但 AC6 没启用（§13 不确定项 #8 的诚实边界）。

## 2. 中间件判定：为什么可以断定是 Wwise

| # | 证据 | 原始出处 | 级别 |
|---|---|---|---|
| 1 | regulation 中存在 **14 张 `WwiseValueToStrParam_*.param`** | `ls van/regulation-bin \| grep Wwise` | B |
| 2 | 这 14 张的结构定义 `<ParamType>` = `WWISE_VALUE_TO_STR_CONVERT_PARAM_ST`，字段只有 `fixstr ParamStr[32]`，日文名「Wwiseパラメータ文字列」 | `Defs/WwiseValueToStrConvertParamFormat.xml` | B |
| 3 | `SoundVoiceBankLoad.param` 的**文件尾内部类型名** = `WWISE_VALUE_TO_STR_CONVERT_W_PARAM_ST`（宽字符版，`fixstrW[32]`=64 字节），实测 66 行 × 64 字节，内容是 `NPC000…NPC257` 的 **Voice SoundBank 名** | 文件尾字符串 + 实测 dump | B |
| 4 | 声音分类枚举里有一项 `d：wwiseダイナミックダイアログ`（值 15），且 `SoundIDSpatialSetting` 6 行全部用 15 | `Tdfs/Sound_Type.tdf` + 实测 | B |
| 5 | 表里存的是**小写下划线命名的 Switch 值字符串**（`shot_gan` / `energy_shield` / `heat_up_3` / `assault_armor`），这是 Wwise Switch 的正常用法，不是 FMOD 的参数路径（FMOD 参数通常以 `parameter:/` 路径出现） | 实测 dump | B |

**判定**：中间件 = **Wwise**（Audiokinetic）。**集成方式 = "数据表直连"**：C++ 侧只负责"算出一个整数"，`WwiseValueToStrParam_*` 把它翻译成 Wwise 参数名，再 `SetSwitch/SetState/SetRTPCValue`。**这套设计的收益是：换声音不用改代码，改表即可；代价是表与 Wwise 工程必须严格同步，任何一侧改名都会静默失效（这是 TA 要负责的"契约"）。**

### 2.1 这个架构选择意味着什么（四段式）

**设计意图**：让音频设计师（而不是程序员）拥有"什么情况响什么声"的最终控制权。在 AC6 这种"零件组合爆炸"的游戏里（腿 × 发电机 × 武器 × 弹种），硬编码的 `if/else` 是不可维护的。

**实现手段（可观察到的）**：把"游戏状态"压缩成一个整数，让 Wwise 侧的 Switch/State 去展开。例如武器的音色选择被拆成 4 个正交维度——`Weapon_Type`（14 值：步枪/霰弹/机枪/火箭筒/狙击/加农/导弹/刺刀/激光…）、`ShootSeCategory`（38 值：含 Pulse/Laser/Plasma 各自的 Handgun/Rifle/Cannon/Machinegun/Shotgun/Bomb 变体）、`WeaponMaterial`（17 值：铁/火/眩晕/EMP/冰/绿 EN/珊瑚/突击装甲/Pulse/Laser/Plasma）、`AttackPowerType`（3 值：小/大/特大，原表字符串 `pow_s/pow_l/pow_ll`）。同一次开火会同时喂这 4 个 Switch，Wwise 侧做**笛卡尔积的 Switch Container 嵌套**。命中侧则用 `HitEffectSfxConceptParam` 做"攻方概念 × 守方概念"的二维查表（12 种攻方概念 × 行 ID 对应的守方概念），查到 `HitEffectSfxParam` 的某一行，再从 25 个槽里按"斩击/刺突/打击/爆风/弹丸 × 小中大特大特特大"取值。

**玩家体验/结果**：玩家不需要知道"这是 Pulse 还是 Laser 的哪一档"，只需要听出来"这把枪不一样"。而因为有 `pow_s/pow_l/pow_ll` 这一维，**同一把枪打在不同血量的敌人身上，反馈音也不同**。

**可复用结论**：**音频参数的维度要正交，不要做成一棵大树。** 如果你的音效切换逻辑是一棵 10 层的 `if` 树，说明你没有把维度拆开。AC6 的做法是"4–5 个独立维度同时生效"，这既让数据表保持小（14/38/17/3 行），又让组合空间足够大。

### 2.2 代价：静默失效是这套架构的固有风险

上一条说"改表即可"，但反过来看：**表里写的是字符串，Wwise 工程里同名对象一旦消失，`SetSwitch` 就静默失败，不报错、不崩溃，只是没声音。** 14 张表、共计约 400 行字符串，加上 9 张 Switch 表之外的 RTPC 名字符串（`RuntimeSoundParam_*.RTPC01_ID[16]` 实测只出现 `acceleration` 与 `motion` 两种），构成一份**隐式契约**。这就是为什么这个岗位叫"技术音频/音频 TA"而不是"音效师"——**你需要写工具去校验"表里的每个字符串在 Wwise 工程里都存在"**，否则一个改名会让某个武器整整一个版本没有音效，而且没人能靠听发现问题（因为"没声音"和"没触发"在 QA 眼里是同一件事）。

## 4. ★ 信息性音频：为什么这些信息用耳朵而不是眼睛

### 4.1 先把"哪些信息是声音"列出来

| 信息 | 载体（可验证程度） | 为什么要用声音 |
|---|---|---|
| **锁定 / 软锁定抓取与释放** | 社区逐项观察（B，Carter Menary 的对照表：soft lock 抓取/释放、进入/离开武器最佳射程触发红色准星、导弹锁定，各自有**独立的 chirp**） | 准星在屏幕中心，锁定目标可能在**屏幕外或边缘**；视觉需要"转移视线"，声音不需要 |
| **导弹来袭警报** | 社区观察（B）明确写到「warning beeps that tell the player to get out of the way of a big or explosive incoming projectile」，并指出这些警报被**混音推到很前面** | 来袭方向可能在背后/侧方；声音提供**方位 + 时间紧迫度**两维信息，视觉只给"有东西来了" |
| **姿态崩溃（ACS/SA 崩溃）** | `Tdfs/ActionSoundTypeEnum.tdf` 有独立动作态 `"ガードブレイク","7"` 与 `"SAブレイク","22"`（还有两个 debug 强制版 25/26） | 崩溃瞬间玩家视线常被特效占据；崩溃是**状态切换**，听觉是持续可感知的通道 |
| **EN 耗尽 / EN 回复延迟** | 表中有 `EquipParamGenerator.energyRecoveryDelayTimeForEmptySec`、`energyRecoverValForEmpty`（P2 已实测）；且 `RuntimeSoundGlobalParam` 注册的全局 RTPC 是 `acceleration`（0–300）——**声学状态与机械状态共用同一套量** | EN 是资源，不是事件；听觉能做**连续量**（音高/滤波随 EN 变化），视觉只能给离散 UI |
| **敌人充能预警** | `AtkParam_Pc` 的 `AppearAiSoundId = 2100`（441 行）、`HitAiSoundId = 2010`（646 行）——**攻击动作自带 AI 声事件 ID**；`AiSoundParam` 34 行的听觉半径 30/100/150 m | 蓄力常有 1–2 s 前摇，视觉上只是"炮口亮了"；**声音可以抢在动画关键帧之前**给玩家反应窗口 |

### 4.2 声音的信息带宽优势（拆成可操作的 3 条）

**① 全向通道，不占用中央凹。** AC6 的战斗里玩家视线几乎恒定锁在准星+目标上。声音是**唯一的 360° 通道**：`PadRumble` 的 `targetType =「全て/PCのみ」`、`SoundIDSpatialSetting` 的 `ReflectLv`、`SoundAutoReverb*` 的室内外分档，全部服务于"这个声音从哪来"。

**② 时间分辨率高于视觉刷新。** 动画/战斗演出跑 30 Hz（P7 实测），意味着一帧 33 ms。而声音的事件分辨率可以做到毫秒级。`AtkParam_Pc.criticalHitSfxRestrictionSec` 只有 0.3（2 行）、而 `SoundParam.EffectiveHitSEDelayTime = 0.6 s`——**开发者专门给"致命一击音"留了一个 0.6 秒的延迟预算**，因为它必须在最恰当的瞬间出现，而不是跟着命中帧。

**③ 并行信道数远高于视觉。** 视觉同一时刻只能突出一个焦点；听觉可以同时承载"BGM 强度 + 来袭警报 + 队友语音 + 自身推进器"。数据层的证据是 **SlotNo 体系**：`RuntimeSoundParam_Pc` 用 −1/0–6 槽，`RuntimeSoundParam_Npc` 用 −1/0–90 槽——**共 90+ 个并发槽位是显式编号的**。

### 4.3 静音会损失什么：把"信息通道"还原成可计数的量

先给一个可计数的口径。`RuntimeSoundParam_Pc` + `RuntimeSoundParam_Npc` 合计 425 行（165 + 260），映射到 **184 个唯一 SeID**（Pc 43 个、Npc 142 个，两个集合唯一共有者只有 `0`）。`HitEffectSfxParam` 有 53 个非空行，**每行非零 SfxId 槽数实测 min 10 / max 20 / 均值 19.8 / 中位 20**。再加上 `FootSfxParam` 的 26 材质 × 51 有效槽、`ThrustersSfxIdParam_Pc` 的 22 行 × 3 层，可以估计 AC6 在战斗中最常触发的声音类别是**百量级**、实际资产是**千量级**。这不是"配乐好听不好听"的问题，而是**一条并行度远超视觉的信息总线**。

静音之后，玩家并不会"体验到更差的打击感"这种模糊描述——会发生的是下面三件具体的事：

**第一，方位信息归零。** 声音是 360° 的，视觉是约 100° FOV 的。工程侧的证据是 `PadRumble` 的 `targetType`（`全て / PCのみ`）、`SoundIDSpatialSetting.ReflectLv`、以及 `SoundAutoReverbSelectParam` 的室内外分档——**整个空间化管线只服务听觉**。静音等于把"背后有导弹"这条信息删掉，玩家只能等屏幕边缘的红色指示器，而那个指示器本身出现得比声音晚。

**第二，提前量归零。** AC6 的战斗演出跑 30 Hz（P7 实测），一帧 33 ms。`SoundParam.EffectiveHitSEDelayTime = 0.6 s` 这个数字很说明问题：开发组为一个"致命一击音"专门留了 0.6 秒的延迟预算，意味着**这个声音必须精确地落在某个瞬间，而不是跟着动画帧走**。静音后玩家失去的正是这种"在正确瞬间出现的提示"，而这些瞬间往往早于视觉的关键帧。

**第三，双向信息变成单向。** 这是最容易被忽略的一点：`AiSoundParam` 34 行证明**声音是敌方 AI 的输入**（`radius` 30/100/150 m、`priority` 300、`opposeTarget` 33/34 置位、`lifeFrame` 1 秒存活）。玩家听到的推进器音、脚步音，同时也是 AI 判定"你在哪、你在干什么"的依据。静音玩不会让 AI 失聪，但会让玩家**失去对"我是否暴露"的自我监控能力**——你会反复怀疑"我刚才那一下是不是被听到了"，因为没有听觉反馈来确认。

把三条合起来：**静音玩 AC6 不是"少了氛围"，而是把一个三通道信息流（方位 + 时机 + 自我状态）砍到只剩视觉单通道，同时保留了一个仍在使用声音的 AI。** 这就是为什么 §6.2 里那些"把警报推到混音最前"的设计是刚需而不是锦上添花。

具体的损失清单（逐条给依据与级别）：

| 损失 | 依据 | 级别 |
|---|---|---|
| 失去"背后/侧方来袭"的方位信息，只能靠伤害数字与屏幕边缘指示 | 社区观察指出警报音被推到混音最前；`PadRumble` 有 `targetType` 与距离衰减 | C |
| 失去"提前量"：蓄力/装填/推进器起动的**起点音**永远早于视觉关键帧 | `AtkParam_Pc.AppearAiSoundId` 存在于 441/712 行 | C |
| 失去"机械状态连续量"：加速、EN 债、PA 展开中 | `RuntimeSoundGlobalParam` 注册 `acceleration`(0–300)，`RuntimeSoundParam_*` 用 `RTPC1_ValueChangeDuration=100 ms` 平滑 | B（数据）/C（体验） |
| **失去"反制 AI 的线索"**：`AiSoundParam` 说明声音是 AI 的**输入**。玩家能听到的、与自己行为绑定的声音，同时也是敌方 AI 的索敌依据——静音玩家会**误判自己是否暴露** | `AiSoundParam` 34 行、`AtkParam_Pc.HitAiSoundId` | C |

> **诚实边界（D）**：锁定提示音、导弹警报音**具体哪个 SeID**，regulation 里查不到——它们是运行时由游戏代码直接 Post 的事件（`SoundIDSpatialSetting` 里的 6 个 ID `30100/30200/30300/30400/30500/10100` 全部归类为 15「wwiseダイナミックダイアログ」，且 `30100/30200/30400` 在 `RuntimeSoundParam_Pc` 中被 4/1/2 个 ConditionID 复用，**不能据此断定它们是警报音**）。
> **验证方法**：dump 游戏内存中的 Wwise Event 调用日志（需 Instrumented build 或 Cheat Engine 挂 Wwise 的 `PostEvent`），或解包 PC 版 `.pck`/SoundBank 后按 ID 反查 Event 名。

## 5. 机甲音效方法论："几吨重的机器"怎么做出来

### 5.1 六条可测通道

| # | 手法 | 本机证据 | 级别 |
|---|---|---|---|
| 1 | **低频冲击 / 量感** | `PadRumble` 与 `CAMERA_RUMBLE_PARAM_ST` 共用结构；`lifeTimeSec` 最大 99 s、`changeTime` 最大 5 s。低频能量靠**震动通道 + 相机 FOV（`fovApplyType 加算/上書き`）**做超听觉加固 | B |
| 2 | **金属共振** | `Switch_Material` 115 行把材质分成 `iron / heavy_iron / iron_shield / energy_shield / coral_shield` 等；`HitEffectSfxConceptParam` 里**攻方材质（atkIron/atkPulse/atkLaser/atkPlusma/atkCoral…）× 守方材质** 做二维查表 → `HitEffectSfxParam` 的 71 行 | B |
| 3 | **伺服 / 液压（动作机械）** | `ActionSoundTypeEnum` 39 项：`歩行/走行/ダッシュ/ブーストダッシュ/ブースト飛行/QB/ガードブレイク/着地/ドスン着地/ドリフト/旋回/壁激突ダメージ…`。「ドスン着地」是**独立于「着地」的第二档落地** | B |
| 4 | **延迟与层次叠加** | `ThrustersSfxIdParam_PC` 每行存 **3 个 SfxId**（`410000 → 410000/411000/412000`，固定 +1000/+2000 步长）。推断为**同一推进器的三级距离细节层**；`SOUND_PARAM_ST` 里 `BulletHitSoundRestrictionTime = 0.56 s`、有效距离 10000 m | B（数据）/C（语义） |
| 5 | **素材变形处理** | `RuntimeSoundParam_*` 的 `RTPC01_ValueChangeDuration` 实测 **100 ms（155/165 行）**、0 ms(6)、1 ms(4)。这就是"同一个循环音源，被加速度参数在 100 ms 内连续做滤波/音量变形"的痕迹；`RuntimeSoundExpressionParam_Pc`（677 行）更进一步——**用 7 个条件做布尔表达式**（`RuntimeSoundOperatorType`：かつ/または/【/】），在数据层写"混合逻辑" | B |
| 6 | **体量 = 距离与倍率** | `PadRumble.airRateSelf / landRateSelf / airRateAnother / landRateAnother`：**自己 vs 对手、空中 vs 地面** 各 0–100 %；`beginDist` 均值 690 m、`endDist` 均值 1638 m。**"重"被数字化成"距离不衰减 + 对手侧倍率"** | B |

### 5.2 四段式

- **设计意图**：让玩家"用耳朵判断自己开的是什么机器、重量多少、当前处于什么状态"，从而省掉看 HUD。
- **实现手段**：
  - **脚部类型整组替换**：`EquipParamProtector.legTypeSeId` 实测只有 4 个取值 `{0:107 行, 100:9, 200:4, 210:1}`，正好对上 `RuntimeSoundParam_Pc` 的行 ID 分组 `{0 / 100 / 200 / 300}`。**换腿 = 换一整套 41 个动作音**。
  - **材质层 × 动作层**：`FootSfxParam` 26 行（材质）× 211 槽（动作/脚型组合），实测"被任一材质使用的槽位 = 51 / 211"——即 **51 个槽是真正在用的，160 个是预留**。
  - **速度分层**：`TentativePlayerParam.turnFootSfx_MinSpeedKMH = 30` / `MaxSpeedKMH = 250`、`MinTurnSpeed = 30 deg/s` / `MaxTurnSpeed = 80 deg/s`——**旋回足元音在 30→250 km/h 之间线性增强**。这是"同一个循环音 + 速度 RTPC"的直接证据。
  - **生成器分色**：`EquipParamGenerator.criticalDefSfxMaterial` 实测 `109（ジェネレーター_通常）13 行` / `110（ジェネレーター_コーラル）3 行` / `0 8 行`——**珊瑚发电机被致命一击时的音色确实不同**（这与社区观察"coral generator 听起来不一样"完全吻合）。
- **玩家体验/结果**：不用看 UI 就能判断"我现在有多快""我的腿是什么""我的发电机是不是珊瑚"。
- **可复用结论**：**"重"不是靠把音量调大，是靠①低频+震动双通道 ②距离不衰减 ③同一事件的多层变体**。把"体量"写成参数（`beginDist`/`endDist`/`airRate`/`landRate`）而不是靠美术听感调，是这个体系最值得学的地方。

## 6. 混音：语音清晰 vs 爆炸够猛

### 6.1 数据层能证明的三件事

| 机制 | 实测证据 |
|---|---|
| **独占槽位（= 并发上限）** | `RuntimeSoundParam_*.SlotNo`：Pc 用 −1/0/1/2/3/4/5/6；Npc 用 −1/0/1/2/3/5/15/20/30/31/…/36/40/90。**不同来源走了不同的槽位段**，等于把"自机 / NPC / 爆炸 / 语音"分开排队 |
| **重播冷却（= 防止糊）** | `SoundParam`：`BulletHitSoundRestrictionTime = 0.56 s`（弹着音最短重播间隔）、有效距离 10000 m；`CounterBoostPlayInterval = 0.4 s`；`EffectiveHitSEDelayTime = 0.6 s`。`AtkParam_Pc`：`soundRestrictionSec` 6 档最大 0.45 s（329/712 行非零）、`soundLandingRestrictionSec` 最大 1.0 s（239 行）、`soundFlyRestrictionSec` 最大 1.0 s（165 行） |
| **距离/负载剔除（= 预算）** | `GameSystemParam.Net_MapHitSfxOmitteDist = 600 m`、`Net_MyTeamHitSfxOmitteCpuExecRate = 1.2`。**联机对战里，超出 600 m 的地图着弹音直接不发**——这是"用音频预算换 CPU/带宽"的明牌 |

### 6.2 侧链 ducking（C 级推断链）

**推断**：`RuntimeSoundExpressionParam_Pc` 有 **677 行**、`Npc` 有 **459 行**，字段包括 `Expression`（8 种布尔结构）、`RTPC_OnOff`、`Eval01_Condition`（60 种）、`Eval01_MinValue/MaxValue`、`RTPC_MinValue/MaxValue`、`ConditionID`。实测 `Expression=1`（=`(A|B|C|D|E|F|G)` 的"任一条件"）在 Pc 占 506/677 行；`RTPC_OnOff=1` 有 18 行；`RTPC_MaxValue` 有 18 行非零（最大 300）。

**推断链**：一个"括弧 + 布尔运算符"的表达式枚举（`RuntimeSoundOperatorType`：`かつ(AND)=1 / または(OR)=2 / 【=4 / 】=8 …`）说明 **游戏侧自己实现了一个小型的"条件求值器"**，用来计算"当前该往 Wwise 送什么值"。`RTPC_ValueChangeDuration = 100 ms` 则是**淡入淡出的平滑时间**——这正是侧链 ducking 在数据层会留下的形状（触发条件 + 目标值 + 平滑时间）。

**社区侧的旁证（B）**：Carter Menary 的听感分析明确写「警报 beep 被推过混音，potentially through side-chain compression with a quick attack and release」，同时指出环境音（树倒、集装箱）**几乎总被混得比其它低**（除 scripted 桥段）。

**Wwise 侧应该长什么样（C）**：
- `Sound_Type` 的 17 个分类（`a:環境音 / c:キャラ / f:メニュー / s:SFX / m:BGM / v:音声 / x:床材質依存 / b:鎧材質依存 / y:マルチチャンネルストリーミング / d:wwiseダイナミックダイアログ`）天然就是 **AuxBus/Bus 的分组键**。首字母即路由。
- 语音清晰的做法通常是 **Bus 上挂 Sidechain（Ducking）**：Source = "SE/Alarm" Bus，Target = "Voice" 与 "BGM" Bus，Attack 快、Release 中等。
- 爆炸"够猛"的做法是 **BGM/Voice 让路，但爆炸自身不被压**（它挂在被 duck 的一方，不挂在 duck 的触发方）。

> **D 级边界**：Wwise 工程本体（Bus 层级、Ducking 具体参数、Voice Limit、Priority 数值）**不在 regulation 里**，上面 6.2 全部是推断。验证方法见 §12。

### 7.1 数据

| 事实 | 实测 |
|---|---|
| BGM 状态枚举 | `Switch_BGMStatus` **8 行**：`normal / in_combat / heat_up_1 / heat_up_2 / heat_up_3 / heat_up_4 / heat_up_5 / death`（原表小写下划线文本） |

| 过场时的 one-shot BGM 行为 | 字段 `OneShotBgmBehaviorOnStart`，枚举 `SoundCutsceneBgmBehaviorType`：`何もしない=0 / 再生=1 / 停止=2` |

### 7.2 四段式

- **设计意图**：让"出撃 → 交战 → Boss 战 → 濒死 → 帰還"这条情绪曲线**不断线**，同时给"任务专用演出"留钩子。
- **实现手段**：
  - **State/Switch 而非曲目切换**：`BGMStatus` 是 Wwise State（全局单值），`BgmEnemyTypeOnStart/End` 是 `Bgm_ID` Switch（按敌人类型选曲）。
  - **5 级 Heat Up**：`heat_up_1..5` 说明战斗强度是一把 **6 档（含 normal/in_combat）的连续量**，Wwise 侧大概率是"同一首曲子的多层 stem 按 State 加减"或"stinger 叠加"。
  - **无缝的接缝在过场侧**：`OneShotBgmBehaviorOnStart`（过场里 BGM 做什么）+ `BgmEnemyTypeOnEnd`（过场结束后回到哪个 ID）+ `EnterMapMuteStopTimeOnDrawCutscene`（何时解除静音）。**"无缝"是三个字段协作的结果，不是音频文件做了 crossfade。**
  - **跳过也要接得上**：`PostPlaySeIdForSkip` 与 `PostPlaySeId` 成对存在（`…1000/…1050`），说明跳过过场时走另一条事件链。
- **玩家体验/结果**：AC6 的"战斗热度上升"感觉是音乐给的，而不是靠 UI 提示。
- **可复用结论**：**要做动态音乐，先在数据层定义"状态枚举"，再定义"进入/离开状态时谁负责把状态推回去"**。AC6 这张 105 行的过场表就是"状态回推表"，是独立游戏最容易漏掉的一环。

### 8.1 数据驱动的混响选择流程（★ 本节的核心）

```
① 收集碰撞点  SoundAutoReverbEvaluationDistParam（6 行，6 种"评估画像"）

      ↓  点寿命：enableLifeTime = 1.0 / 1.8 s

② 算出一个代表距离（开发者命名：AvgDistForOutdoor / AvgDistForWall / AvgDistMax /
   AvgDistMaxForIndoor / AvgDistMaxForUG / AvgDistForUGWall —— 含 UG=地下 变体）
      ↓
③ 距离分档 → 混响预设  SoundAutoReverbSelectParam（5 行）

      IndoorOutdoor 字段 = SOUND_INDOOR_TYPE：0 屋内(IndoorHalf) / 1 完全屋内(IndoorAll)

      Room9_Outdoor_SurfaceIR / Room10_Outdoor_SnowMountainIR / Room11_indoor_garage /
```

### 8.2 四段式

- **设计意图**：AC6 的战斗发生在**50 m 到 1000 m** 的尺度上（`beginDist` 均值 690 m、`SoundAutoReverbSelectParam` 分档上限 1024 m）。手摆混响触发器在这个尺度下根本不够用——一帧飞 100 m 的机甲会瞬间穿过 5 个触发器。
- **实现手段**：**用"碰撞点统计"代替"空间触发器"**。引擎不断记录最近打到的碰撞点（墙/地面/室外），算一个平均距离，再把距离分档映射到 AuxBus。混响变化因此是**连续的、位置无关的**。
- **玩家体验/结果**：在开阔月面听起来干，冲进室内车库瞬间变闷，且**不会因为高速穿越而出现"噗噗噗"的触发器爆音**。
- **可复用结论**：**"距离分档 + 碰撞点统计"是高速游戏（机甲/飞行/赛车）做动态混响的通用解**。甚至可以直接用射线打几条（Raycast）× 距离分档复刻，不必依赖 Wwise Spatial Audio 的完整房间系统。
- **反射层单独一套**：`WwiseValueToStrParam_ReflectTextureType`（6 行：`MoonSurface/Concrete/Iron/Water/Snow/Dirt`，注意第 4 行 ID 重复出现 Snow 与 Dirt）与 `RuntimeReflectTextureType`（100 行，把材质归并成 `none/MoonSurface/Concrete/Snow/Iron/Water/Dirt` 7 类）、`ReflectAuxBusType`（4 行：`Reflect_Preset/no/no/no`）。**即：混响（AuxBus）与反射（Reflect）是两条独立总线，各自按材质分派。**

## 9. 分析三问

### 9.0 先补上通用第二问：关键参数被放大/缩小 10 倍会怎样

音频维度的"参数放大 10 倍"和战斗数值不一样——很多参数只要挪一点点就越界。下面用本机实测到的真实值做边界推演。

| 参数 | 实测值 | ×10 | ÷10 | 判断 |
|---|---|---|---|---|
| `SoundParam.BulletHitSoundRestrictionTime` | 0.56 s | 5.6 s | 0.056 s | **×10 直接毁掉战斗**：连射武器每 5.6 秒才响一次弹着，玩家会以为游戏卡了。÷10 则每次弹着都响，30 Hz 时间基准下会堆出几十层同相位声音 → 严重失真与削波 |
| `SoundParam.CounterBoostPlayInterval` | 0.4 s | 4 s | 0.04 s | 反制推进音的节奏感消失（×10）；÷10 会与推进器循环音打架 |
| `SoundParam.BulletHitSoundRestrictionEnebleDist` | 10000 m | 100 km | 1000 m | 1000 m 意味着**超出 1 km 的弹着完全没有声音**。AC6 的交战距离常在 300–800 m（P7/Bullet 表的射程量级），÷10 会让远距离狙击**彻底没有命中反馈**——这是最容易踩的坑 |
| `PadRumble.beginDist / endDist` | 均值 690 / 1638 m | 6.9 / 16 km | 69 / 164 m | ×10 → 震动全程不衰减，"重"的感觉消失；÷10 → 只有贴脸才震，远程炮击的体感全丢 |
| `SoundAutoReverbSelectParam.DistMaxA` | 最大 1024 m | 10.2 km | 102 m | ×10 → 整个地图都判成"特大混响"，室内外无差别；÷10 → 只有 102 m 内才有环境感，开阔战场全干声 |
| `SoundAutoReverbEvaluationDistParam.maxDistRecordNum` | 10 / 15 / 20 | 100–200 | 1–2 | **这是采样预算**。×10 = 每帧多算 10 倍的碰撞点（CPU 风险）；÷10 = 只记 1–2 个点，混响会在两个房间之间乱跳 |
| `SoundAutoReverbEvaluationDistParam.enableLifeTime` | 1.0 / 1.8 s | 10 / 18 s | 0.1 / 0.18 s | ×10 → 穿过房间后混响"粘"在原地十几秒；÷10 → 混响永远来不及生效 |
| `AiSoundParam.radius` | 30 / 100 / 150 m | 300/1000/1500 m | 3/10/15 m | ×10 → **AI 全图听觉**，潜行玩法直接消失，敌人在你出生点就锁定你；÷10 → AI 变成聋子，靠声音吸引敌人注意的战术（比如用爆炸声引开）全部失效 |
| `AiSoundParam.lifeFrame` | 1 s | 10 s | 0.1 s | 声事件在 AI 记忆里存活时间。×10 = 敌人会追一个十秒前的脚步声 |
| `RuntimeSoundParam_*.RTPC01_ValueChangeDuration` | 100 ms（155/165 行） | 1000 ms | 10 ms | ×10 → 推进器音加速时**慢半拍**，与画面脱节；÷10 → RTPC 变化变成阶梯状，能听到"咔哒"的量化声 |
| `HitEffectSfxParam` 的 SfxId 复用（如 `atkIron_1 = 10` 被 40+ 行共用） | — | — | — | 这不是数值而是**结构**：如果把"复用"改成"每个材质对都独立音效"，资产数会从百量级涨到千量级，**内存与打包体积直接爆掉**。所以复用不是偷懒，是预算决策 |

**结论**：音频参数的设计空间**不是线性的**——大多数参数上下各只能挪 2–3 倍。这跟战斗数值（伤害可以 ×10 还照样能玩）完全不同，也是"音频调参必须靠实测听感而不是算公式"的根本原因。

### 9.1 如果去掉所有锁定提示音？

| 维度 | 变化 |
|---|---|
| 玩家体验 | 锁定/解锁、进入最佳射程（红准星）这些**完全依赖中央准星的视觉**的信息，会退化成"看准星颜色变化"。而 AC6 的战斗要求玩家**同时盯住 3 个东西**（目标、EN 条、弹数），准星颜色变化需要"注意转移"。结果是：软锁被无意中解除、武器不在最佳射程时开火，都是**玩家自己不知道**的失误。 |
| 数据层印证 | 社区逐项观察（B）记录了 4 类独立 chirp；UI 音被放在高频段做频段分离（B）。说明开发组把"UI 可读性"当成硬需求。 |
| 结论 | 这不是"少了个音效"，而是**把 3 个状态从听觉通道搬到视觉通道，直接提高了玩家的注意力预算消耗**。 |

### 9.2 如果 BGM 全程播放不切换？

| 维度 | 变化 |
|---|---|
| 玩家体验 | ① 战斗中「Heat Up」这条强度曲线消失——玩家失去"我打得越来越凶"的正反馈；② 过场结束回到探索时，音乐不会"落回来"，情绪曲线被拉平；③ `PostPlaySeId` 的收尾音（`999991000` 系列）会与 BGM 打架。 |
| 参数放大 10 倍的类比 | 反过来，如果状态切换做得**过度**（比如每 0.5 秒切一次），玩家会听到音乐不断重启——这就是 `OneShotBgmBehaviorOnStart` 的「何もしない / 再生 / 停止」三档存在的理由：**过场开始时的行为必须显式声明，不能默认**。 |
| 结论 | 动态音乐的价值不在于"更好听"，而在于**它是唯一能同时表达"强度"和"阶段"的连续通道**（视觉上要同时表达这两者需要 HUD + 场景氛围两套东西）。 |

### 9.3 如果通讯语音改成纯字幕？

| 维度 | 变化 |
|---|---|
| 玩家体验 | 战斗中玩家 100% 的时间在看准星，**字幕在屏幕边缘会被直接漏读**。AC6 的战斗时长常在 3–8 分钟，通讯语音承担"下一步做什么""队友在哪""Boss 换阶段了"三类信息。改成字幕 = 这三类信息实际丢失。 |
| 数据层印证 | `SoundVoiceBankLoad` 66 行 = 每个 NPC 一个 Voice SoundBank（`NPC000…NPC257`）→ **语音是按角色分包加载的**，说明语音量级之大必须分 bank 管理；`SoundIDSpatialSetting` 给 6 个 Dynamic Dialogue ID 单独设 `ReflectLv`；`VoiceChatGroupType` 有 `ホスト味方` 分组。 |
| 反过来（放大 10 倍） | 如果语音音量被放大 10 倍（或不做 ducking），BGM 与爆炸会被压掉，玩家会**失去"战场态势"的听觉感知**——这与 §6.2 的侧链设计正好对冲。 |
| 结论 | 语音在数据上被当成**独立资源池（Voice Bank）+ 独立空间处理（ReflectLv）+ 独立混音目标（ducking 对象）**，不是"加了个人声"。 |

## 10. TA 转化：音频技术美术（Technical Audio）干什么

### 10.1 岗位职责 → AC6 的对应证据

| 职责 | AC6 里对应的东西 | 你要会什么 |
|---|---|---|
| **中间件集成** | `WwiseValueToStrParam_*` 14 张表的**读写接口**、`SoundVoiceBankLoad` 的 bank 加载清单 | Wwise Unreal/Unity 集成、`AkSoundEngine` API、SoundBank 生成与加载策略、`LoadBankAsync` 时机 |
| **参数（RTPC/Switch）绑定** | `RuntimeSoundGlobalParam`（`acceleration` 0–300，per-area 注册）、`RuntimeSoundParam_*.RTPC01_ID / RTPC01_Value / RTPC01_ValueChangeDuration(100 ms)`、9+4 张 Switch 表 | Wwise Authoring 的 Game Parameter / Switch / State 定义；**命名契约管理**（改表名会静默失效） |
| **资源命名与打包** | `SfxId = 1×10⁵ + 材质×10³ + 槽`（`101000`/`111000`/`120000`）；`TentativePlayerParam` 注释「XYYZZZ」；`Sound_Type` 的 17 个字母前缀（`a:/c:/f:/o:/p:/s:/m:/v:/x:/b:/i:/y:/z:/e:/g:/d:/v_f:`）；NPC SeID 的 9 位 `300001100 / 305001601` | 命名规范设计、Excel/CSV → Wwise 批量导入脚本、ID 段位分配、批量改名工具链 |
| **声音预算与内存** | `SoundVoiceBankLoad` 66 个 Voice Bank；`MapDefaultInfoParam.MapAdditionalSoundBankId`（地图追加 bank）；`GameSystemParam.Net_MapHitSfxOmitteDist = 600 m` + `Net_MyTeamHitSfxOmitteCpuExecRate = 1.2`；`SlotNo` 并发槽位；`AtkParam_Pc` 4 个 Restriction 秒数 | Wwise SoundBank 内容规划、流式 vs 内存（`y:マルチチャンネルストリーミング`）、Voice Limit 设置、内存 profiler、**网络同步时的音频剔除策略** |
| **音频事件与动画/状态同步** | `RuntimeSoundParam_*` 的 `ConditionID → SeID`；`AttachDmypolyID`（绑到骨骼挂点）；`AssetModelSfxParam`（364 行 × 8 组 `sfxId_N / dmypolyId_N`）；`NpcParam` 的 PA 状态机 6 态 × (SfxId + Dmypoly)；`EquipParamWeapon` 的 `guardOpenStart/Stay/End` + `guardInitOpen*` + `residentSfxId_1..4`（+ `IsVisibleForHang` 位） | TAE/动画通知绑定、Dummypoly 概念、状态机驱动的 PostEvent、**同一武器的多个挂点音同时管理** |
| **调试工具** | `WwiseValueToStrParam` 的存在本身就是**可读性工具**（数值→字符串）；`SoundAutoReverb*` 的 `AreaNo` 可覆盖；`disableParam_NT:1 / disableParam_Product:1` 位域（**同一张表里区分 NT 版与制品版输出**） | Wwise Profiler / Capture Log / Voices 视图、自制表查看器、**"表↔工程"一致性校验脚本**（这是 AC6 这套架构的必然产物） |

### 10.2 学习路径（按优先级）

1. **Wwise 101 + 201 认证课程**：重点吃透 **Switch / State / RTPC / Trigger / Event** 五件套，以及 **Bus 层级 + Ducking + AuxBus（混响）+ Reflect**。
2. **一个"数据表驱动"的小项目**：自己用 CSV 定义 `(条件ID, SoundID, 播放类型, 槽位, RTPC名, RTPC值, 平滑ms)`，用脚本生成 Wwise Event + 在 Unity/UE 里读表 Post。**这就是 AC6 `RuntimeSoundParam_*` 的简化版**，做完你就懂了整条链。
3. **空间音频**：Wwise Spatial Audio 的 Room / Portal / `AkRoomAware`，以及**退阶方案**"射线 + 距离分档"（AC6 用的就是这个思路）。
4. **性能**：Wwise Profiler 的 Voices / CPU / Memory 三视图，Voice Limit 与 Virtual Voice 行为。
5. **工具链**：Python/Excel 处理 CSV → WAAPI（Wwise Authoring API）批量建对象。**AC6 的 14 张 Wwise 表意味着他们必然有"表→工程"的自动化管线**。

## 11. 若不用 Wwise：用 MetaSounds（UE5）复刻同一套结构

| AC6 的层 | MetaSounds 对应物 |
|---|---|
| `WwiseValueToStrParam_*`（数值→字符串 Switch） | **不需要**。MetaSounds 直接用 `int`/`enum` 输入；但为了可读性，保留一个 `DataTable` 做 `int → FName` 映射（等价物） |
| `Switch_Weapon_Type` / `ShootSeCategory` 等 Switch | `MetaSound` 的 `Switch on Int` 节点 + `Wave Player` 数组索引 |
| `RuntimeSoundGlobalParam` 的 `acceleration`(0–300) RTPC | `Game Parameter` 输入引脚（float），用 `Interpolate` 节点做 100 ms 平滑（对应 `RTPC01_ValueChangeDuration`） |
| `RuntimeSoundExpressionParam`（布尔表达式求值） | `Trigger`/`Compare`/`Branch` 节点图；或游戏侧 C++ 算好一个 int 再送进来（**更推荐，因为 AC6 就是这么做的**） |
| `RuntimeSoundPlayerType`（13 个调度原型） | 一个 `UAudioComponent` 池 + 自定义 `USoundSubmix` 分配器；或 `Sound Concurrency` 资产 |
| `SlotNo`（并发槽位） | **Sound Concurrency**（`Max Count` + `Resolution`），这是直接对应物 |
| `SoundParam`/`AtkParam` 的限制秒数 | `Sound Concurrency` 的 `Retrigger Time`，或游戏侧计时器 |
| `ReverbAuxBusType` Room0–11 | `Reverb Effect` + `Submix Send`，用 `Audio Volume` 或**自研距离分档**（对应 `SoundAutoReverbSelectParam`）切换 |
| `ReflectTextureType` | 无直接对应物；用 `Submix` + 自定义 `SourceEffect`，或退阶为"按材质换 IR 卷积" |
| `SoundVoiceBankLoad` | `Sound Bank`（UE 的 SoundBank 是对话专用）+ `Async Load` 时机表 |
| `PadRumble`（CAMERA_RUMBLE_PARAM_ST） | **Enhanced Input 的 Force Feedback + 自研距离/优先级管理器**。UE 没有等价的"空间化震动表"，这块必须自研 |

**最小复刻清单（能跑起来的最小闭环）**：
1. 一个 CSV：`ConditionID, SoundId, PlayType, Slot, RtpcName, RtpcValue, FadeMs`。
2. 一个 `UDataTable` + 一个 `UAudioComponent` 池（按 Slot 分桶，每桶 Max Count）。
3. 一个全局 RTPC 管理器（速度/加速度/水平/垂直加速度，对应 `RuntimeSoundGlobalParamType` 100/200/201/202）。
4. 一个"碰撞点平均距离 → Submix 切换"的混响管理器（对应 `SoundAutoReverb*`）。
5. 一个"数值 → 枚举名"的调试输出（对应 `WwiseValueToStrParam`，**这条最容易被忽略，但它是可维护性的关键**）。
